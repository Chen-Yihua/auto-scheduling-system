# 0013. 不改行為的清理可以在目前的 PR 做

- 狀態：已採用
- 日期：2026-11-13

## 背景

[0012](0012-simplify-process-levels.md) 規定審查發現只有四種去處，不阻擋的發現一律開 issue，開發者明確要求時才在這個 PR 修，而且要先寫成驗收條件。PR #91 的實作審查發現兩個測試檔留著沒用到的 import，照規則開了 #93。刪兩行死碼要寫一份兩層格式的 issue、之後再走一次 `/issue`，成本比修正本身高很多。開發者決定放寬：不改行為的清理照童子軍原則（Boy Scout Rule，離開時讓程式比來的時候乾淨一點）在目前的 PR 做（2026-11-13）。

## 決定

1. **不改行為的清理**可以在目前的 PR 做，不開 issue、不寫成驗收條件、不用開發者確認。範圍：
   - 刪死碼：沒用到的 import、變數、函式、檔案，前提是確認過沒有任何引用（包括測試與動態引用）。
   - 文字修正：錯字、註解與文件的措辭，規則與意思不變。
2. **不算清理**的，照原本的規則處理：使用者或呼叫端看得到的文字（API 回應的 `detail`、畫面文字、log 訊息）、測試斷言會看到的文字、重構、改名、套件升級、改變規則的文件內容。判斷不確定時不算清理。
3. 清理放在獨立的 commit，PR 描述列出；審查發現用這個方式處理時，審查紀錄的「結果」寫這個 PR 的 commit。`acceptance-reviewer` 確認清理真的沒有改變行為。
4. 0012 的四種去處加上「這個 PR 清理」，成為五種。

## 放棄的做法

- **只限這個 PR 改到的檔案**：審查常在相關但沒改到的檔案發現死碼（例如 #93），限制檔案就又要開 issue。行為不變的條件已經把風險限制住了。
- **維持開 issue，只簡化 issue 格式**：issue 仍要另外排程、另外開 PR，成本沒有消失。

## 影響

- PR 的 diff 可能多出和需求無關的小改動；放在獨立的 commit、在 PR 描述列出，讓審查的人分得開。
- 需要同步：`implement-and-review`（發現處理表、限制、新增「不改行為的清理」）、`feature`（文字修正的流程）、`/issue`、`feature-implementer`、`acceptance-reviewer` 與本索引；0012 只改狀態行。
