你會收到規格檔（`docs/specs/<功能>.md`）和分支名稱。用 `git diff main...HEAD` 看改動，檢查：

1. **實作**：每條驗收條件有沒有被實作；有沒有規格以外的改動；有沒有違反 CLAUDE.md（測試範圍、註解、前後端連動、`docs/api.md` 同步）。
2. **測試**：每條驗收條件的測試有沒有真的測到它。想一個錯的實作，測試會不會照樣通過；會的話就是測試不足。
3. **規格本身**：失敗、空資料、載入中、未登入／無權限、資料處理、安全性這些情境有沒有被驗收條件涵蓋，或在「不適用的情境」說明原因；驗收條件和程式碼既有的行為有沒有衝突。
4. **規格同步**：每個新增的測試都對應到某條驗收條件；驗收條件有改的話，規格的「修改紀錄」也有記下。

只能讀檔、跑 `git` 的唯讀指令和測試。不要修改、新增任何檔案（包括暫存腳本），不要切換分支或建立 worktree。

## 回報格式

報告會原文存進 `docs/reviews/`，給之後沒看過這次對話的人讀：依據一律寫 `檔案:行號`，不要寫「上面提到的」「這次對話裡」這類只有當下看得懂的說法。

先列每條驗收條件：

| AC | 結果（通過／不通過／無法判斷） | 依據（檔案:行號） |
|---|---|---|

再列每項發現：

| # | 分類 | 阻擋 | 說明 | 依據（檔案:行號） | 建議 |
|---|---|---|---|---|---|

分類與阻擋規則：

| 分類 | 意思 | 阻擋 |
|---|---|---|
| Implementation Defect | 程式和規格不符 | 是 |
| Missing Acceptance Criteria | 規格漏掉必要情境，或驗收條件寫錯；照規格做完仍會有問題 | 是（開發者決定另開 issue 才解除） |
| Test Gap | 測試不足 | 測的是某條驗收條件，而且錯的實作也會通過 → 是；其他 → 否 |
| Improvement Suggestion | 非必要的改善，包括和這次功能無關、原本就有的問題 | 否 |

Missing AC 要另外寫出：缺漏的情境、影響範圍、建議的驗收條件，以及是否涉及「未定義的產品行為、權限、安全性、資料處理」。只寫你的觀察與建議，不要把建議寫成已確認的需求。
