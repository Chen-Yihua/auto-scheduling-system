# 0019. 規格審查依需要才做、驗收條件依需求推導、精簡審查留言

- 狀態：已採用
- 日期：2026-11-26

## 背景

開發流程的規則越加越多，同一條規則寫在好幾份文件裡，審查的輪數也比規定的多：

- 規格審查規定最多 2 次（[0012](0012-simplify-process-levels.md) 決定 4），但「開發者要求的修改不計入」讓次數沒有上限。最近有規格審查的 PR 實際跑了 2 到 4 輪：#179、#183 各 4 輪，#164、#184 各 3 輪，#163、#166、#167、#172 各 2 輪。每一輪 reviewer 都要重讀規格與程式碼。
- 驗收條件靠一份固定的情境清單（失敗、空資料、載入中、未登入、一致性、同時操作、安全性、和既有規則交會）逐項檢查。逐項檢查抓不到需求本身才有的情況：#182（PR #183）的初稿有 19 條驗收條件，審查後變成 35 條；緩衝時間與每日上限沒有範圍限制，到實作審查才被發現。「重新產生」按鈕的實際行為寫錯，到第 1 輪規格審查才發現。
- 審查留言要先存報告原文、再複製成留言檔，最後一輪之後還要另貼補充留言（[0015](0015-review-results-in-pr-comments.md)）。一次開發在草稿資料夾留下十幾個檔案。
- 規格與審查紀錄一律永久保存，`docs/specs/` 累積了 44 份。其中只改流程文件的規格已經被現在的 skill 取代，沒有測試對應，卻還是留著。

## 決定

1. **規格審查依需要才做**：高風險一定做。一般等級只在三種情況下做：規格有影響實作的重要歧義、寫規格時還有要開發者決定的事，或開發者的決定改變了既有的規則或行為。問答裡已經決定好、只影響這次新增行為的事，以及只是確認細節，都不算。這是一般常見的做法：依變更的重要程度與風險決定要不要做設計審查（例如 Rust 的 RFC 只要求「重大變更」），不依過程中有沒有做過決定。不做時，在規格開頭寫「規格審查：沒有（理由）」，和規格一起核准，之後由 `acceptance-reviewer` 補做事實查證與缺漏檢查。快速路徑照舊不做。
2. **規格審查的次數**：第 1 次完整審查；處理發現時改了驗收條件、假設或設計，第 2 次只審改過的部分與受影響的內容。之後的修改（包括開發者要求的修改）由主 session 自己檢查影響。修改帶出新的重大需求歧義、架構或安全問題時，可以再交給 `specification-reviewer`，不受次數限制。
3. **驗收條件依需求推導**：每條 AC 標出對應的需求編號，依需求分組排列。依需求的性質選測試設計方法：輸入驗證用等價類與邊界值、多步驟流程用狀態轉換、多個條件一起決定結果用決策表，其他用正常與異常流程。原本的情境清單不再逐項強制檢查，只在寫完後用來想一下有沒有漏。規格不再有「不適用的情境」一節，刻意不處理的情況寫在「不做」。
4. **發現處理只有一份**：規格審查與實作審查共用 `implement-and-review`「發現處理」，用「核准前」「核准後」兩欄區分做法。
5. **審查留言每輪一則**：內容是報告原文加上「處理」。實作審查的留言在這一輪的修正都 commit 後才貼，要修的項目直接寫修正的 commit；不再另貼補充留言。
6. **問答後不另外確認「已確認」清單**：開發者核准規格時，一併確認已確認決定的對照結果。
7. **交付清單的術語只分兩類**：「新增」與「修改既有定義」。`feature-implementer` 照舊對照 `origin/main`，有相同或相近、定義不同的術語就停下來回報。
8. **規格與審查紀錄可以刪除**：保留下來的程式、測試（包括用 AC 編號對應規格的測試）、文件、ADR 與 open issue 都沒有引用時，就沒有持續參考價值，可以刪除；刪除在 PR 描述列出檔案與理由。ADR 照舊不刪除，被取代時只改狀態。
9. **回報不再檢查所有 open 的 PR**：只回報這次的 PR。

## 放棄的做法

- **一般等級一律做規格審查**（[0006](0006-bugs-use-full-spec.md)、[0007](0007-process-depth-by-risk.md) 的做法）：#28、#46 的問題出在驗收條件的矛盾與缺漏，所以 0007 不採用「輕量不做規格審查」。現在不做規格審查時，`acceptance-reviewer` 會補做事實查證與缺漏檢查，這類問題仍會被發現，只是到實作後才發現。需求有歧義或有開發者的決定時，照舊在實作前審查。
- **把規格審查限制成只做 1 次**：第 1 次處理發現時常會改寫驗收條件，改寫的部分沒人看過，所以保留只看修改部分的第 2 次。
- **刪除全部舊規格**：改到程式的規格，測試用 AC 編號對應它們，open issue 也引用其中幾份，刪掉後這些編號就對不到需求。
- **保留情境清單、另外加測試設計方法**：兩者並存時 agent 會兩套都逐項做，成本更高，清單仍會讓 agent 依清單思考，不依需求思考。

## 影響

- 部分取代 [0005](0005-specification-review.md)（所有等級都做規格審查）、[0007](0007-process-depth-by-risk.md)（「放棄的做法」不採用一般等級不做規格審查）、[0010](0010-scratchpad-loss-recovery.md)（暫存產物表寫出產生它的步驟與每一種的恢復方式）、[0018](0018-fast-path.md)（決定 3 改走完整流程時一定做規格審查）、[0006](0006-bugs-use-full-spec.md)（bug 的規格一律做規格審查）、[0008](0008-grilling-without-plan-mode.md)（開發者確認「已確認」清單後才寫規格草稿）、[0009](0009-docs-delivery-and-glossary.md)（術語的「更新本 PR 的術語」分類）、[0012](0012-simplify-process-levels.md)（決定 4 規格審查次數）、[0015](0015-review-results-in-pr-comments.md)（決定 1 的留言時機與補充留言）。
- 沒有規格審查的一般等級，規格的錯誤要到實作審查才會發現，可能要回頭改規格、重做部分實作。
- `specification-reviewer` 的缺漏檢查改成依需求的性質檢查，不再逐項對照情境清單。
- 被刪除的規格與審查紀錄從 git 歷史找。
