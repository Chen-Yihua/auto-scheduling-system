# 開發流程依風險分級，並建立文件生命週期規則

- 狀態：已核准
- 等級：標準（改 skill、agent 與流程規則；不改程式碼）
- PR：（待補）

## 背景

ADR 0006 之後，`/feature`、`/issue` 的每個變更都走完整規格、最多 2 輪規格審查、實作審查到沒有阻擋，連文件錯字也一樣。開發者要求依風險調整深度，並整理文件的生命週期。盤點時另外發現：ADR 0005「影響」的紀錄檔路徑過時；規格「已完成」狀態沒人維護；沒有「已取代」狀態；審查紀錄只保存最終結果；`docs/specs/README.md` 仍寫「兩種格式」；`architecture.md` 沒寫排程快照存在快取與讀出時間帶 UTC；issue-16 plan 裡「合併後在 #16 留言」只存在 plan 檔（已補留言）。

## 需求

1. `/feature` 第 1 節新增「判斷等級」：高風險、標準、輕量、文字修正，依變更碰到的範圍判斷，定義只寫在這裡（單一來源），`/issue` 引用。
2. 文件生命週期規則寫在 `docs/README.md`「生命週期」，其他文件引用。
3. 修正盤點發現的過時與矛盾內容；歷史文件（ADR、規格、審查紀錄）只改狀態行，不改內容。

## 不做

- 不新增 skill 或 agent。
- 不改寫既有規格、審查紀錄、實驗紀錄的內容（只改狀態行）。
- 不改程式碼。
- 不改 `/feature-grill` 的問答規則（實驗中）。

## 假設

1. 等級由主 session 提出、和規格一起由開發者核准，就足以防止判斷錯誤（ADR 0007「放棄的做法」第 4 點）。
2. ADR 0007 以前的規格沒有「等級」，一律當作完整流程，不補標。

## 驗收條件

| # | 條件 | 類型 |
|---|---|---|
| AC1 | 主 session 讀 `/feature` 或 `/issue` 時，能只依變更碰到的範圍判斷出唯一的等級；下面的例子各自落在預期的等級：文字修正（包括 skill、agent 只改措辭）→ 文字修正；改 CLAUDE.md 或 `docs/` 裡的流程規則 → 標準；單一 API bug（router＋crud＋測試）→ 輕量；只補測試 → 輕量；重構、套件升級 → 不是文字修正；要轉換既有資料的 schema 變更 → 高風險；只新增選填欄位、舊資料照常讀得出來 → 不因此成為高風險；改變認證、授權、資料一致性的保證 → 高風險；新增服務 → 高風險；大型功能 → 標準（改變高風險清單的行為或保證時是高風險） | 使用者行為（用 agent 的開發者） |
| AC2 | 不會過度審查：文字修正不跑任何審查 agent；輕量的規格審查最多 1 輪，實作審查的重新審查看修正的項目、它們的 AC、修正改到的程式與相關測試和連帶影響，不重審整個功能；只有高風險多填檢查表 | 不變條件 |
| AC3 | 輕量不會省略必要的工程判斷：仍有規格審查 1 輪、驗收條件、實作計畫、測試對應（bug 含「改程式前是否失敗」）、CLAUDE.md「完成的定義」；仍要逐一想過 `docs/specs/README.md`「格式」列出的每一類情境（失敗、空資料、載入中、未登入／無權限、資料處理、安全性），合成一列時寫出每一類名稱；沒有被 AC 涵蓋的每一類都要能用一句話說明為什麼不適用，做不到就不是輕量；任何階段發現範圍更大就升級 | 不變條件 |
| AC4 | 文字修正中發現涉及程式行為時，流程要求停下、告訴開發者、重新判斷等級並照新等級從寫規格開始；發現可被利用的漏洞時照「漏洞的處理」，發現無關的問題時照「不阻擋的發現開 issue」 | 使用者行為 |
| AC5 | 已決定事項寫在 scratchpad 的 `<功能>-decisions.md`；核准前逐項對照到規格或 ADR；屬於重大架構決策的在核准前寫成 ADR；審查時開發者的新決定也照同樣方式處理 | 不變條件 |
| AC6 | `docs/README.md`「生命週期」涵蓋永久保存、持續更新、暫存、實驗四類，每類寫出保存或清理的規則；plan 檔在 `/feature` 第 4 節回報後刪除，刪除前把未完成的後續動作列進回報 | 不變條件 |
| AC7 | 規格的狀態可以標「已被 X 取代」或「部分被 X 取代（AC…）」，取代時只改狀態行；規格 README 說明規格是核准當時的紀錄，目前狀態以程式碼、api.md、architecture.md 為準 | 不變條件 |
| AC8 | 審查紀錄格式有「各輪摘要」，處理方式在後續輪改變時接著寫、不覆蓋；每輪完整報告不 commit | 不變條件 |
| AC9 | 同一條規則只定義一次，其他地方引用：等級（`/feature`）、生命週期（`docs/README.md`）、分類與檢查表（`docs/reviews/README.md`）、規格格式（`docs/specs/README.md`）、「改資料庫結構」的範圍（`/feature` 第 3 節）；彼此沒有矛盾 | 不變條件 |
| AC10 | 所有 skill、agent、文件引用的路徑與節名稱都存在；ADR 0001、0002、0005、0006 的狀態行標出被 0007 或之後的改動影響的部分，內文不變 | 不變條件 |
| AC11 | 輕量第 1 輪規格審查後新增或改寫的 AC（包括開發者在核准前要求的修改），在規格審查紀錄的「未經審查的驗收條件」列出，不另外跑一輪；`acceptance-reviewer` 對它們補做事實查證、一致性與缺漏檢查；改寫涉及新的需求、架構決策或重大設計取捨時升級成標準、跑第 2 輪，只是文字澄清不升級 | 不變條件 |

## 不適用的情境

| 情境 | 原因 |
|---|---|
| 載入中、空資料、未登入 | 只改流程文件，沒有畫面與 API |
| 安全性 | 不改「漏洞的處理」與公開資訊邊界；高風險另外加檢查表 |
| 併發 | 不適用 |

## 實作計畫

和這份規格同一個 PR：
- `.claude/skills/feature/SKILL.md`：判斷等級、文字修正流程、已決定事項、輕量審查輪數、回報加等級與清理暫存。
- `.claude/skills/issue/SKILL.md`：等級引用、文字修正沒有規格與審查紀錄。
- `.claude/agents/specification-reviewer.md`、`acceptance-reviewer.md`：收到等級、高風險檢查表、等級偏低列 Specification Defect。
- `docs/specs/README.md`：規格和目前系統的關係、狀態、等級、各等級的規格、核准後。
- `docs/reviews/README.md`：每輪差異、各輪摘要、安全與一致性檢查表、Specification Defect 定義加「等級判斷偏低」。
- `docs/README.md`：生命週期。
- `docs/decisions/0007-process-depth-by-risk.md`（新增）、`README.md`、0001／0005／0006 狀態行。
- `docs/architecture.md`、`CLAUDE.md`、`docs/experiments/feature-grill/TEMPLATE.md`、`docs/specs/issue-28-…`（狀態：部分被 issue-46 取代）。
