# 實作與審查

> 發現可被利用的漏洞時（任何階段），直接讀「漏洞的處理」。「發現處理」也給 `write-spec` 的規格審查用。

核准後照下面的步驟往下做，不用每一步都等開發者確認；只有下面寫明要問開發者的情況才停下來問。

## 步驟

每一步要用到前一步的結果：PR 建好才能貼留言，規格審查的留言貼出才能附給 `acceptance-reviewer`，審查完才有發現可處理。所以照順序做：

1. 整理交付清單，交給 `feature-implementer` 實作、開 PR（「交付清單」「交辦實作與處理回報」）。
2. PR 建立後，貼規格審查每一輪的留言（「審查留言」）。
3. 交給 `acceptance-reviewer` 審查（「交給 acceptance-reviewer 審查」）。
4. 依每項發現處理，要修的交給 `feature-implementer`（「發現處理」）。
5. 這一輪的修正都 commit 後，貼這一輪的留言（「審查留言」）。
6. 還有阻擋的項目就回到第 3 步（「重新審查」）。
7. 沒有阻擋後，照 `feature`「回報」回報。

## Commit 責任

| 種類 | 檔案 | 誰寫內容 | 誰 commit、push |
|---|---|---|---|
| 產品文件 | 規格（`docs/specs/`）、ADR（`docs/decisions/`）、術語表（`docs/glossary.md`） | 主 session（核准前在草稿資料夾（`.drafts/`）） | `feature-implementer`，照交付清單 |
| 程式碼與測試 | 其他 | `feature-implementer` | `feature-implementer` |

文字修正沒有 `feature-implementer`，照 `feature`「文字修正的流程」自己 commit。

## 交付清單

交給 `feature-implementer` 產品文件時附上，列出每個檔案的 repo 路徑與草稿資料夾來源。術語分成「新增」與「修改既有定義」：修改是指開發者確認要改 `origin/main` 上已有的定義，寫出術語名稱、原定義與新定義。

```
交付清單：
- `docs/specs/<功能>.md` ← <草稿資料夾>/<功能>-spec.md（快速路徑改寫成「PR 描述 ← <草稿資料夾>/<功能>-spec.md（快速路徑）」）
- `docs/decisions/NNNN-<名稱>.md` ← <草稿資料夾>/<功能>-adr-<名稱>.md（沒有寫「無」）
- `docs/glossary.md` ← <草稿資料夾>/<功能>-glossary.md（沒有寫「無」）
  - 新增：<名稱>、<名稱>（沒有寫「無」）
  - 修改既有定義（開發者已確認）：<名稱>；原定義：<origin/main 上的定義>；新定義：<新定義>（沒有寫「無」）
```

用在兩個時間點：

- 核准後第一次交辦：交付前在草稿資料夾把規格狀態改成「已核准」，再把交付清單和分支名稱交給 `feature-implementer`。主 session 不自己把規格、ADR、術語表寫進工作目錄。
- 核准後修改規格、ADR、術語表：先改草稿資料夾的來源檔，同樣整理交付清單交辦，列出這次改了哪些檔案、哪些術語。

## 交辦實作與處理回報

- 交給 `feature-implementer`，附上交付清單和分支名稱。
- 它建立 PR 後會把規格開頭的「PR」補上編號、commit、push，並回報 PR 編號。收到後，以 PR 分支上已 commit 的規格為準，同步更新草稿資料夾的 `<功能>-spec.md`，之後的交付清單才不會把 PR 編號蓋回去。
- 它回報規格有問題時：要改規格就照「規格問題的處理」，不用改就直接回覆它怎麼做。
- 它因為「術語重複或衝突」或「工作目錄有歸屬不明的改動」停下來時：用 `clarify-requirements`「需求問答」的格式問開發者，依決定更新交付清單（例如把術語改標成「修改既有定義」），再交辦。
- 它回報的「發現但沒處理的問題」：照「發現處理」第 1 步或第 6 步處理。

## 審查留言

規格審查與實作審查的每一輪，各用一份檔案、貼一則公開的 PR 留言，內容是報告原文加上這一輪的「處理」。之後的讀者在一個地方就看得到這一輪發現了什麼、怎麼處理。照順序做：

1. 報告原文存成草稿資料夾的 `<功能>-spec-review-r<N>.md`（規格審查）或 `<功能>-impl-review-r<N>.md`（實作審查）。
2. 處理完這一輪的每項發現：決定處理方式，開好要開的 issue，要修的修正都 commit。
3. 在同一份檔案加上：
   - 第一行寫 `## <功能>：規格審查第 N 輪` 或 `## <功能>：實作審查第 N 輪（commit <sha>）`（`<sha>` 是這一輪審查的 commit）。
   - 「技術證據」一節包在收合區塊裡：前面加 `<details><summary>技術證據</summary>`，後面加 `</details>`。
   - 最後加一節「處理」，每項發現照 `docs/reviews/README.md`「處理」寫。
4. 有標題開頭是「漏洞：」的發現時，報告原文要保留給重新審查用，所以另外複製成 `<功能>-spec-review-r<N>-comment.md` 或 `<功能>-impl-review-r<N>-comment.md`，在這份照「漏洞的處理」第 4 步改寫，貼這一份。
5. 用 `gh pr comment <PR> --body-file <檔案>` 貼出。成功時印出的網址就是留言連結，回報時附上。

留言貼出後不修改，也不另貼補充留言。最後一輪的留言貼出後才有的修正（例如開發者後來要求的修改），主 session 看過 diff，commit 訊息寫清楚原因；新增或改了驗收條件的，照「核准後修改規格」記在規格的修改紀錄，再照「重新審查」審一輪。

時機：規格審查的留言在 `feature-implementer` 回報 PR 已建立之後、交給 `acceptance-reviewer` 之前，依輪次貼出；實作審查的留言在這一輪的修正都 commit 後、下一輪審查前貼出。

## 交給 acceptance-reviewer 審查

交給 `acceptance-reviewer` 前先 `git fetch origin main`，附上規格檔路徑、等級、分支名稱、PR 編號、規格審查每一輪留言的連結與 PR 描述全文（`gh api repos/{owner}/{repo}/pulls/<PR> --jq .body`）；第 2 輪以後再附上前幾輪實作審查留言的連結，以及這一輪的審查範圍（見「重新審查」）。

沒有規格審查時，改附「沒有規格審查」與原因，`acceptance-reviewer` 會補做規格審查的檢查。沒有規格審查的情況有 3 種：規格寫「規格審查：沒有」、快速路徑（不附規格檔路徑，等級寫「一般（快速路徑）」），以及規格審查的留言檔遺失、開發者決定不補（見 `feature/references/resume.md`）。

## 發現處理

規格審查與實作審查共用。分類的定義見 `docs/reviews/README.md`「分類」。一項發現可能同時符合幾條，所以照下面順序判斷，符合一條就停：漏洞要先擋住細節外流，要開發者決定的要先問，才不會改了又退回。reviewer 沒寫清楚要不要改規格、屬於這次 PR 或無關時，主 session 查證後自己判斷，在「處理」的「決定者」寫主 session。

| # | 情況 | 核准前（規格審查） | 核准後（實作審查） |
|---|---|---|---|
| 1 | 標題開頭是「漏洞：」 | 照「漏洞的處理」 | 照「漏洞的處理」，不交給實作、不開 issue |
| 2 | `question`；或修正會改變規格寫到的行為、新增規格沒寫的行為；或核准後，修正要改已核准的規格、ADR 或術語表（不改行為也算：核准後的修改都要開發者確認）；或涉及沒有核准過的重大架構決策（定義見 `feature`「重大架構決策」，不分阻擋與否） | 先查程式碼與文件能不能回答；要開發者決定的，照「規格問題的處理」第 2 步問。重大架構決策決定後需要時寫 ADR 草稿 | 同左，照「規格問題的處理」。阻擋的回答前不往下做 |
| 3 | 阻擋，不用開發者決定 | 主 session 依依據改草稿 | 交給 `feature-implementer` 修正或補測試 |
| 4 | `nitpick` | 主 session 直接改草稿，交給開發者時列出改了哪些 | 主 session 決定改不改，不開 issue。`feature-implementer` 寫的檔案請它改，主 session 寫的自己改；已核准的規格、ADR、術語表照「核准後修改規格」 |
| 5 | 不阻擋，屬於這次 PR | 列在交給開發者核准的訊息裡，寫主 session 建議採不採用，由開發者決定 | 主 session 決定改不改，要改的交給 `feature-implementer`；不改的在「處理」寫原因 |
| 6 | 不阻擋，和這次 PR 無關 | 列在交給開發者核准的訊息裡；規格還沒核准，不開 issue | 之後還需要有人處理的，照「開 issue 追蹤」開；不需要的在「處理」寫原因。開發者要求在這個 PR 處理時，照第 2 步寫成驗收條件 |

實作審查第 4、5 步的修正，同一輪沒有阻擋的項目時，不另加一輪審查：主 session 看過修正的 diff，把修正的 commit 寫進這一輪留言的「處理」。同一輪還有阻擋的項目時，修正併進下一輪審查。

開發者回答 `question` 或做新決定後，照 `clarify-requirements`「新的決定一律回到決策樹」。

**停下來問開發者時，一起整理不阻擋的發現**：因為第 1、2 步（第 2 步只算阻擋的項目），或「重新審查」第 1 步停下來時，同一則訊息分成「需要你決定」與「不阻擋的發現」兩區；後者寫主 session 對每一項的決定（改、不改、開 issue），開發者可以改。

## 規格問題的處理

要先整理好內容，開發者才有東西可以決定；開發者決定後，才知道是這個 PR 補還是另開 issue。所以照順序做：

1. 整理每一項：問題的情境、影響範圍（哪些檔案、哪些既有驗收條件）、建議的驗收條件與理由。
2. 用 `clarify-requirements`「需求問答」的格式問開發者；核准後的問題另外請開發者決定在這個 PR 補上，還是另開 issue。涉及產品行為、權限、安全性、資料處理或架構時，照「需求問答」的規則標明「需要你選擇」。
3. 依開發者的決定：
   - 這個 PR 補：照下面「核准後修改規格」做影響檢查，把確認後的驗收條件寫進草稿資料夾的規格，照「交付清單」交給 `feature-implementer` 更新規格、實作並補測試。
   - 另開 issue：用 `gh issue create` 記下缺漏與建議的驗收條件，在規格的「修改紀錄」與 PR 描述附上連結，這項就解除阻擋。快速路徑沒有「修改紀錄」，連結附在 PR 描述與那一輪留言的「處理」。

### 核准後修改規格

寫進「修改紀錄」之前，先列出這次修改會影響到的其他驗收條件、假設、實作計畫與測試對應，一起更新或確認不用改。「修改紀錄」照 `docs/specs/README.md`「核准後」寫。

快速路徑核准後要改短版規格時，照 `feature`「快速路徑」。

## 開 issue 追蹤

照「發現處理」第 6 步判斷要開的，才照下面的步驟開。先查重複，才知道要開新的還是在既有 issue 留言；issue 開好，才有連結可以寫進留言檔。所以照順序做：

1. 先查重複：`gh issue list --state all --search "<關鍵字>"`。已有相同問題時，在既有 issue 留言補充（`gh issue comment`），不另開。
2. 一項發現一個 issue；同一個檔案、同一個原因的多項發現合併成一個。
3. 內容照 `docs/issues.md`，最後附來源 PR 的連結，「來源」寫 `PR #NN 第 N 輪規格審查／實作審查 #M`。
4. 標籤：程式行為不正確（包括原本就有的問題）用 `bug`，其餘（例如測試補強、可讀性、文件）用 `enhancement`。不加優先度，交給 `/issue-triage`。
5. 在這一輪審查檔案「處理」的「結果」寫上 issue 連結。

## 漏洞的處理

漏洞的定義見 `docs/reviews/README.md`「漏洞」；細節不能出現的地方見 CLAUDE.md「漏洞」。這裡只寫主 session 怎麼處理，不定義漏洞的修復與發布流程。

先暫停，修正才不會被推到公開的 repo；先查重複再建立，同一個漏洞才不會有兩份 advisory。所以照順序做：

1. 暫停目前的開發流程，不再交給 `feature-implementer` 任何修正。
2. 可以提出建立 private security advisory 的方案（附上要填的內容），開發者確認後才建立：
   1. 先查重複：`gh api --paginate repos/{owner}/{repo}/security-advisories --jq '.[] | {ghsa_id, summary, state}'`。已有相同問題時沿用它的 GHSA 編號，需要補充時先把要更新的內容寫進草稿資料夾的 `<功能>-advisory.json`，再 `gh api -X PATCH repos/{owner}/{repo}/security-advisories/<GHSA> --input .drafts/<功能>-advisory.json` 更新 description，不另建。
   2. 建立草稿 advisory（只有 repo 管理者看得到）：把下面的 JSON 寫進草稿資料夾的 `<功能>-advisory.json`，再 `gh api -X POST repos/{owner}/{repo}/security-advisories --input .drafts/<功能>-advisory.json`。
      ```json
      {
        "summary": "<一句話>",
        "description": "現象、影響範圍、依據（檔案:行號）、建議的修法、來源 PR",
        "severity": "low | medium | high | critical",
        "vulnerabilities": [{"package": {"ecosystem": "other", "name": "auto-scheduling-system"}}]
      }
      ```
   3. 建立失敗時，不要改開公開 issue，停下來問開發者。
3. 之後照開發者決定的方式處理；開發者決定前，PR 不能結束，不看 reviewer 標的阻擋。
4. 貼留言前，在留言檔（「審查留言」第 4 步）檢查整份報告（「摘要」「問題說明」「技術證據」的每一張表），所有提到漏洞位置或利用方式的地方，都改寫成一般性的描述（或開發者確認建立後的 advisory 編號）。報告原文不動，也不 commit。重新審查時 reviewer 只看得到改寫過的留言，所以主 session 把原始內容直接寫進給 reviewer 的指示，不存檔。

## 重新審查

修正後重新審查，直到沒有阻擋的項目為止。第 2 輪以後的審查範圍照 `feature`「判斷等級」表的「實作審查」欄，寫進給 `acceptance-reviewer` 的指示。

連續好幾輪都還有阻擋，通常是規格或做法本身有問題，再交回實作也修不好，所以：

1. 實作審查連續 3 輪都還有阻擋的項目時，第 3 輪的留言「結果」寫「等開發者決定」，貼出後不再交給 `feature-implementer` 任何修正；照「發現處理」最後一段整理後問開發者。不看是不是同一個原因。
2. 開發者決定繼續後，從下一輪重新算。

規格審查的次數見 `write-spec`「審查次數」，不適用這一節。

## 限制

- 不可把 agent 推測的行為當成已確認的需求；開發者確認前，不寫進規格的驗收條件。
- 不可因為發現缺漏就擴大範圍：只做開發者確認過要在這個 PR 補上的部分。
