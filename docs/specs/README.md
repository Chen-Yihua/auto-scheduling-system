# 功能規格

用 `/feature` 開發的每個變更一份，檔名 `<功能>.md`；用 `/issue` 開發的檔名 `issue-<N>-<簡短名稱>.md`。等級是「文字修正」的不寫規格（見 `/feature`「判斷等級」）。核准後才存進這裡，和實作放在同一個 PR。為什麼放在這裡見 [ADR 0002](../decisions/0002-specs-in-repo.md)。

規格是實作 agent 唯一的需求來源，要寫到不看討論過程也能照著做。

照 `CLAUDE.md`「寫作規則」；流程用語的意思見 `docs/README.md`「術語表」。

## 規格和目前系統的關係

規格記錄的是**核准當時**的需求、設計與驗收條件，PR 合併後不再隨程式更新。之後的變更改了它定義的行為，寫在新的規格裡，不回頭改舊規格的內容。目前系統的行為以程式碼、[api.md](../api.md)、[architecture.md](../architecture.md) 為準。

- 新規格取代了舊規格定義的行為時，在新規格的 PR 裡把舊規格的「狀態」改成「已被 [<新規格>](<檔名>.md) 取代」；只取代一部分時寫「部分被 [<新規格>](<檔名>.md) 取代（AC3、AC5）」。只改狀態這一行，其他內容保留原樣。
- 規格永久保存，不因為過時而刪除（[docs/README.md](../README.md)「生命週期」）。
- ADR 0007 以前的規格有的寫「已完成」，意思是 PR 已合併，等同「已核准」；之後不再使用這個狀態，因為合併由開發者決定，沒有人負責回頭更新。

## 驗收條件怎麼寫

各等級都適用，issue 裡「建議的驗收條件」也照這裡寫（見 [docs/issues.md](../issues.md)）。

- **使用者行為**：使用者（或部署維護者、用 agent 的開發者）做了什麼、看得到什麼結果。
- **不變條件**：只看畫面驗不出來、但需求成立一定要守住的系統狀態，例如資料庫和 Google Calendar 的事件一致、同時送出兩個請求的結果和依序執行一樣、只動得到自己的資料。需求涉及資料一致性、併發、權限、外部系統狀態時一定要寫，因為只看畫面的 AC 讓錯的實作也能通過。
- 每條都要能驗證：寫得出對應的測試，或寫明手動驗證的步驟（例如 CI run、部署紀錄）。
- 每條驗收條件只講一件事：出現「而且」「以及」就考慮拆開。
- 和需求無關的技術細節不寫進 AC，例如指定實作方式、沒有人會碰到的防禦情境。

## 格式

```markdown
# <功能名稱>

- 狀態：草稿 | 已核准 | 已被 [<規格>](<檔名>.md) 取代 | 部分被 [<規格>](<檔名>.md) 取代（AC…）
- 等級：一般 | 高風險（理由）
- issue：#NN（由 `/issue` 開發時）
- PR：#NN

## 簡短說明
這份規格要解決什麼，用一兩句話。寫不清楚、範圍可能太大時，在「請你決定」提出要不要拆成多份規格的建議，由開發者決定。

## 背景
為什麼要做。

## 需求
要做什麼。每條需求只講一件事：出現「而且」「以及」就考慮拆開。

## 不做
明確排除的範圍。

## 假設
程式碼看不出來、經開發者核准的業務規則，逐條編號。

## 驗收條件
| # | 條件 |
|---|---|
| AC1 | 在 X 情況下，系統要 Y |

每條都要能驗證。逐一想過失敗、空資料、載入中、未登入／無權限、資料處理、安全性；不適用的寫在下面並說明原因。

## 實作計畫
要改的檔案、步驟，以及為什麼這樣做（解決做法）。高風險另外寫考慮過、沒選的做法與理由；屬於重大架構決策的連結 ADR。
```

## 修 bug 時

修 bug 的規格照一般的格式寫，另外：

- **背景**：寫重現步驟、預期與實際的結果，以及原因，原因要附程式碼依據（`檔案:行號`）。重現步驟與原因是對現有系統的描述，規格審查會去查證。修正前先確認根本原因。
- **AC1**：對應重現步驟：照重現步驟操作，不再出現這個錯誤。
- **其他 AC**：這次修正不能弄壞的既有行為（有的話）。
- **測試對應**：每條 AC 都有測試，並填「改程式前是否失敗」。AC1 對應的測試，改程式前必須失敗，才證明它真的重現了這個 bug。

## 各等級的規格

等級的判斷與各等級的審查見 `/feature`「判斷等級」（[ADR 0007](../decisions/0007-process-depth-by-risk.md)）。草稿寫在 scratchpad 的 `<功能>-spec.md`，核准前不存進這裡，所以狀態「草稿」只會出現在 scratchpad 的草稿。

| 等級 | 必要的節 | 可以省略 |
|---|---|---|
| 一般 | 簡短說明、背景、需求、驗收條件、實作計畫、測試對應、修改紀錄、請你決定 | 沒有內容的「不做」「假設」；「不適用的情境」可以合成一列，例如「載入中、未登入：沒有改到畫面與登入流程」 |
| 高風險 | 全部；「實作計畫」寫放棄的做法 | 無 |

省略是指那一節沒有內容，不是沒有想過：一般也要逐一想過「格式」裡「驗收條件」下方列出的每一類情境，合成一列時要寫出每一類的名稱；沒有被驗收條件涵蓋的每一類，都要能用一句話說明為什麼不適用，做不到就不能省略那一節。

## 核准後

規格核准後，驗收條件的任何新增、修改、刪除都要記在「修改紀錄」，並註明開發者確認過。「原因」寫決定的內容（一句話）＋寫在哪裡（規格的節或 AC 編號、ADR 編號，或「術語表」）＋檢查過哪些，例如「開發者決定一般等級也要問答 → AC3；檢查過 AC1、AC4 不用改」；有規格的等級（一般、高風險）都這樣寫。PR 合併後的變更照上面「規格和目前系統的關係」寫新規格。
