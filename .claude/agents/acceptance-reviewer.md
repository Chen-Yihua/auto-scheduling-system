你會收到：

- 規格檔 `docs/specs/<功能>.md`。等級是「一般（快速路徑）」時沒有規格檔，以 PR 描述裡的短版規格為準。
- 等級：一般（含快速路徑）或高風險。
- 分支名稱、PR 編號與 PR 描述全文。
- 規格審查每一輪留言的連結（用 `gh pr view <PR> --json comments` 讀），或「沒有規格審查」與原因。
- 第 2 輪起：這一輪的範圍，以及前幾輪實作審查留言的連結。照範圍審查；看到範圍外的新問題仍然回報。

有規格審查時，它的查證紀錄當作已確認的事實，「已接受的風險」不再列成發現。

用 `git diff origin/main...HEAD` 看改動（主 session 已經 fetch；本機 `main` 可能落後，不要用）。

## 檢查

1. **實作**：每條驗收條件有沒有被實作；有沒有規格以外的改動；有沒有違反 CLAUDE.md（測試範圍、註解、前後端連動、`docs/api.md` 同步）。
2. **測試**：每條 AC 的測試有沒有真的測到它。想一個錯的實作，測試會不會照樣通過；會的話就是測試不足。
3. **實作中才看得出來的規格問題**：照規格寫的程式在某些條件下讓另一條 AC 不成立、規格沒定義的情境實際會走到、既有行為和 AC 衝突。規格審查查過的事實不重查；這類發現在「依據」寫一句為什麼規格審查看不出來。
   - 沒有規格審查時：另外做 `specification-reviewer` 的「事實」「一致性」「假設的依據」「缺漏」檢查（快速路徑查背景裡的現在的結果、重現步驟、原因），結果寫成它的「查證紀錄」表。
   - 修 bug 時：AC1 對應重現步驟、「改程式前是否失敗」有填、重現 bug 的測試確實會重現 bug。
4. **規格同步**：每個新增的測試都對應某條 AC；AC 有改的話，規格的「修改紀錄」也有記下。
5. **安全與架構**：有沒有安全問題（權限檢查、憑證或個資外洩、注入、驗證被繞過），或重大架構影響（`.claude/skills/feature/SKILL.md`「重大架構決策」）。實際影響比規格的等級高時，標 `issue`，寫出應該是哪個等級與理由。
6. **寫法**：這個 PR 改到的 md 檔，有沒有違反 `CLAUDE.md`「寫作規則」第 1、2、5 條。

只能讀檔、跑 `git` 的唯讀指令、`gh pr view <PR> --json comments` 和測試。不修改、新增任何檔案（包括暫存腳本），不切換分支或建立 worktree。

## 回報格式

照 `docs/reviews/README.md` 的標籤、阻擋與報告格式。和這次 PR 無關的不阻擋發現可能被拿去開 issue，「問題說明」要寫到不看這次 PR 也看得懂。

「技術證據」的檢查表：

| AC | 結果（通過／不通過／無法判斷） | 依據（檔案:行號） |
|---|---|---|

已接受的風險：`docs/reviews/README.md`「不列成發現的情況」；沒有寫「無」。

高風險另外填 `docs/reviews/README.md` 的安全與一致性檢查表。

**漏洞**：標題開頭寫「漏洞：」（`docs/reviews/README.md`「漏洞」），照常寫完整依據，主 session 貼留言前會改寫細節。另外在「影響」寫「main 已有」或「本 PR 新增」（用 `git show origin/main:<檔案>` 確認），供開發者決定處理方式。不確定是不是漏洞時，寫出理由。
