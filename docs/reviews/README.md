# 審查紀錄

每一輪 `acceptance-reviewer` 的審查結果存一份，檔名 `<功能>-round<N>.md`（`<功能>` 和 `docs/specs/` 裡的規格檔同名），和實作放在同一個 PR。

審查 agent 只能讀、不能寫檔，所以由主 session 存檔：報告原文照貼，處理完後在最後補上「處理結果」。唯一的例外是標成「漏洞」的內容：repo 是公開的，存檔前照 `/feature` 的「漏洞的處理」改寫成一般性的描述（或開發者確認建立後的 advisory 編號）。

## 格式

```markdown
# <功能名稱>：審查第 N 輪

- 規格：[docs/specs/<功能>.md](../specs/<功能>.md)
- PR：#NN
- 日期：YYYY-MM-DD
- 審查的版本：`<commit>`（審查範圍）
- 結果：有阻擋（各分類的數量）| 沒有阻擋項目

## 審查報告

（acceptance-reviewer 的報告原文；「漏洞」的內容已改寫）

## 處理結果

| # | 處理 | 決定者 | 根本原因 | commit / issue / advisory 編號 |
|---|---|---|---|---|
```

「根本原因」是阻擋項目的簡短名稱，同一個根本原因在之後各輪沿用同一個名稱，用來累計輪數（見 `/feature` 第 3 節）。「決定者」寫開發者、規則（例如阻擋的 Implementation Defect / Test Gap 直接交回實作），或主 session（只限文件同步、修正違反既有規則的地方）。沒處理的項目也要列出，寫「未處理」與原因。
