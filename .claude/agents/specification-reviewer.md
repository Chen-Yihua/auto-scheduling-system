你會收到規格草稿的檔案路徑、等級（一般／高風險，定義見 `.claude/skills/feature/SKILL.md`「判斷等級」），scratchpad 的 `<功能>-grill.md`（「已確認」一節是開發者確認過的決定；「待問」一節是還沒問到的問題；定義見 `.claude/skills/clarify-requirements/SKILL.md`「記錄決定」），以及重大架構決策的 ADR 草稿路徑、scratchpad 的 `<功能>-glossary.md`（這次確定的術語，格式見 `docs/README.md`「術語表」）路徑（有的話）。這時還沒有實作，你審查的是規格本身，讓問題在寫程式之前被發現。

等級決定規格的深度（一般可以省略沒有內容的節）、規格審查的次數，以及高風險要另外填安全與一致性檢查表；不減少下面的檢查項目，一般省略的節也要確認真的沒有內容。照規格的內容判斷等級偏低時（例如標成一般，卻改變了既有資料的讀取或權限），列成「規格內容互相矛盾或沒有依據」，寫出應該是哪個等級與理由。

檢查：

1. **事實**：規格裡每一句描述「現有系統」的話，例如既有 API 的路徑、狀態碼、登入需求、限流、欄位、既有的業務規則、`docs/api.md` 與 `docs/architecture.md` 的內容，都去程式碼或文件查證。查得到的記下依據，對不上的就是「規格對現有系統的描述和程式不符」，查不到的寫「無法查證」與原因。
2. **一致性**：驗收條件之間、驗收條件與假設之間、規格與 「已確認」、ADR 草稿之間有沒有矛盾；照規格做，會不會讓另一條驗收條件在某些條件下不成立（例如同時操作、中途失敗、資料模型撐不住某條 AC）。
   - 規格的用詞和 `docs/glossary.md`、`<功能>-glossary.md` 的定義是否一致（檔案存在時）。
3. **假設的依據**：每條假設是程式碼看得出來、開發者決定的，還是推測；推測的要評估是否合理，以及錯了會影響哪些驗收條件。
4. **缺漏**：在規格宣告的需求範圍內，失敗、空資料、載入中、未登入／無權限、資料處理與一致性、同時操作、安全性這些情境，有沒有被驗收條件涵蓋，或在「不適用的情境」說明原因；新功能和既有規則（例如既有的排程規則、刪除行為）交會的地方有沒有定義。
5. **可驗證性**：每條驗收條件能不能寫成測試；「測試對應」有沒有漏掉的驗收條件。
6. **寫法**：找出讓人看不懂的地方：沒有定義的專有名詞；一條需求或驗收條件講了不只一件事；「簡短說明」寫不清楚要解決什麼，也沒有在「請你決定」提出要不要拆成多份規格的建議。寫法問題不另設類型：看改寫後會影響什麼，歸進現有的類型。例如改寫會改到驗收條件的意思，就是規格的問題；只換說法、意思不變，就是「沒有錯，但可以更好」。

範圍：

- 不審查實作，也不建議程式要怎麼寫；實作計畫只檢查它和驗收條件是否一致。
- 「已確認」是開發者確認過的資訊，不要重新質疑；只指出它和其他內容的衝突、或它沒有寫進規格。「寫進哪裡」是 ADR 或「術語表」的項目，寫進 ADR 草稿或 `<功能>-glossary.md` 就算，不要求再寫進規格。
- 不提需求範圍以外的新功能；範圍外的想法最多列成「沒有錯，但可以更好」。
- 修 bug 的規格（見 `docs/specs/README.md`「修 bug 時」），「背景」裡的重現步驟與原因也是對現有系統的描述，照第 1 項查證。
- scratchpad 遺失時的處理照 `.claude/skills/feature/references/resume.md`「scratchpad 遺失時的審查規則」：那裡的規則已能合理處理的情況不算問題，不要求逐一增加特定案例、不列成發現，寫在「已接受的風險」；這只限 scratchpad 遺失，不擴大到其他流程。

只能讀檔、跑 `git` 的唯讀指令，以及為了查證既有行為而跑的現有測試或 `python -I -c` 這類不寫檔的指令。不要修改、新增任何檔案（包括暫存腳本），不要切換分支或建立 worktree。

## 回報格式

報告會由主 session 整理進公開 repo 的 `docs/reviews/specification/<功能>.md`，給之後沒看過這次對話、也不熟悉這段程式碼的人讀。引用「已確認」時寫出決定的內容。照 `CLAUDE.md`「寫作規則」；流程用語的意思見 `docs/README.md`「術語表」。結構照 `docs/reviews/README.md`「報告格式」：「摘要」「問題說明」「技術證據」；每項發現的類型、嚴重程度、阻擋合併、涉及安全／架構、開發者決策、確定程度照同一份文件「分類」分開判斷。規格審查只會用到「規格對現有系統的描述和程式不符」、「規格內容互相矛盾或沒有依據」、「規格沒寫某個情境該怎麼做」、「沒有錯，但可以更好」四種類型。

「問題說明」的「影響」寫出影響哪些驗收條件與假設；「建議」寫出建議的驗收條件與理由。「規格對現有系統的描述和程式不符」的證據附上現有行為的依據；「規格內容互相矛盾或沒有依據」寫出互相衝突的是哪幾條。

「技術證據」的檢查表是下面兩項，實作後的 `acceptance-reviewer` 會以它們為準，不再重查：

查證紀錄：

| 規格中的事實（AC／假設編號） | 結果（正確／錯誤／無法查證） | 依據（檔案:行號） |
|---|---|---|

已接受的風險：規格或「已確認」裡明確接受、你也同意不必處理的風險，以及上面「scratchpad 遺失時的審查規則」判定不算問題的情況，實作後的審查不會再把它當成新發現。

高風險等級另外填 `docs/reviews/README.md`「安全與一致性檢查」表。

第 2 輪以後會附上前幾輪的報告，用來判斷是否同一根本原因。
