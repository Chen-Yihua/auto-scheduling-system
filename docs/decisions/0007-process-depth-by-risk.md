# 0007. 依變更碰到的範圍決定規格與審查的深度

- 狀態：已採用
- 日期：2026-11-08

## 背景

[0006](0006-bugs-use-full-spec.md) 之後，`/feature` 和 `/issue` 的每個變更都走同一套流程：完整格式的規格、最多 2 輪規格審查、實作審查直到沒有阻擋。只改文件錯字的 issue 也要寫完整規格、跑兩個審查 agent。開發者要求（2026-11-07）依變更的複雜度與風險調整規格與審查的深度，降低不必要的流程成本，但不降低測試與驗收的標準。

0006 放棄了「依 bug 的大小決定要不要審查」，因為大小在寫規格前不好判斷：#28、#46 一開始看起來都是小修正，問題出在驗收條件之間的矛盾與缺漏，只有規格審查找得到。

## 決定

- 分成四個等級：文字修正、輕量、標準、高風險。定義、各等級要做的步驟只寫在 `/feature` 第 1 節「判斷等級」。
- **依變更碰到什麼判斷，不依大小**：高風險看的是有沒有改變資料一致性、認證與授權、個資保護、外部同步、安全性的行為或保證，或屬於重大架構決策；輕量要只在一個功能範圍內（例如一支 API 的 router＋crud＋測試），而且不是高風險。改幾行不是判斷依據。
- 等級由主 session 提出、寫明理由，和規格一起由開發者核准。判斷不確定時取較高的等級；任何階段發現碰到更高等級的範圍就升級，補做該等級的步驟；降級要開發者同意。
- **輕量保留 0006 的核心**：驗收條件、實作計畫、測試對應（含「改程式前是否失敗」）與 1 輪規格審查都要有；可以省略的只有沒有內容的節，以及第 2 輪之後的自動審查。第 1 輪後新增或改寫的驗收條件標成「未經審查」，由實作審查補做事實查證、一致性與情境檢查；涉及新的需求、架構決策或重大設計取捨時升級成標準。
- **文字修正**（不改變任何程式行為，也不改流程文件裡的規則；重構、套件升級不算）不寫規格檔、不做審查，由主 session 在 plan mode 列出改動、開發者核准後直接修改並開 PR。改動沒有行為，[0001](0001-separate-feature-roles.md) 分開角色要防的「計畫漏掉的情境」不存在。
- **高風險**在標準之外，實作計畫要寫放棄的做法與理由，兩種審查都要填安全與一致性檢查表；屬於重大架構決策的，在規格核准前寫成 ADR。
- 所有等級都照 CLAUDE.md「完成的定義」與「開發流程」：改行為就要有測試、修 bug 要有改程式前會失敗的回歸測試、透過 PR 與 CI、合併由開發者決定。

## 放棄的做法

- **把 `/issue` 和 `/feature` 拆成兩套流程**：0003 的理由仍然成立，兩套會各自演變。等級和入口無關，`/feature` 的需求也可能是文字修正，issue 也可能是高風險。
- **依改動的行數或檔案數分級**：0006 已經說明大小在寫規格前不好判斷。
- **輕量不做規格審查**：0006 的 #28、#46 都是規格審查才找得到的問題，省掉就回到 0006 之前的狀況。
- **由 agent 自己決定等級、不經開發者**：等級決定要不要審查，判斷錯了的代價由開發者承擔，所以和規格一起核准。
- **碰到資料庫欄位、個資或外部同步就算高風險**：大部分變更都會讀寫資料庫，高風險就失去區分作用。要看的是一致性、權限、個資、外部同步、安全的行為或保證有沒有改變。
- **「模組」照架構分層定義**：單一 API 的 bug 通常同時改 router 和 crud，會被判成標準，輕量幾乎用不到。
- **輕量第 1 輪後改寫驗收條件就一律升級**：多數改寫只是把文字寫清楚，一律升級等於輕量也跑 2 輪；一律問開發者則把負擔轉給開發者。改成標成「未經審查」由實作審查補查，只有新的需求、架構決策或重大設計取捨才升級。

## 影響

- 規格多一行「等級」。0007 以前的規格沒有這一行，當作標準或高風險的完整流程。
- 輕量的規格審查只跑 1 輪，第 1 輪還有阻擋時直接問開發者，開發者要回答的問題可能比標準等級早出現。
- [0002](0002-specs-in-repo.md) 的「每個功能的規格放在 `docs/specs/`」，文字修正是例外，不寫規格檔。
- 輕量第 1 輪後改寫的驗收條件，問題要到實作審查才會被發現，修正的成本比在規格階段高；這是為了不讓輕量跑 2 輪而接受的代價。
- 0006 的「bug 一律用完整格式並做規格審查」改成：文字修正不寫規格、不審查；輕量可以省略沒有內容的節、規格審查 1 輪。0006 的其他決定照舊。
- 不同等級跑出來的實驗紀錄（`docs/experiments/`）不能直接比較，紀錄已經有「流程版本」欄位。
