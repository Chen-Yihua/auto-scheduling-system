# scratchpad 遺失時以暫存產物為單位的通用恢復規則

- 狀態：已核准
- 等級：標準（改 `/feature`、兩個 reviewer、`docs/README.md`、`docs/reviews/README.md` 的流程規則；不改程式碼。不涉及安全、資料一致性，也不是重大架構決策）
- issue：#73、#72
- PR：#（待開）

## 背景

來源 issue：https://github.com/Chen-Yihua/auto-scheduling-system/issues/73、https://github.com/Chen-Yihua/auto-scheduling-system/issues/72

`/feature` 核准前只寫 scratchpad；scratchpad 是 session 專用的暫存資料夾，session 中斷後可能被清掉。`/feature` 第 4 節「暫停與接續」（`.claude/skills/feature/SKILL.md:301-306`）在舊 scratchpad 不存在時，依時間點列了四種情況：核准前、核准後、核准後但 PR 還沒建立、文字修正。`docs/README.md:29` 又把同一套規則抄了一份，`docs/README.md:23` 與 `.claude/skills/feature/SKILL.md:20`、`:301` 各列了一次暫存檔清單。

PR #71 的實作審查中，同一個根本原因「舊 scratchpad 不存在時的接續」連續 3 輪阻擋：每補一個時間點，就找到下一個（規格審查紀錄草稿 commit 前、審查報告原文整理前、文字修正核准後但還沒套用完）。原因是時間點可以一直切下去，列舉永遠不完整。依 ADR 0003 的先例（每補一層規則就出現新的邊界情況時，另開 issue 一次設計），這些情況移到 #73。#72 則是同一段規則的另一個缺口：核准後接續時，從 PR 分支複製的術語表、ADR、審查紀錄要存成什麼檔名、放什麼內容沒有寫。

scratchpad 裡的每一種暫存產物都由某個步驟產生。以「遺失了哪個產物」而不是「在哪個時間點遺失」來定義恢復方式，規則就不需要逐一列舉時間點。ADR 0009 只寫了舊路徑存在時的複製與編號接續（`docs/decisions/0009-docs-delivery-and-glossary.md:29`），沒有寫遺失時的處理，所以這次新增 ADR 0010 補充，不改 0009。

## 需求

1. **通用恢復規則**：接續時舊 scratchpad 不存在（或缺了部分檔案），主 session 依序處理：
   1. 找出遺失的暫存產物（對照需求 2 的清單）。
   2. 先 `git fetch`，確認 repo、本機分支、`origin` 上這次的分支或工作目錄裡是否已有它的正式版本。有就以正式版本為準，照需求 2 的恢復方式處理，不憑記憶重新產生。
   3. 確認是否已有部分成果（例如分支上已改了一部分）。有就照需求 3 逐項列出完成狀態，避免重複執行或遺漏。
   4. 用了正式版本或部分成果時，告訴開發者依據的來源（分支、commit、工作目錄有沒有未 commit 的改動），請開發者確認之後有沒有已確認、但還沒交付或寫進紀錄的修改或項目。有就逐項列出，照需求 3 標狀態；沒有依據（正式版本與部分成果都找不到）的項目，重新核准後才執行。項目清單本身遺失時（例如文字修正的改動清單）也照這一步，由開發者補上項目。
   5. 沒有可恢復的成果時，告訴開發者缺了哪個產物，依產生它的步驟，用「需求問答」的格式請開發者照清單該列的選項選擇（清單沒有寫的，選重做或不補）。已核准的內容要重做時，重做後要重新核准；不把已核准的內容當成未核准，也不憑記憶重寫正式文件。
   6. 不補時，在 PR 描述記錄遺失的項目、影響與不補的決定；有實作審查紀錄的，同時寫在紀錄的「已接受的風險」。紀錄的「尚未處理」若也列出，註明「已決定不補」，不當成待辦。
2. **暫存產物清單**：在 `/feature` 第 4 節「暫停與接續」定義一次，每一種寫出檔名、產生它的步驟與恢復方式。清單不是固定的：新增暫存產物時，同時寫出這三項，就能套用需求 1。目前的清單：

   | 暫存產物 | 檔名 | 產生它的步驟 | 正式版本與恢復方式 |
   |---|---|---|---|
   | Context／Frontier | `<功能>-grill.md` | 標準、高風險：需求問答；輕量、文字修正：寫規格草稿或改動清單時的確認；核准後的決定也會寫進來 | 核准後，決定已寫進規格（內容與落點），以規格為準，不重建；之後新的決定 C、Q 從 1 重新編號。核准前沒有正式版本，從產生它的步驟重做 |
   | 術語 | `<功能>-glossary.md` | 需求問答、寫規格草稿、規格審查；核准後的實作回報、實作審查 | 已交付的術語以正式版本（第 2 步找到的位置）的 `docs/glossary.md` 為準，不複製；之後要修改時，只把要修改的術語條目照「術語表」的格式複製到 `<功能>-glossary.md`（不含檔頭）再改。核准前沒有正式版本，重新確認 |
   | 規格草稿（文字修正是改動清單） | `<功能>-spec.md` | 寫規格草稿／寫改動清單；核准後修改規格 | 規格以正式版本（第 2 步找到的位置）的 `docs/specs/<功能>.md` 為準，複製成 `<功能>-spec.md`（之後照交付清單交付要用）；找不到時，已核准的規格請開發者選擇重寫再核准或取消。文字修正的改動清單沒有正式版本，照需求 1 第 3、4 步 |
   | ADR 草稿 | `<功能>-adr-<名稱>.md` | 寫規格草稿；核准後的重大架構決策 | 以正式版本（第 2 步找到的位置）的 `docs/decisions/` 為準，不複製；之後要修改時，從 PR 分支複製到 `<功能>-adr-<名稱>.md` 再改。沒有時重寫，和規格一起重新核准 |
   | 規格審查紀錄草稿 | `<功能>-spec-review.md` | 規格審查 | 以正式版本（第 2 步找到的位置）的 `docs/reviews/specification/` 為準，不複製；沒有時請開發者選擇重跑規格審查（審目前的規格）或不補（需求 4） |
   | 審查報告原文 | 各輪報告 | 該輪審查 | 已整理進審查紀錄的部分以紀錄為準；沒有整理的請開發者選擇重跑該輪審查或不補 |

   重跑審查的發現：核准前照第 1 節「規格審查」的處理表，核准後照第 3 節「規格問題的處理」與處理表；重跑同一輪不另計輪數。
3. **部分改動的完成狀態**：逐項標出已完成、未完成、部分完成、待確認。無法確認某項是否完成時標成「待確認」，不可推定已完成。未完成、部分完成與待確認的項目，請開發者確認怎麼處理。
4. **規格審查紀錄不補時**：交給 `acceptance-reviewer` 時寫明「沒有規格審查紀錄」與原因，跳過「確認規格審查紀錄已 commit、push」；`acceptance-reviewer` 照既有的「完整格式的規格卻沒有規格審查紀錄」補做情境檢查。PR 描述與實作審查紀錄照需求 1 第 6 步。
5. **取代四種情況**：刪除 `/feature`「暫停與接續」依時間點列的四種情況（核准前、核准後、核准後但 PR 還沒建立、文字修正），全部改用需求 1–4。暫停時「告訴開發者 scratchpad 路徑」、接續時「舊路徑存在就複製全部暫存檔、C、Q 編號接續」維持不變。
6. **審查豁免**（只限 scratchpad 遺失）：
   - 需求 1–4 已能合理處理的 scratchpad 遺失情況，審查不得要求逐一增加特定案例，也不因此阻擋合併。reviewer 不把這類情況列成發現，寫在報告的「已接受的風險」。
   - 只有需求 1–4 無法處理，而且會造成下列實際風險時才列為發現並阻擋：已核准的決定被推翻、正式文件被憑記憶重寫、開發者沒被告知決定或成果遺失。
   - 這項豁免不擴大到 scratchpad 遺失以外的流程。
   - 規則只在 `/feature`「暫停與接續」定義；`specification-reviewer` 與 `acceptance-reviewer` 各加一句引用它；`docs/reviews/README.md`「分類」加一句例外（Specification Defect、Missing AC 一律阻擋的規則，不適用於被豁免的情況）並指向 `/feature`。
   - `docs/reviews/README.md`：`acceptance-reviewer` 的檢查表加「已接受的風險」（列被豁免的情況，沒有寫「無」）；實作審查紀錄有被豁免或決定不補的項目時，加「## 已接受的風險」一節。
7. **單一來源**：暫存產物清單只在需求 2 定義。`/feature` 第 1 節開頭的暫存檔列表（`.claude/skills/feature/SKILL.md:20`）、`:301` 的括號列舉、`docs/README.md:23` 暫存那一列的檔名列舉，都改成指向 `/feature` 第 4 節「暫停與接續」的清單。`docs/README.md`「生命週期」的暫停與接續（`:29`）只留一句說明並指向同一節，不再抄一份規則；同一段的「取消」（`:28`）也改成一句說明並指向 `/feature` 第 4 節「取消」。
8. 新增 ADR 0010，記錄以暫存產物為單位的恢復規則與審查豁免，背景寫明補充 ADR 0009（0009 只寫了舊路徑存在時的接續）；ADR 清單加一列。ADR 0009 不改。

## 不做

- 不保留依時間點列舉的特定情況。
- 不改 scratchpad 的位置或保存方式（例如改成 repo 內的資料夾）。
- 審查豁免不擴大到 scratchpad 遺失以外的流程。
- 不改既有規格、審查紀錄、ADR 的內文（例如 `docs/specs/issue-69-context-in-repo.md` 的 AC20 是當時的紀錄），ADR 0009 的狀態行也不改。
- 不改程式碼。

## 假設

1. 暫存產物清單放在 `/feature` 第 4 節「暫停與接續」：恢復方式和接續規則放在一起最好對照；其他地方只指向它。
2. 「已核准的內容要重做時重新核准」涵蓋規格與 ADR：兩者都和規格一起核准。

## 不適用的情境
