# 文件寫作規則

- 狀態：已核准
- 等級：一般（改了定義流程的文件裡的規則；沒有碰到資料、登入權限、安全性）
- PR：#NN

## 簡短說明

讓不熟這套流程的人也看得懂 repo 裡的 md 文件：寫之前有規則可照，審查時照同一套規則檢查，看不懂的流程用語改成白話或寫進術語表。

## 背景

- 流程文件用了很多自己定義的詞，例如「落點」「交回」「豁免」，第一次讀的人看不懂。流程文件指 skill（主 session 照著做的流程說明，在 `.claude/skills/`）、agent（主 session 派去做單一工作的另一個 Claude，在 `.claude/agents/`）與 `docs/` 底下的 README。
- 審查問題的類型與嚴重程度用英文名稱（例如 Factual Error、Minor），不查定義看不懂。
- 現在沒有寫作規則：哪些詞要解釋、一條要寫多少事，都沒有規定。
- `docs/README.md`「術語表」現在只收產品用詞，寫明「不收開發流程的用詞」。
- 主 session 每次開始都會載入 `CLAUDE.md`，所以寫在 `CLAUDE.md` 的規則，寫文件前就看得到。

## 需求

**寫作規則**

1. `CLAUDE.md` 新增「寫作規則」一節，寫下面 4 條規則：
   - 用白話。一條需求或一個步驟只寫一件事，用一句話。
   - 不自創詞。必須用的專有名詞，第一次出現時在括號裡寫白話意思；已經列在 `docs/glossary.md` 或 `docs/README.md`「流程用語」的詞不用。
   - 開發者沒有決定過的規則，不寫進文件；不確定的列成「請你決定」。
   - 讀者看不懂的地方是文件的問題，由寫的人改，不是讀者去學那個詞。
2. 「寫作規則」一節的最後寫：「流程用語的意思見 `docs/README.md`「術語表」」。
3. 3 個 agent 和 `docs/specs/README.md` 各加一行：「照 `CLAUDE.md`「寫作規則」；流程用語的意思見 `docs/README.md`「術語表」」。
4. skill 與 agent 不重抄寫作規則的內容。

**術語表與白話**

5. `docs/README.md`「術語表」新增「流程用語」小節，收「實作計畫」第 1 步的詞與白話定義。
6. 「術語表」刪掉「不收開發流程的用詞」那句，連同括號裡的說明。
7. 「術語表」寫明流程用語收在「流程用語」小節。
8. 「實作計畫」第 2 步的 8 個詞，在現行流程文件（範圍見假設 1）裡改成白話。

**問題類型與嚴重程度改名**

9. 審查問題的 6 種類型，在現行流程文件裡改成「實作計畫」第 3 步的名稱。
10. 現行流程文件裡審查報告的節名改成中文：Summary 改「摘要」、Problem Details 改「問題說明」、Technical Evidence 改「技術證據」。指令、檔名、GitHub 的欄位與狀態名稱保留英文。
11. 4 種嚴重程度，在現行流程文件裡改成「實作計畫」第 3 步的名稱。
12. 「流程用語」小節列出舊英文名稱對應的新名稱。

**規格模板**

13. 規格模板（`docs/specs/README.md`「格式」）的最前面加「簡短說明」一節，寫這份規格要解決什麼。
14. 規格模板規定：簡短說明寫不清楚、範圍可能太大時，在「請你決定」提出要不要拆成多份規格的建議，由開發者決定。
15. 規格模板的最後加「請你決定」一節，列出要開發者決定的事。
16. 規格模板規定：「請你決定」在核准前全部回答完，答案寫進需求、不做或驗收條件，這一節改寫「無」。
17. 規格模板規定：每條需求只講一件事。
18. 規格模板規定：每條驗收條件只講一件事。

**審查時檢查寫法**

19. `specification-reviewer` 新增第 6 項檢查，找出寫法讓人看不懂的地方：沒有定義的專有名詞、一條需求或驗收條件講了不只一件事、簡短說明寫不清楚要解決什麼也沒有在「請你決定」提出拆不拆的建議。
20. `acceptance-reviewer` 新增一項檢查：這個 PR 改到的 md 檔，有沒有違反 `CLAUDE.md`「寫作規則」第 1、2 條。
21. 寫法問題不另設類型：reviewer 看改寫後會影響什麼，歸進現有的類型。例如改寫會改到驗收條件的意思，就是規格的問題；只換說法、意思不變，就是「沒有錯，但可以更好」。

**找到後怎麼處理**

22. 會影響行為或驗收條件的寫法問題，照它歸進的類型，用現有的處理方式。
23. 只換說法、意思不變的寫法問題不阻擋，由寫那份文件的人改掉：規格審查時主 session 直接改草稿；實作審查時在同一個 PR 改，不開 issue。

## 不做

- 不做自動檢查工具（例如 Vale）。
- 不改永久保存的文件：`docs/specs/` 的規格、`docs/reviews/` 的紀錄、`docs/decisions/` 的 ADR（架構決策紀錄），以及 `docs/decisions/README.md`「清單」表抄自 ADR 的標題與狀態。這些文件裡的英文類型名稱也保持原樣。
- 不改 `docs/experiments/` 的實驗紀錄與說明。
- 不改審查次數與重新審查的規則。
- 不限制規格的長度。
- 「不做」一節維持現狀：一般等級沒有內容時可以省略。
- 6 個 skill 不加指向「寫作規則」的那一行：主 session 本來就載入 `CLAUDE.md`。
- `CLAUDE.md`「做這類任務前先讀」表不改。
- 實作審查紀錄和 PR 描述不檢查寫法：實作審查紀錄在實作審查結束後才寫，PR 描述不是 repo 裡的檔案。
- scratchpad（這次對話專用的暫存資料夾）的檔案不檢查寫法：它們不會 commit。
- 不改 PR #94（不改行為的清理可以在目前的 PR 做）和它的規格。#94 已轉成 Draft，等這份合併後照新規則重寫。
- 已核准的規格裡的寫法問題，照現有「核准後修改規格」的規則處理，不適用需求 23。
- 不刪除現有說明「讀者是誰」的句子，例如「給之後沒看過這次對話的人讀」。

## 實作計畫

**第 1 步：「流程用語」小節**（`docs/README.md`「術語表」）：

| 詞 | 白話定義 |
|---|---|
| 等級：一般／高風險／文字修正 | 依變更碰到什麼分成的三種處理深度，各自對應規格要寫多細、要審查幾次 |
| 阻擋／不阻擋 | 這個問題要先處理完（或由開發者決定另開 issue）才能往下走：規格審查是核准前，實作審查是交給開發者決定合併前／不用先處理 |
| 發現 | 審查找到的一個問題或建議 |
| 已確認／待問 | 開發者已經回答的決定／還沒問的問題 |
| 交付清單 | 交給 `feature-implementer` 的檔案與要做的事 |
| 主 session | 和開發者對話、指派其他 agent 的那個 Claude |
| scratchpad | 這次對話專用的暫存資料夾，不會進 repo |
| 已接受的風險 | 確定不處理、之後審查也不再提出的風險 |
| 決策樹 | 把問題依「哪一題要先回答」排出的順序 |
| 不變條件 | 只看畫面驗不出來，但一定要守住的系統狀態 |
| advisory | GitHub 上不公開的漏洞報告 |

另外附第 3 步的舊名稱對新名稱對照表，給讀舊紀錄的人查。

**第 2 步：8 個詞改成白話**（現行流程文件，依句子調整語法，不改規則的意思）：

| 詞 | 改成 |
|---|---|
| 去處 | 處理方式 |
| 交回 | 請 `feature-implementer` 修正 |
| 針對性審查 | 只審改過的部分的審查 |
| 落點 | 寫在哪裡 |
| 豁免、審查豁免 | scratchpad 遺失時不算問題的情況；`resume.md`「審查豁免」一節改名成「scratchpad 遺失時的審查規則」 |
| 暫存產物 | 暫存檔（`resume.md`「暫存產物表」一節改名成「暫存檔表」） |
| 驗收表 | 驗收條件、測試與結果的對照表 |
| 中途升級 | 做到一半改成較高的等級（`clarify-requirements`「中途升級」一節改成這個名稱） |

**第 3 步：問題類型與嚴重程度改名**（現行流程文件）：

| 舊名稱 | 新名稱 |
|---|---|
| Factual Error | 規格對現有系統的描述和程式不符 |
| Specification Defect | 規格內容互相矛盾或沒有依據 |
| Missing Acceptance Criteria（Missing AC） | 規格沒寫某個情境該怎麼做 |
| Implementation Defect | 程式沒照規格做 |
| Test Gap | 測試抓不到錯的程式 |
| Improvement Suggestion | 沒有錯，但可以更好 |
| Critical | 會壞資料、有安全問題，或主要功能不能用 |
| Major | 一般操作就會遇到的錯 |
| Minor | 影響小的問題 |
| Info | 不影響功能，只供參考 |

「嚴重程度」表下方提到和 `docs/experiments/feature-grill/README.md` 定義相同的那句，改成指向「流程用語」的對照表，不直接寫舊名稱。

**第 4 步：規格模板**：`docs/specs/README.md` 照需求 13–18 改「格式」「驗收條件怎麼寫」「各等級的規格」。「每條只講一件事」旁邊寫「出現『而且』『以及』就考慮拆開」。

**第 5 步：審查與處理**：

- `specification-reviewer`：照需求 19、21 加第 6 項檢查。
- `acceptance-reviewer`：照需求 20、21 加一項檢查。
- `write-spec`「處理發現」：只換說法的寫法問題由主 session 直接改草稿，交給開發者時列出。
- `implement-and-review`「發現處理表」：加上只換說法的寫法問題在同一個 PR 改、不開 issue，並更新「處理方式只有四種」的數量。
- `feature-implementer`：「不對應驗收條件的要求不要做」加上例外：只換說法的寫法問題照做。
- `acceptance-reviewer`：「不阻擋的發現會開 issue」加上例外：只換說法的寫法問題不開 issue；這類問題的標題開頭寫「寫法：」，讓主 session 分得出來。
