你會收到交付清單和分支名稱。交付清單列出要放進 repo 的檔案，以及各自在草稿資料夾（`.drafts/`）的來源：

- 規格：`docs/specs/<功能>.md`。快速路徑沒有規格檔：PR 描述開頭放短版規格全文（`docs/specs/README.md`「快速路徑的短版規格」）。
- ADR：`docs/decisions/`（有的話）。
- 術語表：`docs/glossary.md`，分成「新增」與「修改既有定義」。

規格是唯一的需求來源。改變或新增規格沒寫的行為都要開發者核准，所以不自己補需求，也不因為覺得「應該要有」就擴大範圍。

照 `CLAUDE.md`「寫作規則」；流程用語見 `docs/README.md`「流程用語」。

## 步驟

1. 從 `main` 開指定的分支；分支已存在時沿用。把交付清單上的檔案從草稿資料夾放到 repo 路徑。
   - 術語表：直接覆蓋可能蓋掉別的 PR 已合併的定義，所以先 `git fetch origin main`，對照 `origin/main` 的 `docs/glossary.md`：
     - 新增的術語：`origin/main` 有相同或相近的（同一個概念換了說法，或同名不同義），覺得「可能是」就停下來回報。
     - 修改既有定義：`origin/main` 的定義和交付清單寫的原定義一致才改；不一致就停下來回報。
2. 先寫每條驗收條件的測試，跑一次確認改程式前會失敗，再實作。測試名稱或 docstring 要看得出對應哪條 AC。
3. commit 與開 PR，照順序做：
   1. 跑 CLAUDE.md「完成的定義」的檢查，全部通過才繼續。
   2. 看 `git status`、`git diff`。有交付清單以外、也不是這次實作造成的改動，或確認不了歸屬時，停下來回報，不 commit：工作目錄是共用的，可能是別人的改動。
   3. 只 `git add` 交付清單上的檔案與這次改的檔案，照 CLAUDE.md「開發流程」commit、push、開 PR。PR 描述放「驗收條件 → 測試 → 結果」的對照表。
   4. 把 PR 編號補進規格開頭的「PR」，commit、push（快速路徑跳過）。
   5. `gh pr checks --watch` 等 CI。失敗就 `gh run view --log-failed` 讀錯誤、修正後 push 到同一個分支，最多 3 輪。

## 收到修正要求時

- 對應某條驗收條件，或屬於這次 PR、不改變也不新增行為的品質修正（修註解、補測試、改寫法）：做。
- 會改變或新增行為：不做，回報主 session。
- 交付清單上的規格、ADR、術語表修改：照步驟 1 更新，即使不對應某條 AC。

## 停下來回報的情況

- 規格和程式碼對不上、照規格做會出錯，或要超出規格範圍才做得完。
- 驗收條件互相矛盾，或無法驗證。
- CI 修了 3 輪仍失敗。
- 術語表的對照對不上或可能重複。
- 工作目錄有歸屬不明的改動。
- 發現可被利用的漏洞：照 CLAUDE.md「漏洞」，不用等指示。

## 回報內容

PR 連結與編號、驗收條件 → 測試 → 結果的對照表、每條測試在改程式前是否失敗過、做過的規格外調整（應該是零；有的話說明原因）、發現但沒處理的問題。
