# 寫規格

> 文字修正不寫規格，見 `feature`「文字修正的流程」。

規格草稿照 `docs/specs/README.md` 的格式寫，放在草稿資料夾（`.drafts/`）的 `<功能>-spec.md`。修 bug 的規格照同一份文件的「修 bug 時」寫。ADR 草稿和規格一起核准，核准後照 `implement-and-review`「交付清單」交給 `feature-implementer` 存進 `docs/decisions/`。

## 規格內容

- **需求／不做**：要做什麼、明確排除什麼。
- **假設**：逐條列出程式碼看不出來、由你判斷的事，以及開發者明確交給你決定的事。
  - 開發者決定的事寫進需求、不做或驗收條件，不寫成假設。
  - 只有無法合理假設、而且會影響整體方向的問題，才先問開發者。
  - 碰到需要開發者決定的業務規則，照 `clarify-requirements`「新的決定一律回到決策樹」問開發者，不寫成假設。
- **驗收條件**：編號 AC1、AC2…，照 `docs/specs/README.md`「驗收條件怎麼寫」。
- **計畫與測試對應**：要改的檔案、步驟、每條驗收條件對應的測試或驗證步驟，與預期結果。

## 已確認的決定寫進規格

`<功能>-grill.md` 不 commit，所以交給開發者核准前，逐項對照「已確認」的每一項：都在規格、ADR 草稿或 `<功能>-glossary.md` 裡找得到，驗收條件和它不矛盾；開發者決定、會影響實作的項目寫在需求、不做或 AC，不寫成「假設」。要寫在術語表的項目，在 `<功能>-glossary.md` 找得到就算。屬於重大架構決策（定義見 `feature`「重大架構決策」）的，寫成 ADR 草稿 `<功能>-adr-<名稱>.md`，和規格一起核准。

## 規格審查

文字修正以外的等級，草稿寫好、交給開發者核准前，把草稿 `<功能>-spec.md` 的路徑、等級、`<功能>-grill.md` 的路徑，以及 ADR 草稿、`<功能>-glossary.md` 的路徑（有的話）交給 `specification-reviewer`。

### 處理發現

核准前，規格草稿由主 session 修改。每項發現照下面順序判斷，符合一條就停：

1. 標題開頭是「漏洞：」：照 `implement-and-review`「漏洞的處理」。
2. 涉及重大架構取捨，而且沒有已核准的決定可以依循：整理選項、各自的影響與建議，問開發者；需要時，決定後寫 ADR 草稿。不涉及重大決策的架構改善，照下面的步驟。
3. `question`，或修正會改變規格寫到的行為，或新增規格沒寫的行為：照 `implement-and-review`「規格問題的處理」第 2 步問開發者。
4. 阻擋的 `issue`、`suggestion`，修正不改變行為：主 session 依依據直接改草稿。
5. `nitpick`：主 session 直接改草稿，不開 issue；交給開發者時列出改了哪些。
6. 不阻擋的 `issue`、`suggestion`：列在交給開發者的訊息裡，由開發者決定採不採用；規格還沒核准，不開 issue。

`question` 經開發者回答後，照回答改草稿；回答帶出新的重大架構取捨時，照第 2 步。

處理發現時開發者做的新決定，照 `clarify-requirements`「新的決定一律回到決策樹」。

### 審查次數與審查後的修改

- **次數**：上限見 `feature`「判斷等級」的表。第 1 次完整審查；為了處理發現而新增或改寫驗收條件、假設或設計時，第 2 次只審改過的部分與連帶影響，不重審整份規格。送審時附上：修改內容與原因、受影響的 AC、假設、實作計畫與相關決策，以及第 1 次報告與上一版規格（`<功能>-spec-v<N>.md`）在草稿資料夾的路徑。第 2 次還有阻擋的項目，就整理好問開發者，不繼續自動審查。
- **只改措辭、意思不變**：不需要重新審查；改完確認沒有改變原本的規格意思。
- **開發者要求修改**：改了驗收條件、假設或設計，就再做一次只審改過的部分的審查（不計入上面的次數上限）；修改已影響整體設計方向、原本的審查基準失效時，評估是否需要完整審查。
- 任何修改都先確認影響範圍：不能只看修改的文字或單一 AC，要一併看受影響的其他 AC、假設、實作計畫與測試對應。

### 審查紀錄

每一輪的報告原文存成草稿資料夾的 `<功能>-spec-review-r<N>.md`；處理完這一輪的發現，寫成留言檔 `<功能>-spec-review-r<N>-comment.md`（寫法見 `implement-and-review`「審查留言」）。規格審查在 PR 開之前做，留言在 PR 開好後（`feature-implementer` 回報 PR 已建立）、交給 `acceptance-reviewer` 前，照 `implement-and-review`「審查留言」依輪次貼出。

### 交給開發者核准

訊息附上草稿路徑與審查摘要：改了什麼、還需要開發者決定什麼、有哪些不採用的建議；以及已確認決定的對照結果（每一項寫在規格、ADR 草稿或術語表的哪裡）。核准的定義見 `feature`「硬規則」。
