# 審查

規格審查與實作審查共用這份文件的標籤、報告格式與「處理」。每一輪的結果由主 session 貼成一則公開的 PR 留言（審查 agent 不能寫檔），貼法見 `implement-and-review`「審查留言」。

| 審查 | agent | 時機 |
|---|---|---|
| 規格審查 | `specification-reviewer` | 規格核准前，需要時才做（`write-spec`「什麼時候做規格審查」）；留言在 PR 開好後貼出 |
| 實作審查 | `acceptance-reviewer` | 實作完成後 |

文字修正不做審查。

## 標籤與阻擋

每項發現標一個標籤（[Conventional Comments](https://conventionalcomments.org/)），另外標阻擋或不阻擋。標籤描述性質，阻擋看實際影響，兩件事分開判斷。

| 標籤 | 意思 |
|---|---|
| `issue` | 要修的問題，包括會讓需求或驗收條件被讀錯的寫法 |
| `suggestion` | 可以更好的改法，包括安全改善、讓文字更清楚 |
| `nitpick` | 只換說法、意思不變的小地方，一律不阻擋 |
| `question` | 要開發者決定或回答的事，例如未定義的產品行為、權限、資料處理 |

**阻擋**：照現在的規格或程式，這次 PR 不應該被接受（規格審查是規格不應該被核准）。考量正確性、安全性、可靠性、是否符合驗收條件，以及之後讀、改的難易。個人偏好、純風格、非必要的改善不阻擋。

實作審查的 `issue`、`suggestion`，在「建議」另外寫：

- 修正要不要改規格；涉及重大架構決策（`feature`「重大架構決策」）時寫明。
- 不阻擋的，是「屬於這次 PR」（問題在 `git diff origin/main...HEAD` 改到的檔案，或和某條驗收條件有關）還是「和這次 PR 無關」。

沒有實際驗證的推論，在「依據」寫明是推論與推斷的步驟。

### 漏洞

漏洞是實際可被利用的程式漏洞；安全改善建議不是漏洞，標 `suggestion`。

- 漏洞的標題開頭寫「漏洞：」，例如 `### #1 \`issue\`（阻擋）：漏洞：…`。
- 處理照 `implement-and-review`「漏洞的處理」。下面「不列成發現的情況」不適用於漏洞。

### 不列成發現的情況

下面的情況寫在報告的「已接受的風險」，不列成發現：

- **暫存檔遺失**：照 `.claude/skills/feature/references/resume.md` 處理得了的遺失。處理不了，而且會推翻已核准的決定、讓正式文件被憑記憶重寫，或開發者沒被告知時，才列成發現。遺失的時間點列舉不完，不要求替每種情況加規則。
- **規格「不做」寫明不處理的情況**。只有下面三種列成發現：實作做了「不做」排除的改動；「不做」依據的事實不成立（例如實作新增了會產生這個情況的依賴）；規格審查時認為某個情況不該列在「不做」。

## 報告格式

讀者是沒看過這次對話、也不熟這段程式碼的人：先用使用者的操作與結果說明問題，技術細節放後面。依據寫 `檔案:行號`，引用規格寫 AC 或假設的編號，不寫「上面提到的」這類只有當下看得懂的說法。

````markdown
## 摘要

- 主要風險：一到三句，用使用者的操作與結果描述
- 建議優先處理：#1 → #3 → …，各附一句理由

| # | 標題 | 標籤 | 阻擋 |
|---|---|---|---|

沒有發現時寫「沒有發現」，只留這一節和「技術證據」。

## 問題說明

順序和摘要的表相同；`nitpick` 可以只寫「問題」與「建議」。

### #1 `<標籤>`（阻擋／不阻擋）：<一句話標題>

1. **問題**：在什麼操作或條件下，發生了什麼。
2. **影響**：使用者或資料會怎樣；影響哪些驗收條件、檔案或功能。
3. **依據**：哪裡造成的（`檔案:行號`）；互相矛盾的寫出是哪幾條。
4. **建議**：怎麼處理與理由。規格的問題寫出建議的驗收條件；`question` 列出選項與各自的影響，最後寫建議。
````

## 處理

主 session 貼留言前，在報告最後加這一節：

```markdown
## 處理

| # | 處理方式 | 決定者 | 結果 |
|---|---|---|---|

### 開發者決定

| # | 選項 | 開發者的決定 | 理由 |
|---|---|---|---|
```

- 「#」沿用報告的編號；「處理方式」照 `implement-and-review`「發現處理」。
- 「決定者」：開發者、規則（例如阻擋又不用改規格的，直接請 `feature-implementer` 修），或主 session。核准後改規格一律由開發者確認。
- 「結果」寫其中一種：修正的 commit；issue 或 advisory 編號；「不改：<原因>」；「不開 issue：<原因>」；「等開發者決定」；規格審查寫「規格已修改」或「開發者決定不採用」。
- 「開發者決定」表只列開發者決定的項目；沒有時寫「無」。
