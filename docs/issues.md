# Issue 寫法

所有 issue 都照這份寫，不論是審查後開的、開發途中開的，還是在對話裡直接開的。issue 是之後 `/issue` 寫規格的需求來源，讀者是之後沒看過這次對話的開發者與 agent。

先從受影響的人怎麼遇到這個問題寫起，再寫工程資訊。兩層都要有：只有使用者情境，寫不出正確的驗收條件；只有程式狀態，看不出要不要修、修好的樣子是什麼。不要為了好讀省略技術條件，也不要寫成「身為…我想要…」的固定句型。

## 格式

```markdown
<一句話：誰在做什麼的時候，發生了什麼>

## 情境
- **誰／在做什麼**：
- **實際**：
- **影響**：
- **預期**：

## 技術背景
目前系統的行為、原因（`檔案:行號`）、涉及的 API、資料庫欄位、第三方服務。

## 必要條件
和這個需求相關的資料一致性、併發、權限、安全性、外部系統狀態。不相關的不寫。

## 建議的驗收條件
| # | 條件 | 類型 |
|---|---|---|
| AC1 | 在 X 情況下，系統要 Y | 使用者行為 |
| AC2 | … | 不變條件 |

## 驗證方式
自動化測試、CI run、手動步驟。

## 待調查／待決定
已知限制、尚缺的證據、要開發者決定的事。

來源：PR #NN 實作審查（`docs/reviews/implementation/<名稱>.md` #M）
```

- 欄位沒有內容就整段拿掉，不要寫「無」湊格式。唯一的例外是「影響」：沒有使用者影響時寫「使用者：無影響」，再寫對誰有影響。
- 審查開的 issue，「技術背景」與「建議的驗收條件」以審查報告為準，不刪原有的依據；「情境」由開 issue 的人從報告的影響範圍改寫。
- 「建議的驗收條件」只是建議，`/issue` 寫進規格、開發者核准後才算數。寫法照 [docs/specs/README.md](specs/README.md)「驗收條件怎麼寫」。
- 可被利用的漏洞不開 issue：repo 是公開的，照 `/feature`「漏洞的處理」。

## 依類型決定「誰」

| 類型 | 誰 | 情境的重點 | 驗證方式 |
|---|---|---|---|
| 產品的 bug、功能 | 使用者 | 在哪個畫面做什麼操作、看到什麼、預期看到什麼；功能寫想完成的事與現在卡在哪 | 自動化測試 |
| 部署、CI、基礎設施 | 部署維護者（合併、部署、看監控的人） | 做了什麼操作、系統怎麼反應；對上線與使用者的間接影響，確認不了就寫「待確認」 | CI run、部署紀錄、手動檢查 |
| 開發工具（skill、agent、文件） | 用 skill 或 agent 的開發者 | 流程走到哪一步、產出了什麼錯的結果、造成什麼成本（多跑幾輪、誤判、要人工分辨） | 重現情境的手動步驟、`grep` 文件 |
