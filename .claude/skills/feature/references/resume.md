# 暫停、接續與 scratchpad 遺失

> 什麼時候讀：暫停或接續一次開發、scratchpad 遺失時。`specification-reviewer` 與 `acceptance-reviewer` 只讀「審查豁免」。

## 審查豁免

只限 scratchpad 遺失。

- 下面的步驟、暫存產物表與部分改動的完成狀態已能合理處理的 scratchpad 遺失情況，審查不得要求逐一增加特定案例，也不因此阻擋合併。reviewer 不把這類情況列成發現，寫在報告的「已接受的風險」。
- 只有下面的規則無法處理，而且會造成下列實際風險時才列為發現並阻擋：已核准的決定被推翻、正式文件被憑記憶重寫、開發者沒被告知決定或成果遺失。
- 這項豁免不擴大到 scratchpad 遺失以外的流程。

## 暫停與接續

暫停時 scratchpad 保留，告訴開發者 scratchpad 的路徑。接續時請開發者提供舊路徑，把舊 scratchpad 裡這次開發的全部暫存檔（`<功能>-` 開頭，種類見下面的暫存產物表）複製到新的 scratchpad。

舊 scratchpad 不存在，或缺了部分檔案時，以遺失了哪個暫存產物為單位處理，不依遺失的時間點（`docs/decisions/0010-scratchpad-loss-recovery.md`）。依序：

1. 對照下面的暫存產物表，找出遺失的暫存產物。
2. 先 `git fetch`，確認 repo、本機分支、`origin` 上這次的分支或工作目錄裡是否已有它的正式版本。有就以正式版本為準，照表上的恢復方式處理，不憑記憶重新產生。
3. 確認是否已有部分成果（例如分支上已改了一部分）。有就照下面「部分改動的完成狀態」逐項列出，避免重複執行或遺漏。
4. 用了正式版本或部分成果時，告訴開發者依據的來源（分支、commit、工作目錄有沒有未 commit 的改動），請開發者確認之後有沒有已確認、但還沒交付或寫進紀錄的修改或項目。有就逐項列出，照「部分改動的完成狀態」標狀態；沒有依據（正式版本與部分成果都找不到）的項目，重新核准後才執行。項目清單本身遺失時（例如文字修正的改動清單）也照這一步，由開發者補上項目。
5. 沒有可恢復的成果時，告訴開發者缺了哪個產物，依產生它的步驟，用 `clarify-requirements`「需求問答」的格式請開發者照表上該列的選項選擇（表上沒有寫的，選重做或不補）。已核准的內容要重做時，重做後要重新核准；不把已核准的內容當成未核准，也不憑記憶重寫正式文件。
6. 不補時，在 PR 描述記錄遺失的項目、影響與不補的決定；有實作審查紀錄的，同時寫在紀錄的「已接受的風險」（`docs/reviews/README.md`「紀錄檔格式」）。紀錄的「尚未處理」若也列出，註明「已決定不補」，不當成待辦。規格審查紀錄不補時，交給 `acceptance-reviewer` 照 `implement-and-review`「交給 acceptance-reviewer 審查」的方式處理。

## 暫存產物表

這張表是暫存檔唯一的清單。新增暫存產物時，在表上同時寫出檔名、產生它的步驟與正式版本與恢復方式，就能套用上面的步驟。

| 暫存產物 | 檔名 | 產生它的步驟 | 正式版本與恢復方式 |
|---|---|---|---|
| 已確認的決定與待問 | `<功能>-grill.md` | 需求問答；文字修正：寫改動清單時的確認；核准後的決定也會寫進來 | 核准後，決定已寫進規格（內容與落點），以規格為準，不重建。核准前沒有正式版本，從產生它的步驟重做 |
| 術語 | `<功能>-glossary.md` | 需求問答、寫規格草稿、規格審查；核准後的實作回報、實作審查 | 已交付的術語以正式版本（第 2 步找到的位置）的 `docs/glossary.md` 為準，不複製；之後要修改時，只把要修改的術語條目照 `docs/README.md`「術語表」的格式複製到 `<功能>-glossary.md`（不含檔頭）再改。核准前沒有正式版本，重新確認 |
| 規格草稿（文字修正是改動清單） | `<功能>-spec.md` | 寫規格草稿／寫改動清單；核准後修改規格 | 規格以正式版本（第 2 步找到的位置）的 `docs/specs/<功能>.md` 為準，複製成 `<功能>-spec.md`（之後照交付清單交付要用）；找不到時，已核准的規格請開發者選擇重寫再核准或取消。文字修正的改動清單沒有正式版本，照第 3、4 步 |
| ADR 草稿 | `<功能>-adr-<名稱>.md` | 寫規格草稿；核准後的重大架構決策 | 以正式版本（第 2 步找到的位置）的 `docs/decisions/` 為準，不複製；之後要修改時，從 PR 分支複製到 `<功能>-adr-<名稱>.md` 再改。沒有時重寫，和規格一起重新核准 |
| 規格審查紀錄草稿 | `<功能>-spec-review.md` | 規格審查 | 以正式版本（第 2 步找到的位置）的 `docs/reviews/specification/` 為準，不複製；沒有時請開發者選擇重跑規格審查（審目前的規格）或不補（不補時照上面第 6 步交給 `acceptance-reviewer`） |
| 審查報告原文 | 各輪報告 | 該次審查 | 已整理進審查紀錄的部分以紀錄為準；沒有整理的請開發者選擇重跑該次審查或不補 |

重跑審查的發現：核准前照 `write-spec`「處理發現」，核准後照 `implement-and-review`「規格問題的處理」與「發現處理表」；重跑同一次不另計次數。

## 部分改動的完成狀態

逐項標出已完成、未完成、部分完成、待確認。無法確認某項是否完成時標成「待確認」，不可推定已完成。未完成、部分完成與待確認的項目，請開發者確認怎麼處理。
