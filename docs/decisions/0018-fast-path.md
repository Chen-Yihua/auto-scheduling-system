# 0018. 需求清楚的改動走快速路徑

- 狀態：已採用（部分被 [0019](0019-simplify-spec-review-and-ac-derivation.md) 取代）
- 日期：2026-11-20

## 背景

[0012](0012-simplify-process-levels.md) 把輕量併進一般之後，bug 與小的行為修改都要寫完整規格、做最多 2 次規格審查、實作審查做到沒有阻擋。issue 已經寫好重現步驟與預期的小 bug 也一樣，開發者要等好幾輪 commit 與 CI，也要做好幾次決定（issue #157，來自 #152 第二部分第 5 點）。

[0006](0006-bugs-use-full-spec.md) 讓 bug 用完整規格並做規格審查，[0007](0007-process-depth-by-risk.md) 不採用「輕量不做規格審查」，依據都是 #28、#46：兩個一開始看起來都是小修正，問題出在驗收條件的矛盾與缺漏。[0002](0002-specs-in-repo.md) 不採用「只寫在 PR 描述」，理由是 PR 描述沒有版本紀錄。

一般做法：`obra/superpowers` 的 [`brainstorming`](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)：需求都在請求裡的清楚小事直接做、做完說明；小改動用一兩行的短設計，核准後才動手。

## 決定

1. 一般等級裡加一條快速路徑。先照等級判斷是一般，再看是否同時符合：需求（issue 內容或 `/feature` 的參數）已寫清楚現在的結果與預期的結果、沒有要開發者決定的事、不碰高風險範圍。改動大小不是條件。
2. 快速路徑只簡化規格階段：規格用短版（等級、背景、驗收條件、修法、測試對應），放在 PR 描述，不存 `docs/specs/`；需求理解與短版規格一次核准；不做規格審查。
3. 實作、實作審查、核准後改規格的處理沿用一般流程。核准後要改短版規格時由開發者決定：在這個 PR 補上就改走一般的完整流程（完整規格、規格審查、核准、存進 `docs/specs/`）；另開 issue 就留在快速路徑。核准前發現不符合條件時也改走完整流程。
4. 開發者核准、測試要求（修 bug 時 AC1 的測試改程式前必須失敗）、由 `feature-implementer` 實作照舊。`acceptance-reviewer` 另外查證背景裡對現有系統的描述（現在的結果、重現步驟、原因）。

## 放棄的做法

- **恢復輕量等級**：等級依碰到的範圍判斷（0007），快速路徑看的是需求清不清楚，不是範圍；另設等級又會帶回 0012 拿掉的專屬例外。
- **快速路徑也做 1 次規格審查**：短版規格的驗收條件很少，規格審查的主要成本是多一輪等待與決定，省不掉就沒有縮短流程。
- **核准後要改規格時，留在快速路徑、只在 PR 描述記修改**：規格改了之後沒有人從規格的角度再看過，正是 #46 那種情況。
- **實作審查有阻擋就一律改走完整流程**：只是程式寫錯、規格沒問題時，補寫完整規格沒有幫助。
- **快速路徑另外寫一套實作與審查規則**：一般流程已經涵蓋，兩套規則會各自演變。
- **把文字修正併進快速路徑**：文字修正不改行為，不需要 `feature-implementer` 與實作審查（0007），合併會讓文字修正變重。

## 影響

- 部分推翻 0006：符合條件的 bug 用短版規格、不做規格審查。0006 的其他決定照舊（AC1 對應重現步驟、改程式前必須失敗的測試）。
- 部分推翻 0007「放棄的做法」的「輕量不做規格審查」：#28、#46 那種問題改由條件 1、2 減少，發生時由實作審查發現、改走完整流程。
- 部分推翻 0012 決定 2：一般等級不再一律用完整規格與規格審查。
- 部分推翻 0002：快速路徑的規格只在 PR 描述。0002 擔心的版本紀錄，由 GitHub 保留的 PR 描述編輯歷史補上；短版規格核准後不修改（要改就改走完整流程），所以不放修改紀錄。
- 代價：規格本身的問題要到實作審查才會被發現，修正成本比在規格階段高。
- 快速路徑的規格不在 `docs/specs/`，之後查某個變更的需求要看 PR 描述。
