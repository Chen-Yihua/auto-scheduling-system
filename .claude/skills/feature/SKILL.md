# 功能開發流程

需求：$ARGUMENTS

你是提需求、負責驗收的一方，不自己寫程式（等級為「文字修正」除外）。規格核准前交給 `specification-reviewer` 審查，實作交給 `feature-implementer`，實作後交給 `acceptance-reviewer` 審查；它們都看不到這段對話，所以規格要寫到不看這段對話也能照著做。分工的原因見 `docs/decisions/0001-separate-feature-roles.md`、`docs/decisions/0005-specification-review.md`。

## 流程

進入每個步驟前，先用 Skill 工具載入該步驟的 skill，照它的指示做。

| 步驟 | 做什麼 | 載入 |
|---|---|---|
| 1. 判斷等級 | 自己讀程式碼，依本檔「判斷等級」判斷 | 本檔 |
| 2. 需求確認 | 簡述需求理解、需求問答（只問會改變需求、行為或範圍的事）、工程方案探索 | clarify-requirements |
| 3. 規格 | 寫規格草稿、規格審查、交給開發者核准（文字修正不寫規格，見「文字修正的流程」） | `write-spec` |
| 4. 實作與審查 | 開發者核准後：交給 `feature-implementer` 實作，再交給 `acceptance-reviewer` 審查，處理發現 | `implement-and-review` |
| 5. 回報 | 見本檔「回報」 | 本檔 |

暫停、接續、scratchpad 遺失時，讀 `references/resume.md`。


## 硬規則

任何階段、任何等級都適用。

1. **不用 plan mode**，也不用 ExitPlanMode 請開發者核准（`docs/decisions/0008-grilling-without-plan-mode.md`）。開發者在 plan mode 中叫出這個流程時，先請開發者退出 plan mode：plan mode 中不能寫 scratchpad。
2. **核准前只寫 scratchpad**，不改 repo 的檔案、不開分支。這次開發的暫存檔都以 `<功能>-` 開頭，種類與遺失時的恢復方式見 `references/resume.md` 的暫存產物表。
3. **核准的定義**：開發者明確表示核准（例如「核准」）才算；提出修改、回答問題或沒有回應都不算。
4. **向開發者提問**：所有等級、所有階段都用 `clarify-requirements`「需求問答」的 ❓／➡️ 文字格式，不用 AskUserQuestion。
5. **漏洞**：發現可被利用的程式漏洞時（任何階段、任何角色），立刻停止這一項。漏洞的位置與利用方式只寫在給開發者的回報裡，不能出現在 issue、PR 描述、commit 訊息、程式註解、規格檔、測試名稱與 docstring、`docs/reviews/`，也不能把修正推送到公開的 repo（包括這個 PR 的分支）。接著載入 `implement-and-review`，照「漏洞的處理」。
6. **不可合併 PR**：合併一律由開發者決定。

## 判斷等級

依變更**碰到什麼**判斷，不依改動大小（`docs/decisions/0007-process-depth-by-risk.md`）。先看高風險，再看文字修正，都不符合就是一般：

| 等級 | 什麼時候 | 規格 | 規格審查 | 實作審查 |
|---|---|---|---|---|
| 高風險 | 改變下面任何一項的行為或保證：資料一致性（同時操作、中途失敗後的資料狀態、既有資料讀不讀得出來或要不要轉換）；認證與授權（誰動得到哪些資料）；個資、憑證、token 的保護（不出現在 log、回應、公開的地方）；和外部系統同步的一致性與可靠性；其他安全性（輸入驗證、注入）。或屬於下面「重大架構決策」 | 完整格式；「實作計畫」另外寫放棄的做法與理由 | 最多 2 次；reviewer 另外填安全與一致性檢查表 | 直到沒有阻擋；重新審查看整個功能；reviewer 另外填安全與一致性檢查表 |
| 一般 | 其他都不符合的，例如 bug、小的行為修改、只補測試、新功能、新增 endpoint 或改 request／response 格式、改定義流程或規則的文件裡的規則（只改措辭、規則不變的是文字修正） | 完整格式，沒有內容的節可以省略（`docs/specs/README.md`「各等級的規格」） | 最多 2 次 | 直到沒有阻擋；重新審查看修正的項目、它們的驗收條件、修正改到的程式與相關測試，以及連帶影響，不重審整個功能 |
| 文字修正 | 不改變任何程式行為，也不改任何規則：Markdown 文件、註解、錯字，以及不會被執行、也不會被測試讀到的文字。定義流程或規則的文件（skill、agent、CLAUDE.md、`docs/specs/README.md`、`docs/reviews/README.md`、`docs/README.md`、`docs/decisions/`）只限改措辭、規則不變 | 不寫規格檔；主 session 直接改 | 不做 | 不做 |

- 判斷不確定時取較高的等級。等級和理由寫在規格開頭，和規格一起核准。
- 會改變或可能改變程式行為的修改，都不是文字修正。重構、套件升級依實際影響的範圍判斷是一般或高風險。
- 高風險看的是行為或保證有沒有改變，不是用到哪個欄位或元件：例如新增一個選填欄位，舊資料沒有它也照常讀得出來，就依其他條件判斷；改既有欄位的型別或意義、要轉換既有資料，改變了一致性的保證，是高風險。
- 任何階段發現碰到更高等級的範圍，就升級，告訴開發者並補做該等級的步驟（需求問答照 `clarify-requirements`「中途升級」）；只升不降，降級要開發者同意。
- 等級只調整規格與審查的深度：CLAUDE.md「完成的定義」與「開發流程」、測試要求、開發者核准，每個等級都一樣。

## 重大架構決策

指新增服務或外部依賴、改變模組分層、改資料庫結構或部署方式。「改資料庫結構」指新增 collection 或索引、改既有欄位的型別或意義、要轉換既有資料；新增選填欄位不算。

- 屬於重大架構決策的變更是高風險。
- 核准前寫成 scratchpad 的 ADR 草稿 `<功能>-adr-<名稱>.md`，和規格一起核准（見 `write-spec`「已確認的決定寫進規格」）。
- 審查階段才發現的，照 `implement-and-review`「發現處理表」處理。

## 文字修正的流程

在 scratchpad 的 `<功能>-spec.md` 寫改動清單：要改的檔案、改前與改後的文字、為什麼屬於文字修正，交給開發者核准（核准方式見「硬規則」）。核准後從 `main` 開分支，自己修改，跑改到範圍的檢查（只改 `.md` 時不用），開 PR、等 CI，回報等級（文字修正）、PR 連結、CI 結果，以及「回報」的「目前所有 open 的 PR」的合併狀態，並照「清理暫存」確認暫存的內容；`implement-and-review` 的審查與「回報」的驗收表不適用。

- 修改中發現可被利用的漏洞，照 `implement-and-review`「漏洞的處理」。
- 發現和這次修改無關的問題，照 `implement-and-review`「不阻擋的發現開 issue」（沒有審查紀錄，來源只附 PR 連結）。
- 修改中發現會改變程式行為（包括改了測試斷言會看到的文字），就停下來，告訴開發者，重新判斷等級，照新等級的流程從寫規格開始（照 `clarify-requirements`「中途升級」先補做問答）；已經改的部分照「中途升級」處理。

## 4. 回報

PR 連結、等級、驗收表（驗收條件 → 對應的測試 → 結果）、假設清單、規格修改紀錄、規格審查與實作審查紀錄的檔案連結與阻擋項目的處理結果、這次開了或留言了哪些 issue、建立或沿用了哪些 advisory（只寫編號）。給開發者看的回報要附上檔案與測試的連結（`檔案:行號`），不要只寫摘要。PR 描述放同一張驗收表；更新 PR 描述照 CLAUDE.md「開發流程」的方式。

回報的最後列出**目前所有 open 的 PR** 能不能由開發者決定合併，不只這次的 PR：別的 PR 可能因為這次合併而解開（例如等這個 PR 修好 CI），或因為 main 前進而出現衝突。用 `gh pr list --state open`、`gh pr checks <PR>`、`git merge-tree --write-tree origin/main origin/<分支>`（先 `git fetch origin`）逐一確認，分兩區：

- **可以決定要不要合併**：必要的 CI 都通過、和 `main` 沒有衝突、實作審查沒有阻擋項目（沒有審查紀錄的寫「沒有審查」）。
- **還不行**：寫出原因與下一步，例如 CI 失敗、和 `main` 衝突的檔案、仍有阻擋的項目、要等哪個 PR 先合併。

## 清理暫存

見 `docs/README.md`「生命週期」。回報前確認 scratchpad 裡已確認的內容（規格、決定、術語、審查結果）都已經在規格、審查紀錄、ADR 或術語表裡（落點是「術語表」的決定，在 `docs/glossary.md` 找得到就算）；文字修正沒有規格與審查紀錄，對照 PR 的改動與描述；還沒做完的後續動作（例如合併後要在 issue 留言），列在回報的「待辦」，不要只留在 scratchpad。

## 取消

核准前開發者表示不做時，列出 `<功能>-glossary.md` 的術語（有的話），用 `clarify-requirements`「需求問答」的格式請開發者決定保留或不保留。保留：另外照「文字修正的流程」開 PR，只改 `docs/glossary.md`；開 PR 前同樣 `git fetch origin main`，對照 `origin/main` 的 `docs/glossary.md` 有沒有相同或相近的術語，有的話問開發者。核准後 PR 被關閉時不另外處理：改動只在分支上。
