# 寫規格

> 文字修正不寫規格，見 `feature`「文字修正的流程」。快速路徑的短版規格格式見 `docs/specs/README.md`「快速路徑的短版規格」，不做規格審查（`feature`「快速路徑」）。

規格草稿照 `docs/specs/README.md` 的格式寫，放在草稿資料夾（`.drafts/`）的 `<功能>-spec.md`。修 bug 的規格照同一份文件的「修 bug 時」寫。ADR 草稿和規格一起核准，核准後照 `implement-and-review`「交付清單」交給 `feature-implementer` 存進 `docs/decisions/`。

## 規格內容

- **需求／不做**：要做什麼、明確排除什麼。
- **假設**：逐條列出程式碼看不出來、由你判斷的事，以及開發者明確交給你決定的事。先看這件事由誰決定：假設是你判斷、開發者核准時才看到的內容，所以開發者決定的事寫成假設，讀者會以為還沒定。
  - 開發者決定過的事時：寫進需求、不做或驗收條件，不寫成假設。
  - 還要開發者決定的事（例如業務規則）時：照 `clarify-requirements`「新的決定一律回到決策樹」問開發者，確認後寫進需求、不做或驗收條件，不寫成假設。
  - 由你判斷的事，或開發者明確交給你決定的事時：寫成假設；只有無法合理假設、而且會影響整體方向時，才先問開發者。
- **驗收條件**：編號 AC1、AC2…，照 `docs/specs/README.md`「驗收條件怎麼寫」。
- **計畫與測試對應**：要改的檔案、步驟、每條驗收條件對應的測試或驗證步驟，與預期結果。

## 已確認的決定寫進規格

`<功能>-grill.md` 不 commit，所以交給開發者核准前，逐項對照「已確認」的每一項：都在規格、ADR 草稿或 `<功能>-glossary.md` 裡找得到，驗收條件和它不矛盾；開發者決定、會影響實作的項目寫在需求、不做或 AC，不寫成「假設」。要寫在術語表的項目，在 `<功能>-glossary.md` 找得到就算。屬於重大架構決策（定義見 `feature`「重大架構決策」）的，寫成 ADR 草稿 `<功能>-adr-<名稱>.md`，和規格一起核准。

## 規格審查

### 什麼時候做規格審查

規格審查找的是寫程式前就看得出來的問題，例如對現有系統的描述錯了、需求有兩種讀法。需求清楚、沒有決定要做時，審查多出的主要是等待，實作審查也會看規格，所以依下面順序判斷，符合一條就停：

1. 高風險：做。
2. 一般，符合下面任一種：做。問答裡已經決定好、只影響這次新增的行為的事，以及只是確認細節，都不算，因為這類規格出錯的代價小，實作審查也會補查。
   - 規格有影響實作的重要歧義（照字面可以做出兩種行為不同的程式）。
   - 寫規格時還有要開發者決定的事（「請你決定」不是「無」）。
   - 開發者的決定改變了既有的規則或行為（例如既有的排程規則、刪除行為）。
3. 其他的一般：不做。在規格開頭的「規格審查」寫「沒有（<理由>）」，和規格一起核准；之後由 `acceptance-reviewer` 補做規格審查的檢查。快速路徑不做（`feature`「快速路徑」）。

做的時候，把草稿 `<功能>-spec.md` 的路徑、等級、`<功能>-grill.md` 的路徑，以及 ADR 草稿、`<功能>-glossary.md` 的路徑（有的話）交給 `specification-reviewer`。

### 處理發現

照 `implement-and-review`「發現處理」，用「核准前」那一欄。處理發現時開發者做的新決定，照 `clarify-requirements`「新的決定一律回到決策樹」。

### 審查次數

每次審查都要重讀規格與程式碼，所以只在可能找到新問題時才審。照順序做：

1. 第 1 次：完整審查。
2. 處理發現時改了驗收條件、假設或設計時，第 2 次只審改過的部分與受影響的內容。送審時附上修改內容與原因、受影響的 AC、假設與實作計畫，以及第 1 次報告與上一版規格（`<功能>-spec-v<N>.md`）在草稿資料夾的路徑。只改措辭時不審。
3. 之後的修改（包括開發者要求的修改），由主 session 自己檢查：受影響的其他 AC、假設、實作計畫與測試對應都一起改或確認不用改，結果寫進交給開發者核准的訊息。
4. 修改帶出新的重大需求歧義、架構或安全問題時，可以再交給 `specification-reviewer`，只審那個問題，不受上面次數的限制；在交給開發者的訊息寫出理由。

### 審查紀錄

檔案的寫法與貼出的時機照 `implement-and-review`「審查留言」：規格審查在 PR 開之前做，所以留言在 PR 開好後才貼。

## 交給開發者核准

訊息附上草稿路徑，以及：

- 規格審查的摘要：改了什麼、有哪些不採用的建議；沒有做規格審查時寫理由。
- 還需要開發者決定什麼。
- 已確認決定的對照結果：每一項寫在規格、ADR 草稿或術語表的哪裡。開發者核准規格時一併確認這份對照，所以問答結束後不另外請開發者確認「已確認」清單。

核准的定義見 `feature`「硬規則」。
