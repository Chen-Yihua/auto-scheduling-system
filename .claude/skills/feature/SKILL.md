# 功能開發流程

需求：$ARGUMENTS

你是提需求、負責驗收的一方，不自己寫程式。實作交給 `feature-implementer` agent，它只看得到核准的計畫，所以計畫要寫到不需要這段對話也能照著做。

## 1. 需求與計畫（plan mode）

先進入 plan mode，自己讀程式碼，寫成一份計畫交給開發者核准：

- **需求**：要做什麼、不做什麼。
- **假設**：程式碼看不出來、由你自行判斷的業務規則，逐條列出。只有無法合理假設、而且會影響整體方向的問題才先問。
- **驗收條件**：「在 X 情況下，系統要 Y」，每條都要能驗證。除了正常流程，逐一想過失敗、空資料、載入中、未登入／無權限的狀態；不適用的也在計畫裡說明為什麼。
- **計畫**：要改的檔案、步驟、每條驗收條件對應的測試。

開發者要求修改時，更新整份計畫再交一次，直到核准。

## 2. 實作（核准後自動進行，不再中途詢問）

- 交給 `feature-implementer` agent，附上計畫檔路徑和分支名稱。
- 它回報計畫有問題時，判斷是否影響範圍或驗收條件：會影響就停下來問開發者，更新計畫後再交回去；不影響就直接回覆它怎麼做。

## 3. 驗收

交給 `acceptance-reviewer` agent，附上核准的驗收條件和分支名稱。依它標的類別處理：

- **實作不符**：交回 `feature-implementer` 修正，修完再驗一次。
- **驗收條件缺漏**：不要自己補，也不要默默列成範圍外。停下來向開發者提出新增或修改的驗收條件，問要在這個 PR 補上，還是另開 issue 追蹤：
  - 這個 PR 補：更新計畫檔的驗收條件，交回 `feature-implementer` 實作並補測試，再驗一次。
  - 另開 issue：用 `gh issue create` 記下缺漏的驗收條件，PR 描述附上 issue 連結。
- **範圍外**：列進最後的回報。

最後回報：PR 連結、驗收表（驗收條件 → 對應的測試 → 結果）、假設清單、驗收條件的修改紀錄、範圍外發現的問題。PR 描述放同一張驗收表；更新 PR 描述照 CLAUDE.md「開發流程」的方式。
