# 功能開發流程（grilling 實驗版）

需求：$ARGUMENTS

這是實驗用的入口，正式流程仍是 `/feature`。和 `/feature` 唯一的差別是寫規格前多了第 0 節的需求問答；實驗目的與紀錄方式見 `docs/experiments/feature-grill/README.md`。

開始時執行 `git rev-parse HEAD` 和 `date -Iseconds`，記下起始 commit 與時間；之後每個階段結束時也記下時間，第 4 節填實驗紀錄時用。

## 0. 釐清需求（不開 plan mode）

問答規則改寫自 [mattpocock/skills](https://github.com/mattpocock/skills) 的 `grilling`（commit `4ae2317`，MIT 授權）。不開 plan mode：plan mode 會讓你急著產出計畫，這一節要的是問到沒有問題為止。

把需求畫成**決策樹**：每個決定底下掛著因它而來的決定。每一**輪**問「前沿」：前提都已經決定好、現在就能問的所有問題，一次問完，等開發者回答完再算下一輪。同一輪裡，答案取決於另一題的問題，放到下一輪。

每一輪的格式：

```
❓ **Q1** - **<標題>**：<內容，可以有多段、多個選項>

➡️ <建議答案>

---

❓ **Q2** - …
```

- 題目的問法要讓「是」等於接受建議答案。
- 涉及未定義的產品行為、權限、安全性或資料處理的題目，不給建議答案：`➡️` 那一行改成列出選項與各自的影響，每一題都要開發者明確回答（和 `/feature` 第 3 節「Missing AC 的處理」同一個標準）。
- **事實自己查，不問開發者**：程式碼、文件、git 紀錄查得到的就自己讀；範圍很大時才派 `Explore` agent。查詢還沒結束時，只有依賴查詢結果的題目要等，其他照問。
- **決定交給開發者**：業務規則、範圍、取捨都要問，不可自己回答自己的問題。開發者明確說「你決定」的才由你決定，並記下來。
- 只靠討論決定不了的問題（畫面怎麼排、操作感受），不要一直換句話問：說明這題需要看到畫面才能決定，請開發者選擇先用假設、或排除在這次範圍外。
- 不設題數上限。開發者要求收尾時，把還沒問到的分支列為「未決定」，請開發者決定各自寫成假設或不做。

前沿空了就整理「已決定的事項」，編號 D1、D2…，每項標上來源（開發者決定／開發者交給你決定），請開發者確認雙方理解一致。開發者確認前，不進第 1 節。

## 1–4. 照 `/feature` 執行

讀 `.claude/skills/feature/SKILL.md`，照第 1–4 節執行，差異只有：

| 項目 | `/feature-grill` 的做法 |
|---|---|
| 第 1 節的提問 | 不再另外問問題。寫規格時發現第 0 節漏掉的決定，用第 0 節的格式再問一輪，算進問答輪數 |
| 規格內容 | 開發者決定的 D 項寫進「需求」「不做」「驗收條件」；只有開發者交給你決定的 D 項，以及你為了寫規格另外做的判斷，才寫進「假設」。「背景」最後加一行：`需求釐清：/feature-grill（實驗），問答 N 輪` |
| 第 4 節的回報 | 另外照下面「實驗紀錄」填一份紀錄，在回報裡附上檔案路徑 |

## 實驗紀錄

複製 `docs/experiments/feature-grill/TEMPLATE.md` 到 `docs/experiments/feature-grill/records/<功能>-feature-grill.md`，照模板裡每個欄位的說明填寫。

- 數字從規格的「修改紀錄」、`docs/reviews/<功能>-round<N>.md`、這次對話的問答輪數計算，不要估算；拿不到的數字寫「無資料」與原因。
- Missing AC 的嚴重程度由你依模板的定義提出，開發者確認後才算數。
- Token 用量由開發者執行 `/cost` 提供，你沒辦法自己讀；請開發者在第 0 節確認後與流程結束時各執行一次。
- 紀錄檔不要放進這個功能的 PR：實驗紀錄最後一起用另一個 PR 提交。
