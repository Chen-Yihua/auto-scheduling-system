# 0006. bug 也用完整規格格式並做規格審查

- 狀態：已採用（文字修正不寫規格、輕量只審 1 輪的例外見 [0007](0007-process-depth-by-risk.md)）
- 日期：2026-11-07

## 背景

[0003](0003-issue-workflow.md) 讓 bug 用簡化規格（重現步驟＋回歸測試），[0005](0005-specification-review.md) 讓簡化規格不做規格審查，理由是規格很短，而且「改程式前先失敗」的回歸測試已經驗證了重現步驟。

用簡化格式修的三個 bug，規格的問題都到實作後才發現：

- #28（PR #45）：AC1 的前提錯了（導覽發生時第一次登入已經完成，重新登入會被 Clerk 拒絕），CI 跑起來才看出來；之後實作審查又找到 AC1 沒定義的步驟（Missing AC），規格核准後改了 2 次。
- #46（PR #49）：實作審查第 1 輪找到 AC 互相衝突（Specification Defect）與沒定義的網址格式（Missing AC），規格整份重寫。改用完整格式並做規格審查後，2 輪規格審查又找到 17 項，其中 6 項要開發者決定。
- 簡化格式沒有「實作計畫」，開發者核准時看不到修法，判斷不了驗收條件合不合適（#46 時開發者提出）。

回歸測試只驗證「bug 能重現」，驗證不了修法和驗收條件本身對不對。

## 決定

- bug 用和功能相同的完整格式（`docs/specs/README.md`「格式」），另外照「修 bug 時」：背景寫現象、重現步驟、原因；AC1 對應重現步驟；實作計畫寫修法與理由；測試對應多一欄「改程式前是否失敗」。
- bug 的規格也交給 `specification-reviewer` 審查，流程和功能相同（`/feature` 第 1 節）。

## 放棄的做法

- **保留簡化格式，只補「解決做法」一節**：#28、#46 的問題出在驗收條件之間的矛盾與缺漏，沒有規格審查就要到實作後才看得出來，只補修法解決不了。
- **依 bug 的大小決定要不要審查**：大小在寫規格前不好判斷，#28、#46 一開始看起來都是小修正。

## 影響

- 每個 bug 多一次規格審查（agent 執行），規格也比較長。
- 本 ADR 取代 0003 的「bug 用簡化規格」，以及 0005「放棄的做法」裡「bug 簡化格式也做規格審查」的取捨；0003、0005 的其他決定照舊。
- 2026-11-07 以前用簡化格式寫的規格（`docs/specs/issue-28-…`、`issue-37-…`）保留原樣，不改寫。
