# 功能規格

用 `/feature` 開發的每個變更一份，檔名 `<功能>.md`；用 `/issue` 開發的檔名 `issue-<N>-<簡短名稱>.md`。等級是「文字修正」的不寫規格（見 `/feature` 第 1 節「判斷等級」）。核准後才存進這裡，和實作放在同一個 PR。為什麼放在這裡見 [ADR 0002](../decisions/0002-specs-in-repo.md)。

規格是實作 agent 唯一的需求來源，要寫到不看討論過程也能照著做。

## 規格和目前系統的關係

規格記錄的是**核准當時**的需求、設計與驗收條件，PR 合併後不再隨程式更新。之後的變更改了它定義的行為，寫在新的規格裡，不回頭改舊規格的內容。目前系統的行為以程式碼、[api.md](../api.md)、[architecture.md](../architecture.md) 為準。

- 新規格取代了舊規格定義的行為時，在新規格的 PR 裡把舊規格的「狀態」改成「已被 [<新規格>](<檔名>.md) 取代」；只取代一部分時寫「部分被 [<新規格>](<檔名>.md) 取代（AC3、AC5）」。只改狀態這一行，其他內容保留原樣。
- 規格永久保存，不因為過時而刪除（[docs/README.md](../README.md)「生命週期」）。
- ADR 0007 以前的規格有的寫「已完成」，意思是 PR 已合併，等同「已核准」；之後不再使用這個狀態，因為合併由開發者決定，沒有人負責回頭更新。

## 驗收條件怎麼寫

各等級都適用，issue 裡「建議的驗收條件」也照這裡寫（見 [docs/issues.md](../issues.md)）。

- **使用者行為**：使用者（或部署維護者、用 agent 的開發者）做了什麼、看得到什麼結果。
- **不變條件**：只看畫面驗不出來、但需求成立一定要守住的系統狀態，例如資料庫和 Google Calendar 的事件一致、同時送出兩個請求的結果和依序執行一樣、只動得到自己的資料。需求涉及資料一致性、併發、權限、外部系統狀態時一定要寫，因為只看畫面的 AC 讓錯的實作也能通過。
- 每條都要能驗證：寫得出對應的測試，或寫明手動驗證的步驟（例如 CI run、部署紀錄）。
- 和需求無關的技術細節不寫進 AC，例如指定實作方式、沒有人會碰到的防禦情境。

## 格式

```markdown
# <功能名稱>

- 狀態：草稿 | 已核准 | 已被 [<規格>](<檔名>.md) 取代 | 部分被 [<規格>](<檔名>.md) 取代（AC…）
- 等級：輕量 | 標準 | 高風險（理由）
- issue：#NN（由 `/issue` 開發時）
- PR：#NN

## 背景
為什麼要做。

## 需求
要做什麼。

## 不做
明確排除的範圍。

## 假設
程式碼看不出來、經開發者核准的業務規則，逐條編號。

## 驗收條件
| # | 條件 |
|---|---|
| AC1 | 在 X 情況下，系統要 Y |

每條都要能驗證。逐一想過失敗、空資料、載入中、未登入／無權限、資料處理、安全性；不適用的寫在下面並說明原因。

## 不適用的情境
| 情境 | 原因 |
|---|---|

## 實作計畫
要改的檔案、步驟，以及為什麼這樣做（解決做法）。高風險另外寫考慮過、沒選的做法與理由；屬於重大架構決策的連結 ADR。

## 測試對應
| AC | 測試 |
|---|---|

修 bug 時加一欄「改程式前是否失敗」（見下面「修 bug 時」）。

## 修改紀錄
| 日期 | 修改 | 原因 | 確認者 |
|---|---|---|---|
```

## 修 bug 時

bug 也用上面的格式，也做規格審查（[ADR 0006](../decisions/0006-bugs-use-full-spec.md)）。各節的寫法：

- **背景**：現象（誰在做什麼的時候，看到什麼、造成什麼影響）、重現步驟、預期行為與實際行為、原因（`檔案:行號`；還不確定時寫「待確認」與推測）。
- **驗收條件**：AC1 是重現步驟對應的預期行為；修正可能影響到的相關行為另外加 AC。
- **實作計畫**：修法和為什麼這樣修，讓開發者核准前就能判斷驗收條件合不合適。
- **測試對應**：多一欄「改程式前是否失敗」。重現 bug 的測試要在改程式前先確認會失敗，修正後通過；保護既有行為的測試寫「否（保護既有行為）」。

2026-11-07 以前的 bug 規格（`issue-28-…`、`issue-37-…`）用的是已廢止的簡化格式，保留原樣。

## 各等級的規格

等級的判斷與各等級的審查見 `/feature` 第 1 節「判斷等級」（[ADR 0007](../decisions/0007-process-depth-by-risk.md)）。草稿寫在 scratchpad 的 `<功能>-spec.md`，核准前不存進這裡，所以狀態「草稿」只會出現在 scratchpad 的草稿。

| 等級 | 必要的節 | 可以省略 |
|---|---|---|
| 輕量 | 背景、需求、驗收條件、實作計畫、測試對應、修改紀錄 | 沒有內容的「不做」「假設」；「不適用的情境」可以合成一列，例如「載入中、未登入：沒有改到畫面與登入流程」 |
| 標準 | 全部 | 無 |
| 高風險 | 全部；「實作計畫」寫放棄的做法 | 無 |

省略是指那一節沒有內容，不是沒有想過：輕量也要逐一想過「格式」裡「驗收條件」下方列出的每一類情境，合成一列時要寫出每一類的名稱；沒有被驗收條件涵蓋的每一類，都要能用一句話說明為什麼不適用，做不到就不是輕量。

## 核准後

規格核准後，驗收條件的任何新增、修改、刪除都要記在「修改紀錄」，並註明開發者確認過；「原因」寫上對應的 Context 編號（C1、C2…，見 `/feature` 第 1 節「需求問答」），所有等級都寫。PR 合併後的變更照上面「規格和目前系統的關係」寫新規格。
