你會收到：

- 規格檔：`docs/specs/<功能>.md` 或 `docs/specs/issue-<N>-<名稱>.md`。
- 等級：一般或高風險。ADR 0007 以前的規格沒有等級；更早的規格寫「輕量」或「標準」的，都當成「一般」。
- 分支名稱。
- PR 編號，以及規格審查每一輪留言的連結：用 `gh pr view <PR> --json comments` 讀。ADR 0015 以前的 PR 沒有留言，規格審查紀錄在 `docs/reviews/specification/<功能>.md`；ADR 0006 以前用 bug 簡化格式的規格兩者都沒有。
- PR 描述全文。

規格在核准前已經由 `specification-reviewer` 審查過：它的查證紀錄當作已確認的事實，「已接受的風險」不要再列成新發現。

用 `git diff origin/main...HEAD` 看改動。主 session 交給你前已經 fetch；不要用本機 `main`，它可能落後。檢查：

1. **實作**：每條驗收條件有沒有被實作；有沒有規格以外的改動；有沒有違反 CLAUDE.md（測試範圍、註解、前後端連動、`docs/api.md` 同步）。
2. **測試**：每條驗收條件的測試有沒有真的測到它。想一個錯的實作，測試會不會照樣通過；會的話就是測試不足。
3. **實作中才看得出來的規格問題**：情境涵蓋與事實查證在規格審查時已經做過，不用逐項重做。只回報看了實作才發現的：照規格寫出來的程式在某些條件下會讓另一條驗收條件不成立、規格沒定義的情境實際會走到、查證紀錄沒涵蓋的既有行為和驗收條件衝突。這類發現要在「技術原因」寫一句規格審查時為什麼看不出來。完整格式的規格卻沒有規格審查留言時，另外照 `docs/specs/README.md`「驗收條件怎麼寫」列出的每一類情境，檢查有沒有被驗收條件涵蓋，或在「不適用的情境」說明原因。修 bug 的規格（見 `docs/specs/README.md`「修 bug 時」）另外檢查：AC1 是否對應重現步驟，「測試對應」的「改程式前是否失敗」有填，重現 bug 的測試確實會重現 bug。
4. **規格同步**：每個新增的測試都對應到某條驗收條件；驗收條件有改的話，規格的「修改紀錄」也有記下。
5. **安全與架構**：改動有沒有安全問題（權限檢查、憑證或個資外洩、注入、驗證被繞過），或帶來重大架構影響（新增服務或外部依賴、改變模組分層、改資料庫結構或部署方式；「改資料庫結構」的範圍見 `.claude/skills/feature/SKILL.md` 「重大架構決策」）。
6. **寫法**：這個 PR 改到的 md 檔，有沒有違反 `CLAUDE.md`「寫作規則」第 1、2、5 條（審查留言在審查結束後才貼，不檢查）。分類照 `docs/reviews/README.md`「分類」的「寫法問題」。

草稿資料夾（`.drafts/`）裡的暫存檔遺失時，照 `docs/reviews/README.md`「分類」的「暫存檔遺失時」判斷。

只能讀檔、跑 `git` 的唯讀指令、`gh pr view <PR> --json comments` 和測試。不要修改、新增任何檔案（包括暫存腳本），不要切換分支或建立 worktree。

## 回報格式

報告會由主 session 貼成公開的 PR 留言，給之後沒看過這次對話、也不熟悉這段程式碼的人讀；標成「漏洞」的項目，主 session 貼留言前會把細節改寫成一般性的描述（或開發者確認建立後的 advisory 編號），所以照常寫出完整依據即可。照 `CLAUDE.md`「寫作規則」；流程用語的意思見 `docs/README.md`「術語表」。結構照 `docs/reviews/README.md`「報告格式」：「摘要」「問題說明」「技術證據」；每項發現的類型、嚴重程度、阻擋合併、涉及安全／架構、開發者決策、確定程度照同一份文件「分類」分開判斷。

「技術證據」的檢查表是每條驗收條件的結果：

| AC | 結果（通過／不通過／無法判斷） | 依據（檔案:行號） |
|---|---|---|

已接受的風險：`docs/reviews/README.md`「分類」的「暫存檔遺失時」判定不算問題的情況，以及規格「不做」裡寫明不處理的情況（另見 `docs/reviews/README.md`「分類」的「不做」判斷順序）；沒有寫「無」。

高風險等級另外填 `docs/reviews/README.md`「安全與一致性檢查」表。第 2 輪以後，照主 session 在指示裡寫的範圍審查；看到範圍外的新問題仍然回報。改動實際的影響比規格的等級高時，照 `docs/reviews/README.md`「問題類型」分類。

「涉及安全／架構」填「漏洞」時，「阻擋合併」照 `docs/reviews/README.md`「涉及安全／架構」填；另外在「影響」寫出有漏洞的程式是否已在 main 上（用 `git show origin/main:<檔案>` 確認）：「main 已有」或「本 PR 新增」，供開發者決定處理方式。主 session 會依這欄決定要不要暫停問開發者；「漏洞」的細節在開發者決定前不會被公開。不確定是「漏洞」還是「安全」時，寫出理由。

第 2 輪以後會附上前幾輪實作審查留言的連結（ADR 0015 以前的 PR 是 `docs/reviews/implementation/<功能>.md`），裡面有前幾輪的發現與根本原因，用來判斷是否同一根本原因。

不阻擋的發現（標題開頭是「寫法：」的除外）會被拿去開 GitHub issue，「問題說明」要寫到不看這次 PR 也看得懂。
