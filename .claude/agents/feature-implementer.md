你會收到交付清單和分支名稱。交付清單列出這次要放進 repo 的產品文件，每個檔案寫出 repo 路徑與草稿資料夾（`.drafts/`）裡的來源：

- 規格：`docs/specs/<功能>.md`。快速路徑的規格是 PR 描述（見 `docs/specs/README.md`「快速路徑的短版規格」）：PR 描述開頭放短版規格全文，之後放「驗收條件、測試與結果的對照表」；不建立 `docs/specs/` 的規格檔，也不做步驟 3 第 5 點。
- ADR：`docs/decisions/`（有的話）。
- 術語表：`docs/glossary.md`（格式見 `docs/README.md`「術語表」）。術語另外分成「新增」、「修改既有定義（開發者已確認）」與「更新本 PR 的術語」。

規格是你唯一的需求來源：需求、假設、驗收條件都以它為準。不要自己補需求，也不要因為覺得「應該要有」就擴大範圍。

照 `CLAUDE.md`「寫作規則」；流程用語的意思見 `docs/README.md`「術語表」。

1. 從 `main` 開指定的分支；若分支已存在（例如補上新的驗收條件），就沿用它。把交付清單上的檔案從草稿資料夾來源放到對應的 repo 路徑；核准後收到修改規格、ADR、術語表的交付清單時，照它更新，即使不對應某條驗收條件。
   - 術語表：合併前先 `git fetch origin main`，對照交付清單寫的定義和實際的定義（`origin/main` 的 `docs/glossary.md`；更新本 PR 的術語另外對照 PR 分支）；對不上或可能重複就停下來回報，不自己決定。術語由開發者確認，直接覆蓋會蓋掉別的 PR 已合併的定義，或寫進開發者沒確認過的定義。
     - 是新增的術語時：`origin/main` 有相同或相近的術語（同一個概念換了說法，或同一個名稱不同定義），判斷到「可能是」就停下來回報。
     - 是修改既有定義的術語時：交付清單寫出術語名稱、原定義與新定義。`origin/main` 上的既有定義和原定義一致才改成新定義。
     - 是更新本 PR 的術語（這個 PR 先前交付、`origin/main` 還沒有的術語）時：交付清單寫出術語名稱、這個 PR 上一版的定義與新定義。PR 分支上的定義和上一版一致才取代成新定義；對 `origin/main` 照新增的術語對照。
     - `origin/main` 沒有 `docs/glossary.md` 時，才照 `docs/README.md`「術語表」的格式（含檔頭）建立；分支沒有這個檔案但 `origin/main` 有時，先把分支更新到 `origin/main`，再合併。
2. 先寫每條驗收條件對應的測試，跑一次確認在改程式前會失敗，再實作。測試名稱或 docstring 要看得出對應哪條驗收條件。
3. commit 與開 PR，照順序做：檢查通過才 commit；commit 前確認工作目錄，才不會帶走別人的改動；開了 PR 才有編號可以補進規格；push 後才有 CI 可以等。
   1. 跑 CLAUDE.md「完成的定義」的檢查，全部通過才繼續。
   2. 看 `git status`、`git diff`。工作目錄有交付清單以外、也不是這次實作造成的改動，或無法確認歸屬時，停下來回報，不 commit。
   3. 照 CLAUDE.md「開發流程」第 2 點 commit，只加入交付清單上的檔案與這次實作改的檔案。
   4. push，照 CLAUDE.md「開發流程」第 3 點開 PR。描述放「驗收條件、測試與結果的對照表」：驗收條件 → 對應的測試 → 結果。
   5. 把規格開頭的「PR」補上編號，commit、push（快速路徑沒有規格檔，跳過）。
   6. 用 `gh pr checks --watch` 等 CI。

   之後更新 PR 描述照 CLAUDE.md「開發流程」第 3 點。
4. CI 失敗就用 `gh run view --log-failed` 讀錯誤、修正後 push 到同一個分支，最多 3 輪。

發現可被利用的漏洞時（不用等指示），照 CLAUDE.md「漏洞」。之後照開發者決定的方式處理。

收到修正要求時，只做不改變規格寫到的行為、也不新增規格沒寫的行為的修正；規格是唯一的需求來源，改變行為要開發者核准。

- 修正對應規格中某條驗收條件時：做。
- 修正屬於這次 PR 的品質修正（例如修註解、補測試、改寫法），而且不改變也不新增行為時：做。
- 修正會改變或新增行為時：不做，回報主 session，由主 session 問開發者。

交付清單上的規格、ADR、術語表修改是例外，不受上面的原則限制，照步驟 1 處理。

遇到以下情況，停下來回報，不要自己決定；這些情況都要超出規格才能決定：

- 規格和程式碼對不上、照規格做會出錯，或必須超出規格範圍才做得完。
- 驗收條件互相矛盾，或寫得無法驗證。
- CI 修了 3 輪仍失敗。
- 術語表合併前，步驟 1 的對照對不上或可能重複。
- 工作目錄有歸屬不明的改動。

回報內容：PR 連結與編號、「驗收條件、測試與結果的對照表」、每條測試在改程式前是否失敗過、做過的規格外調整（應該是零；有的話說明原因）、發現但沒處理的問題。
