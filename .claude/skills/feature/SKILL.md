# 功能開發流程

需求：$ARGUMENTS

你是提需求、負責驗收的一方，不自己寫程式（第 1 節「文字修正」等級除外）。規格核准前交給 `specification-reviewer` 審查，實作交給 `feature-implementer`，實作後交給 `acceptance-reviewer` 審查；它們都看不到這段對話，所以規格要寫到不看這段對話也能照著做。分工的原因見 `docs/decisions/0001-separate-feature-roles.md`、`docs/decisions/0005-specification-review.md`。

## 1. 規格

順序：自己讀程式碼，判斷變更等級（見第 1 節「判斷等級」）→ 標準、高風險做「需求問答」，開發者確認 Context（開發者確認過的資訊，定義見「Context 與 Frontier」）→ 照 `docs/specs/README.md` 的格式寫規格草稿 → 「規格審查」→ 交給開發者核准。輕量、文字修正判斷完等級直接寫草稿。由 `/issue` 進來時，需求來自 issue；修 bug 的寫法見同一份文件的「修 bug 時」。

不用 plan mode，也不用 ExitPlanMode 請開發者核准（`docs/decisions/0008-grilling-without-plan-mode.md`）。開發者在 plan mode 中叫出這個流程時，先請開發者退出 plan mode：plan mode 中不能寫 scratchpad。

- 規格草稿寫在 scratchpad 的 `<功能>-spec.md`（文字修正寫改動清單，見「文字修正的流程」）。
- 核准前只寫 scratchpad，不改 repo 的檔案、不開分支。這次開發的暫存檔都以 `<功能>-` 開頭：規格草稿 `<功能>-spec.md`、Context 與 Frontier `<功能>-grill.md`（見「Context 與 Frontier」）、術語 `<功能>-glossary.md`（見「術語表」）、重大架構決策的 ADR 草稿 `<功能>-adr-<名稱>.md`、規格審查紀錄草稿 `<功能>-spec-review.md`、各輪審查報告原文。ADR 草稿和規格一起核准，核准後照第 2 節「交付清單」交給 `feature-implementer` 存進 `docs/decisions/`。
- 交給開發者核准時，訊息附上草稿路徑與審查摘要。開發者明確表示核准（例如「核准」）才算核准；提出修改、回答問題或沒有回應都不算。
- 所有等級、所有階段向開發者提問，都用「需求問答」的 ❓／➡️ 文字格式，不用 AskUserQuestion。

### 判斷等級

依變更**碰到什麼**判斷，不依改動大小（`docs/decisions/0007-process-depth-by-risk.md`）。依序比對：先看高風險，再看文字修正、輕量，符合就是那個等級；都不符合就是標準：

| 等級 | 什麼時候 | 規格 | 規格審查 | 實作 | 實作審查 |
|---|---|---|---|---|---|
| 高風險 | 改變下面任何一項的行為或保證：資料一致性（同時操作、中途失敗後的資料狀態、既有資料讀不讀得出來或要不要轉換）；認證與授權（誰動得到哪些資料）；個資、憑證、token 的保護（不出現在 log、回應、公開的地方）；和外部系統同步的一致性與可靠性；其他安全性（輸入驗證、注入）。或屬於第 3 節的重大架構決策 | 完整格式；「實作計畫」另外寫放棄的做法與理由 | 最多 2 輪；reviewer 另外填安全與一致性檢查表 | `feature-implementer` | 直到沒有阻擋；reviewer 另外填安全與一致性檢查表 |
| 標準 | 其他等級都不符合的，例如新功能、跨功能範圍的行為修改、新增 endpoint 或改 request／response 格式、改定義流程或規則的文件裡的規則（只改措辭、規則不變的是文字修正） | 完整格式 | 最多 2 輪 | `feature-implementer` | 直到沒有阻擋 |
| 輕量 | 只在一個功能範圍內的 bug、小的行為修改，或只補測試。功能範圍例如一支 API 的 router＋crud＋測試、一個頁面的元件＋composable；例如單一 API 回錯的狀態碼、畫面顯示錯誤、使用者看得到的文案 | 完整格式，沒有內容的節可以省略（`docs/specs/README.md`「各等級的規格」） | 1 輪；還有阻擋就整理好問開發者，不跑第 2 輪；第 1 輪後改寫的驗收條件見第 1 節「規格審查」 | `feature-implementer` | 直到沒有阻擋；重新審查看修正的項目、它們的驗收條件、修正改到的程式與相關測試，以及修正可能的連帶影響，不重審整個功能 |
| 文字修正 | 不改變任何程式行為，也不改任何規則：Markdown 文件、註解、錯字，以及不會被執行、也不會被測試讀到的文字。定義流程或規則的文件（skill、agent、CLAUDE.md、`docs/specs/README.md`、`docs/reviews/README.md`、`docs/README.md`、`docs/decisions/`）只限改措辭、規則不變 | 不寫規格檔 | 不做 | 主 session 直接改 | 不做 |

- 判斷不確定時取較高的等級。等級和理由寫在規格開頭，和規格一起核准。
- 會改變或可能改變程式行為的修改，都不是文字修正。重構、套件升級依實際影響的範圍判斷是輕量、標準或高風險。
- 高風險看的是行為或保證有沒有改變，不是用到哪個欄位或元件：例如新增一個選填欄位，舊資料沒有它也照常讀得出來，就依其他條件判斷；改既有欄位的型別或意義、要轉換既有資料，改變了一致性的保證，是高風險。
- 任何階段（寫規格、規格審查、實作回報、實作審查）發現碰到更高等級的範圍，就升級，告訴開發者並補做該等級的步驟（需求問答照「中途升級」）；降級要開發者同意。
- 等級只調整規格與審查的深度：CLAUDE.md「完成的定義」與「開發流程」、測試要求、開發者核准，每個等級都一樣。

**文字修正的流程**：在 scratchpad 的 `<功能>-spec.md` 寫改動清單：要改的檔案、改前與改後的文字、為什麼屬於文字修正，交給開發者核准（核准方式同上）。核准後從 `main` 開分支，自己修改，跑改到範圍的檢查（只改 `.md` 時不用），開 PR、等 CI，回報等級（文字修正）、PR 連結、CI 結果，以及第 4 節「目前所有 open 的 PR」的合併狀態，並照第 4 節「清理暫存」確認暫存的內容；第 2 節、第 3 節的審查與第 4 節的驗收表不適用。但修改中發現可被利用的漏洞，照第 3 節「漏洞的處理」；發現和這次修改無關的問題，照第 3 節「不阻擋的發現開 issue」（沒有審查紀錄，來源只附 PR 連結）。修改中發現會改變程式行為（包括改了測試斷言會看到的文字），就停下來，告訴開發者，重新判斷等級，照新等級的流程從寫規格開始（標準、高風險照「中途升級」先補做問答）；已經改的部分照「中途升級」處理。

### Context 與 Frontier（所有等級）

向開發者提問的題目與回答用兩份清單追蹤，都寫在 scratchpad 的 `<功能>-grill.md`（「Context」「Frontier」兩節），每輪問完就更新。對話被摘要、審查 agent 看不到對話時，靠這份檔案。所有等級都用這份檔案：輕量、文字修正不做多輪問答，但問開發者的題目與回答一樣記進去。

- **Context**：開發者確認過的資訊，也就是開發者回答的決定，以及開發者明確交給你決定的事。從程式碼、文件、git 紀錄查到的事實不放進 Context，寫進規格的「背景」。每項編號 C1、C2…（整個功能連續），寫：

  | 欄位 | 內容 |
  |---|---|
  | 內容 | 決定了什麼 |
  | 決定者 | 開發者決定／開發者交給你決定 |
  | 來源 | 哪一題（Qn） |
  | 前提 | 依賴哪些 C 項；沒有寫「無」 |
  | 產生階段 | 問答、寫規格、規格審查、實作回報、實作審查；文字修正是「改動清單」或「修改中」 |
  | 寫進哪裡 | 規格的哪一節或哪條 AC、ADR，或「術語表」（見下面「術語」）；文字修正寫「改動清單」 |

- **Frontier（前沿）**：從目前的 Context 推出、前提都已確認、現在就能問的問題，加上還沒問到的分支。題目編號 Q1、Q2…，整個功能連續編號，不每輪從 Q1 重來。開發者回答後，答案編成 Context 項，題目從 Frontier 移除；回答帶出的新問題加進 Frontier。
- **C、Q 編號只在 scratchpad 用**：編號只用來在 session 中對照 `<功能>-grill.md`，這份檔案不 commit，之後的讀者查不到。寫進規格、審查紀錄、ADR、術語表、PR 描述、issue、commit 訊息時，不寫指向某次開發的 Context／Frontier 項的引用（例如「依 C3」「Q12 的決定」），一律換成決定的內容與落點（規格的節或 AC 編號、ADR 編號，或「術語表」）。說明編號制度本身，或描述既有紀錄的文字，不算引用。
- **決定的追溯**：問答與寫規格階段的決定只留在規格（內容與落點），不記進審查紀錄的「開發者決策」表，當時的選項不保留。審查與核准後產生的決定，照 `docs/reviews/README.md`「紀錄檔格式」記在審查紀錄的「開發者決策」表。
- **術語**（標準、高風險）：開發者回答了一個術語的名稱與定義（包括接受建議答案），這個術語就算確定。
  - 核准前任何階段（問答、寫規格、規格審查）確定的術語：編成 Context 項，「寫進哪裡」寫「術語表」，馬上照「術語表」的格式寫進 scratchpad 的 `<功能>-glossary.md`。核准前仍然只寫 scratchpad，不改 repo。
  - 核准後（實作回報、實作審查）才確定或修改的術語：照第 3 節「規格問題的處理」寫進規格的修改紀錄（落點「術語表」），更新 `<功能>-glossary.md`，照第 2 節「交付清單」交給 `feature-implementer`。
  - 輕量、文字修正不做問答，不寫術語表。

### 需求問答（標準、高風險）

問答規則改寫自 [mattpocock/skills](https://github.com/mattpocock/skills) 的 `grilling`（commit `4ae2317`，MIT 授權）。這一節要的是問到沒有問題為止，再寫規格。第一輪開頭寫出暫定的等級與理由；等級仍和規格一起核准。

問答的題目與回答照「Context 與 Frontier」記進 `<功能>-grill.md`。

把需求畫成**決策樹**：每個決定底下掛著因它而來的決定。每一**輪**問 Frontier 裡現在就能問的所有問題，一次問完，等開發者回答完再算下一輪。同一輪裡，答案取決於另一題的問題，放到下一輪。

每一輪的格式：

```
❓ **Q1** - **<標題>**：<內容，可以有多段、多個選項>

➡️ <建議答案>

---

❓ **Q2** - …
```

- 題目的問法要讓「是」等於接受建議答案；下一點的「需要你選擇」題目除外。
- 涉及未定義的產品行為、權限、安全性、資料處理或架構的題目，先列出選項與各自的影響，`➡️` 那一行寫建議與理由，並標明「需要你選擇」：開發者要選定一個選項（或另外說明），只回「是」不算（和第 3 節「規格問題的處理」同一個標準）。
- **事實自己查，不問開發者**：程式碼、文件、git 紀錄查得到的就自己讀；範圍很大時才派 `Explore` agent。查詢還沒結束時，只有依賴查詢結果的題目要等，其他照問。
- **決定交給開發者**：業務規則、範圍、取捨都要問，不可自己回答自己的問題。開發者明確說「你決定」的才由你決定，並記下來。
- 只靠討論決定不了的問題（畫面怎麼排、操作感受），不要一直換句話問：說明這題需要看到畫面才能決定，請開發者選擇先用假設、或排除在這次範圍外。
- 不設題數上限。開發者要求收尾時，把還沒問到的分支列為「未決定」，請開發者決定各自寫成假設或不做。
- **用詞和術語表不一致時馬上問**：開發者或 issue 用的詞和 `docs/glossary.md`、`<功能>-glossary.md` 的定義不一致時，馬上指出並問清楚。
- **用詞模糊時提出明確的說法**：用詞模糊，或同一個詞可能指不同概念時，提出明確的說法請開發者選。

Frontier 空了之後，先讀規格會碰到、但還沒讀過的程式碼（實作計畫會改的檔案、新功能和既有規則交會的地方，例如既有的排程規則、刪除行為、登入驗證），因為寫規格時才讀到的程式碼，常會冒出問答沒問到的決定。有新的決定就再問一輪。

接著把 Context 列給開發者，請開發者確認雙方理解一致；開發者確認前，不寫規格草稿。

**新的決定一律回到決策樹**：Context 確認之後，任何階段（寫規格、規格審查、實作回報、實作審查）出現需要開發者決定的事，都照這裡處理，不要在決策樹之外決定：

1. 把要問的事加進 Frontier（Q 接著編號），開發者回答後編成新的 Context 項（C 接著編號），寫進 `<功能>-grill.md`，標上產生階段。
2. 做影響檢查：列出可能受影響的既有 Context 項。判斷方式是「同一個欄位、同一支 API、同一條排程或刪除規則」，或「前提」裡有關聯。每一項寫有沒有改變、原因。例如「子任務可以插入任意位置」要檢查 AI 推斷優先序的調整（現在要同時看前後兩個階段）、刪除後遞補（插入、刪除的一致性），以及優先序與截止日的限制。
3. 有既有 Context 項被改變時，把它重新打開，用上面的格式問開發者，影響表附在題目前面。
4. 開發者確認新增和改變的 Context 項後，才能進下一階段；只要確認這些項目，不用整份重看。

**中途升級**：從輕量或文字修正升級成標準或高風險時，依升級的時間點處理：

- 核准前（寫規格、規格審查）：補做問答，再改寫草稿。
- 文字修正修改中發現會改變程式行為：補做問答，再照新等級寫規格；已改的內容保留、不還原，問答與寫規格期間不再繼續修改，併進新規格的實作計畫。
- 規格核准後（實作回報、實作審查）：不補做問答，之後的新決定照「新的決定一律回到決策樹」。

標準升級成高風險不重做問答，新的決定照「新的決定一律回到決策樹」。

### 術語表（標準、高風險）

術語表的格式與上面兩條用詞規則改寫自 [mattpocock/skills](https://github.com/mattpocock/skills) 的 `domain-modeling`（`GLOSSARY-FORMAT`，commit `4ae2317`，MIT 授權）。

- 位置：`docs/glossary.md`。第一個術語合併時由 `feature-implementer` 建立，不預先填寫。
- 只收產品領域、使用者看得到的概念（例如「主任務」「子任務」「階段任務」）；不收開發流程的用詞（Context、Frontier、等級、交付清單等，它們定義在 skill 與 `docs/`）。
- 不寫實作細節，不當規格用：行為與驗收條件寫在規格。
- 核准前寫在 scratchpad 的 `<功能>-glossary.md`（只寫這次確定的術語，不含檔頭），核准後照第 2 節「交付清單」合併進 `docs/glossary.md`。

格式（繁體中文）：檔頭是標題與一兩句說明；每個術語一段：粗體名稱、1–2 句定義（寫它是什麼，不寫它做什麼）、`_避免_：` 列出同一個概念不採用的說法；術語自然形成群組時用小標題分組。

```markdown
# 術語表

這個專案的產品用詞：使用者看得到的概念用哪個名稱、指的是什麼。

## <群組名稱（自然形成群組時才加）>

**<術語>**：
<1–2 句定義：它是什麼>
_避免_：<不採用的說法>、<不採用的說法>
```

### 規格內容

- **需求／不做**：要做什麼、明確排除什麼。
- **假設**：程式碼看不出來、由你判斷的事，逐條列出。
  - 輕量：由你判斷的業務規則寫在這裡；只有無法合理假設、而且會影響整體方向的問題才先問。
  - 標準、高風險：只放開發者交給你決定的 Context 項，以及寫規格時另外做的判斷；開發者決定的 Context 項寫進需求、不做或驗收條件。寫規格時碰到需要開發者決定的業務規則，照「新的決定一律回到決策樹」，不寫成假設。
- **驗收條件**：編號 AC1、AC2…，「在 X 情況下，系統要 Y」，每條都要能驗證。逐一想過失敗、空資料、載入中、未登入／無權限、資料處理、安全性；不適用的寫進「不適用的情境」並說明原因。
- **計畫與測試對應**：要改的檔案、步驟、每條驗收條件對應的測試。

**Context 寫進規格**：`<功能>-grill.md` 不 commit，所以核准前 Context 的每一項都要已經寫進規格、ADR 草稿或 `<功能>-glossary.md`（「寫進哪裡」是「術語表」的項目）：

- 交給開發者核准前，逐項對照：每一項都在規格、ADR 草稿或 `<功能>-glossary.md` 裡找得到，驗收條件和它不矛盾；開發者決定、會影響實作的項目寫在需求、不做或 AC，不寫成「假設」。落點是術語表的項目，在 `<功能>-glossary.md` 找得到就算，不要求再寫進規格。
- 屬於重大架構決策（定義見第 3 節）的，核准前寫成 scratchpad 的 ADR 草稿 `<功能>-adr-<名稱>.md`，和規格一起核准；核准後照第 2 節「交付清單」交給 `feature-implementer` 存進 `docs/decisions/`。
- 規格與 ADR 草稿不寫 C、Q 編號（見「Context 與 Frontier」）。

**規格審查**：文字修正以外的等級，草稿寫好、交給開發者核准前，把草稿 `<功能>-spec.md` 的路徑、等級、`<功能>-grill.md` 的路徑，以及 ADR 草稿、`<功能>-glossary.md` 的路徑（有的話）交給 `specification-reviewer`。依每項發現處理：

| 發現 | 處理 |
|---|---|
| Factual Error（修正不改變行為） | 依依據直接改草稿 |
| Factual Error（修正會改變行為）、Specification Defect、Missing Acceptance Criteria | 涉及產品行為、權限、安全性、資料處理或架構的，照第 3 節「規格問題的處理」第 2 步問開發者；其他的改草稿，在交給開發者時列出 |
| Improvement Suggestion | 列在交給開發者的訊息裡，由開發者決定要不要採用；規格還沒核准，不開 issue |

- 標準、高風險：為了處理發現而新增或改寫驗收條件時，再審查 1 輪，附上第 1 輪報告在 scratchpad 的路徑；第 2 輪還有阻擋的項目，就整理好問開發者，不繼續自動審查。
- 輕量只審 1 輪。第 1 輪後新增或改寫的驗收條件（包括開發者要求的修改），在規格審查紀錄標成「未經審查」，由實作後的 `acceptance-reviewer` 補做事實查證、一致性與情境檢查。新增或改寫涉及新的需求、架構決策或重大的設計取捨時，升級成標準，跑第 2 輪規格審查；只是把文字寫清楚、意思不變，不升級。
- 處理發現時開發者做的新決定，一樣編成 Context 項寫進 `<功能>-grill.md` 並對照規格；標準、高風險照「新的決定一律回到決策樹」。
- 交給開發者核准時，規格之外再附上規格審查的摘要：改了什麼、還需要開發者決定什麼、有哪些不採用的建議、輕量的未經審查驗收條件；以及 Context 的對照結果（每一項寫在規格、ADR 草稿或術語表的哪裡）。
- 每一輪的報告原文存在 scratchpad。照 `docs/reviews/README.md`「紀錄檔格式」把各輪的結果整理在 scratchpad 的 `<功能>-spec-review.md`，寫上每一項的處理方式與決定者；`feature-implementer` 回報 PR 已建立後，照第 2 節「審查紀錄的 commit」存成 `docs/reviews/specification/<功能>.md` 並 commit。

開發者要求修改時，更新整份規格再交一次，直到開發者明確核准；修改只動到措辭、沒有新增或改寫驗收條件時，不必重新審查；輕量照上面「規格審查」的未經審查規則，不另外跑一輪。核准後在 scratchpad 把規格的狀態改為「已核准」，照第 2 節「交付清單」交給 `feature-implementer` 存成 `docs/specs/<功能>.md`；主 session 不自己把規格、ADR、術語表寫進工作目錄。

## 2. 實作（核准後自動進行，不再中途詢問）

**Commit 責任**：依文件種類分清楚由誰 commit。

| 種類 | 檔案 | 誰寫內容 | 誰 commit、push |
|---|---|---|---|
| 產品文件 | 規格（`docs/specs/`）、ADR（`docs/decisions/`）、術語表（`docs/glossary.md`） | 主 session（核准前在 scratchpad） | `feature-implementer`，照交付清單 |
| 審查紀錄 | 規格審查紀錄（`docs/reviews/specification/`）、實作審查紀錄（`docs/reviews/implementation/`） | 主 session | 主 session，commit 後 push 到同一個 PR 分支（見下面「審查紀錄的 commit」） |
| 程式碼與測試 | 其他 | `feature-implementer` | `feature-implementer` |

文字修正沒有 `feature-implementer`，照第 1 節「文字修正的流程」自己 commit。

**交付清單**：交給 `feature-implementer` 產品文件時附上，列出每個檔案的 repo 路徑與 scratchpad 來源；術語表另外列出術語，分成「新增」與「修改既有定義（開發者已確認）」，修改要寫術語名稱、原定義與新定義：

```
交付清單：
- `docs/specs/<功能>.md` ← <scratchpad>/<功能>-spec.md
- `docs/decisions/NNNN-<名稱>.md` ← <scratchpad>/<功能>-adr-<名稱>.md（沒有寫「無」）
- `docs/glossary.md` ← <scratchpad>/<功能>-glossary.md（沒有寫「無」）
  - 新增：<名稱>、<名稱>（沒有寫「無」）
  - 修改既有定義（開發者已確認）：<名稱>；原定義：<origin/main 上的定義>；新定義：<新定義>（沒有寫「無」）
```

新增的術語，`feature-implementer` 對照 `origin/main`，有相同或相近的術語就停下來回報；修改既有定義的術語，它確認 `origin/main` 上的定義和原定義一致才修改，不一致就停下來回報。

用在兩個時間點：

- 核准後第一次交辦：交付前在 scratchpad 把規格狀態改成「已核准」，再把交付清單和分支名稱交給 `feature-implementer`。主 session 不自己把規格、ADR、術語表寫進工作目錄。
- 核准後修改規格、ADR、術語表（第 3 節「規格問題的處理」「核准後修改規格」、核准後的重大架構決策、核准後才確定或修改的術語）：先改 scratchpad 的來源檔，同樣整理交付清單交辦，列出這次改了哪些檔案、哪些術語。

**審查紀錄的 commit**：只限目前 feature 的 PR 分支與這次的 `docs/reviews/` 紀錄檔（規格審查、實作審查）。

1. commit 前確認目前分支是這次的 PR 分支，並看 `git status`。
2. 只用 `git add <這次的紀錄檔路徑>`，不帶其他未提交的修改，不用 `git add -A`、`git add .`。
3. commit 後 push 到同一個 PR 分支，再 `gh pr checks <PR> --watch` 等 CI。
4. 分支或檔案的歸屬無法確認時停止，用「需求問答」的格式問開發者。

時機：規格審查紀錄在 `feature-implementer` 回報 PR 已建立之後、交給 `acceptance-reviewer` 之前 commit（從 `<功能>-spec-review.md` 存成 `docs/reviews/specification/<功能>.md`，「PR」補上編號）；實作審查紀錄見第 3 節「每一輪都更新紀錄檔」。

- 交給 `feature-implementer`，附上交付清單和分支名稱。
- 它建立 PR 後會把規格開頭的「PR」補上編號、commit、push，並回報 PR 編號。收到後，以 PR 分支上已 commit 的規格為準，同步更新 scratchpad 的 `<功能>-spec.md`，之後的交付清單才不會把 PR 編號蓋回去。
- 它回報規格有問題時：先依 `docs/reviews/README.md`「分類」判斷是哪一類；會影響範圍或驗收條件就照第 3 節「規格問題的處理」；不影響就直接回覆它怎麼做。
- 它因為「術語重複或衝突」「工作目錄有歸屬不明的改動」停下來回報時：用第 1 節「需求問答」的格式問開發者；術語的決定照「新的決定一律回到決策樹」；開發者決定修改既有定義時，在交付清單把該術語改標成「修改既有定義（開發者已確認）」，寫上原定義與新定義，再交辦。
- 它回報的「發現但沒處理的問題」，照第 3 節「不阻擋的發現開 issue」處理；是「漏洞」的照「漏洞的處理」。

## 3. 審查

交給 `acceptance-reviewer` 前先 `git fetch origin main`，確認規格審查紀錄已照第 2 節「審查紀錄的 commit」commit、push，附上規格檔路徑、等級、分支名稱、規格審查紀錄的路徑（`docs/reviews/specification/<功能>.md`）與 PR 描述全文（`gh api repos/{owner}/{repo}/pulls/<PR> --jq .body`）；第 2 輪以後再附上實作審查紀錄的路徑（`docs/reviews/implementation/<功能>.md`）。

分類的定義見 `docs/reviews/README.md`「分類」。依每項發現處理：

| 發現 | 處理 |
|---|---|
| 「涉及安全／架構」標成「漏洞」（不論分類） | **一律阻擋**。照下面「漏洞的處理」暫停並回報開發者，不交給實作、不開 issue |
| Implementation Defect（不涉及安全） | 交回 `feature-implementer` 修正 |
| Implementation Defect 標成「安全」 | 暫停，照「規格問題的處理」問開發者，不自動修正 |
| Test Gap（阻擋） | 交回 `feature-implementer` 補測試 |
| Factual Error、Specification Defect、Missing Acceptance Criteria | 暫停，照下面「規格問題的處理」 |
| Test Gap（不阻擋）、Improvement Suggestion（包括標成「安全」的改善建議） | 照下面「不阻擋的發現開 issue」處理，不在這個 PR 修；開發者明確要求在這個 PR 處理時才修：先照「規格問題的處理」第 3 步寫成驗收條件，再交給 `feature-implementer`，並在處理結果記下決定者 |

任何一項涉及**重大架構決策**（新增服務或外部依賴、改變模組分層、改資料庫結構或部署方式；改資料庫結構指新增 collection 或索引、改既有欄位的型別或意義、要轉換既有資料，新增選填欄位不算），不論分類都暫停，照「規格問題的處理」問開發者；決定後寫成 scratchpad 的 ADR 草稿，照第 2 節「交付清單」交給 `feature-implementer` 存進 `docs/decisions/`。

**規格問題的處理：**

1. 整理每一項：分類、問題的情境、影響範圍（哪些檔案、哪些既有驗收條件）、建議的驗收條件與理由。
2. 用第 1 節「需求問答」的格式問開發者，並請開發者決定要在這個 PR 補上，還是另開 issue；決定編成 Context 項，標準、高風險照「新的決定一律回到決策樹」。涉及產品行為、權限、安全性、資料處理或架構時，先列出選項與各自的影響，最後附上建議與理由，標明「需要你選擇」：開發者要選定其中一個選項（或另外說明），只回「是」不算；其他的（包括依查證依據修正、不改變行為的 Factual Error）可以附上建議的驗收條件，讓開發者一次確認：規格已經核准，修改都要開發者確認。
3. 這個 PR 補：先做下面「核准後修改規格」的影響檢查，把確認後的驗收條件寫進 scratchpad 的規格，照第 2 節「交付清單」交給 `feature-implementer` 更新規格、實作並補測試。
4. 另開 issue：用 `gh issue create` 記下缺漏與建議的驗收條件，在規格的「修改紀錄」（照第 2 節「交付清單」交給 `feature-implementer`）與 PR 描述附上連結，這項就解除阻擋。

**停下來問開發者時，一起整理不阻擋的發現：** 這一輪已經因為上面任何一項暫停時，同一則訊息分成「需要你決定」與「不阻擋（預設開 issue，可以改成在這個 PR 修）」兩區，開發者回答後才照下面的規則開 issue。這一輪沒有暫停時，不阻擋的發現直接開 issue。

**核准後修改規格：** 寫進「修改紀錄」之前，先列出這次修改會影響到的其他驗收條件、假設、實作計畫與測試對應，一起更新或確認不用改。「修改紀錄」的「原因」寫：決定的內容（一句話）＋落點（規格的節或 AC 編號、ADR 編號，或「術語表」）＋檢查過哪些，例如「開發者決定輕量也要問答 → AC3；檢查過 AC1、AC4 不用改」。有規格的等級（輕量、標準、高風險）都照這個寫，不寫 C 編號（見第 1 節「Context 與 Frontier」）。

**不阻擋的發現開 issue：**

1. 先查重複：`gh issue list --state all --search "<關鍵字>"`。已有相同問題時，在既有 issue 留言補充（`gh issue comment`），不另開。
2. 一項發現一個 issue；同一個檔案、同一個原因的多項發現合併成一個。
3. 內容照 `docs/issues.md`：先寫受影響的人遇到的情境，再寫技術背景、依據（`檔案:行號`）、審查的建議，最後附來源 PR 的連結與審查紀錄的檔案路徑（`docs/reviews/implementation/<名稱>.md`；不要用分支上的檔案連結，分支刪除後會失效）。開之前（包括在既有 issue 留言）確認內容沒有指向 Context／Frontier 項的 C、Q 編號（見第 1 節「Context 與 Frontier」）。
4. 標籤：程式行為不正確（包括原本就有的問題）用 `bug`，其餘（測試補強、可讀性、文件）用 `enhancement`。不加優先度，交給 `/issue-triage`。
5. 在審查紀錄「發現與處理」的「結果」欄寫上 issue 連結。

**漏洞的處理：**

這個 repo 是公開的。「漏洞」是可被利用的程式漏洞；「安全」是安全相關的改善或規格、流程缺漏，不是漏洞，照上表處理、內容可以公開。這裡只定義安全邊界，不定義漏洞的修復與發布流程。

1. 暫停目前的開發流程，不再交給 `feature-implementer` 任何修正，把漏洞的細節只寫在給開發者的回報裡。
2. 開發者決定處理方式前，漏洞的位置與利用方式不能出現在任何公開的地方：issue、PR 描述、commit 訊息、程式註解、規格檔、測試名稱與 docstring、`docs/reviews/`；也不能把修正推送到公開的 repo（包括這個 PR 的分支）。
3. 可以提出建立 private security advisory 的方案（附上要填的內容），開發者確認後才建立：
   1. 先查重複：`gh api --paginate repos/{owner}/{repo}/security-advisories --jq '.[] | {ghsa_id, summary, state}'`。已有相同問題時沿用它的 GHSA 編號，需要補充時 `gh api -X PATCH repos/{owner}/{repo}/security-advisories/<GHSA> --input <檔案>` 更新 description，不另建。
   2. 建立草稿 advisory（只有 repo 管理者看得到）：把下面的 JSON 寫進暫存檔（放 scratchpad，不放 repo），再 `gh api -X POST repos/{owner}/{repo}/security-advisories --input <檔案>`。
      ```json
      {
        "summary": "<一句話>",
        "description": "現象、影響範圍、依據（檔案:行號）、建議的修法、來源 PR",
        "severity": "low | medium | high | critical",
        "vulnerabilities": [{"package": {"ecosystem": "other", "name": "auto-scheduling-system"}}]
      }
      ```
   3. 建立失敗時，不要改開公開 issue，停下來問開發者。
4. 之後照開發者決定的方式處理；開發者決定前，這一項維持阻擋，不能讓 PR 以「沒有阻擋」結束。

**審查紀錄與重新審查：**

- 寫進紀錄檔前檢查**整份報告**（Summary、Problem Details、Technical Evidence 的每一張表），所有提到「漏洞」位置或利用方式的地方，都改寫成一般性的描述（或開發者確認建立後的 advisory 編號）。scratchpad 裡的報告原文不 commit。
- 重新審查時，reviewer 只看得到改寫過的紀錄：主 session 把原始內容直接寫進給 reviewer 的指示，不存檔。

**每一輪都更新紀錄檔**：審查完把報告原文存在 scratchpad，再照 `docs/reviews/README.md`「紀錄檔格式」更新 `docs/reviews/implementation/<功能>.md`（「漏洞」的內容照上面改寫）；每一項處理完，在「發現與處理」寫下處理方式、決定者、根本原因與 commit / issue / advisory 編號。每一輪整理完就照第 2 節「審查紀錄的 commit」commit 並 push 到 PR 分支，最後一輪沒有修正時也一樣；交回 `feature-implementer` 修正前必須已經 commit、push，否則它會把紀錄檔當成歸屬不明的改動。

**輪數依根本原因計算：** 修正後重新審查，直到沒有阻擋的項目為止。每一項阻擋的發現在紀錄檔的「根本原因」欄標上根本原因（一個簡短的名稱）；之後的發現出自同一個根本原因時沿用同一個名稱並累計，不因為改了不同的驗收條件或規格版本而重新計算。同一個根本原因連續 3 輪都還有阻擋時，停止自動修改，整理具體原因問開發者；不得自行重置輪數。

**限制：**

- 不可把 agent 推測的行為當成已確認的需求；開發者確認前，不寫進規格的驗收條件。
- 不可因為發現缺漏就擴大範圍：只做開發者確認過要在這個 PR 補上的部分。
- 不可只改程式而不改規格：每項修正都要對應到規格裡的驗收條件。
- 不可合併 PR：合併一律由開發者決定。

## 4. 回報

PR 連結、等級、驗收表（驗收條件 → 對應的測試 → 結果）、假設清單、規格修改紀錄、規格審查與實作審查紀錄的檔案連結與阻擋項目的處理結果、這次開了或留言了哪些 issue、建立或沿用了哪些 advisory（只寫編號）。給開發者看的回報要附上檔案與測試的連結（`檔案:行號`），不要只寫摘要。PR 描述放同一張驗收表；更新 PR 描述照 CLAUDE.md「開發流程」的方式。

回報前確認最後一輪的審查紀錄、最後一次審查之後的 commit 訊息（`git log`）與最終的 PR 描述，沒有指向 Context／Frontier 項的 C、Q 編號（見第 1 節「Context 與 Frontier」）：這些在最後一次審查之後才產生，`acceptance-reviewer` 沒有看過。

回報的最後列出**目前所有 open 的 PR** 能不能由開發者決定合併，不只這次的 PR：別的 PR 可能因為這次合併而解開（例如等這個 PR 修好 CI），或因為 main 前進而出現衝突。用 `gh pr list --state open`、`gh pr checks <PR>`、`git merge-tree --write-tree origin/main origin/<分支>`（先 `git fetch origin`）逐一確認，分兩區：

- **可以決定要不要合併**：必要的 CI 都通過、和 `main` 沒有衝突、實作審查沒有阻擋項目（沒有審查紀錄的寫「沒有審查」）。
- **還不行**：寫出原因與下一步，例如 CI 失敗、和 `main` 衝突的檔案、仍有阻擋的項目、要等哪個 PR 先合併。

**清理暫存**（`docs/README.md`「生命週期」）：回報前確認 scratchpad 裡已確認的內容（規格、Context、術語、審查結果）都已經在規格、審查紀錄、ADR 或術語表裡（「寫進哪裡」是「術語表」的 Context 項，在 `docs/glossary.md` 找得到就算）；文字修正沒有規格與審查紀錄，對照 PR 的改動與描述；還沒做完的後續動作（例如合併後要在 issue 留言），列在回報的「待辦」，不要只留在 scratchpad。

**取消**：核准前開發者表示不做時，列出 `<功能>-glossary.md` 的術語（有的話），用「需求問答」的格式請開發者決定保留或不保留。保留：另外照第 1 節「文字修正的流程」開 PR，只改 `docs/glossary.md`；開 PR 前同樣 `git fetch origin main`，對照 `origin/main` 的 `docs/glossary.md` 有沒有相同或相近的術語，有的話問開發者。核准後 PR 被關閉時不另外處理：改動只在分支上。

**暫停與接續**：暫停時 scratchpad 保留，告訴開發者 scratchpad 的路徑。接續時請開發者提供舊路徑，把舊 scratchpad 裡這次開發的全部暫存檔（`<功能>-` 開頭：Context／Frontier、術語、規格草稿、規格審查紀錄草稿、ADR 草稿、各輪審查報告原文）複製到新的 scratchpad，C、Q 編號接續。舊路徑不存在時告訴開發者，依規格是否已核准處理：

- 核准前：標準、高風險從需求問答重新開始；輕量從寫規格草稿重新開始。
- 核准後：先 `git fetch`，確認 PR 分支的最新狀態，把 PR 分支上最新的規格、術語表、相關 ADR、審查紀錄直接複製到新的 scratchpad（規格存成 `<功能>-spec.md`），建立新的工作上下文；不依記憶重新產生或改寫。C、Q 從 1 重新編號。正式文件仍以 PR 分支為準。
