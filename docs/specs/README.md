# 功能規格

- 每個變更一份：`/feature` 的檔名是 `<功能>.md`，`/issue` 的是 `issue-<N>-<簡短名稱>.md`。
- 文字修正不寫規格；快速路徑的短版規格放在 PR 描述（見「快速路徑的短版規格」）。
- 核准前寫在草稿資料夾（`.drafts/<功能>-spec.md`），核准後才存進這裡，和實作同一個 PR。
- 規格是實作 agent 唯一的需求來源，要寫到不看討論過程也能照著做。

照 `CLAUDE.md`「寫作規則」寫；流程用語見 `docs/README.md`「流程用語」。

## 規格和目前系統的關係

規格記錄核准時的需求，合併後不跟著程式更新；目前的行為以程式碼、[api.md](../api.md)、[architecture.md](../architecture.md) 為準。之後的變更改了它定義的行為時：

- 寫在新的規格裡。
- 在新規格的 PR 把舊規格的「狀態」改成「已被 [<新規格>](<檔名>.md) 取代」，只取代一部分時寫「部分被 [<新規格>](<檔名>.md) 取代（AC3、AC5）」。其他內容不改。

## 格式

```markdown
# <功能名稱>

- 狀態：草稿 | 已核准 | 已被 [<規格>](<檔名>.md) 取代 | 部分被 [<規格>](<檔名>.md) 取代（AC…）
- 等級：一般 | 高風險（理由）
- 規格審查：有 | 沒有（理由）
- issue：#NN（由 `/issue` 開發時）
- PR：#NN

## 簡短說明
這份規格要解決什麼，一兩句話。範圍可能太大時，在「請你決定」建議拆成幾份。

## 背景
先用一兩句寫出問題，再用實際案例說明。由 issue 來的規格，先附 issue 連結。

## 需求
要做什麼，逐條編號，一條只講一件事。

## 不做
明確排除的範圍，以及刻意不處理的情況與原因。

## 假設
程式碼看不出來、由主 session 判斷或開發者交給主 session 決定的事，逐條編號。

## 驗收條件
| # | 需求 | 條件 |
|---|---|---|
| AC1 | 1 | 在 X 情況下，做 Y，結果是 Z |

## 實作計畫
要改的檔案、步驟、為什麼這樣做。高風險另外寫考慮過、沒選的做法與理由；有 ADR 時附連結。

## 測試對應
| AC | 測試或驗證步驟 | 預期結果 |
|---|---|---|

## 修改紀錄
| 日期 | 修改 | 原因 | 確認者 |
|---|---|---|---|

## 請你決定
要開發者決定的事，一項一條。核准前全部回答完，答案寫進需求、不做或驗收條件，這一節改寫「無」。
```

| 等級 | 必要的節 |
|---|---|
| 高風險 | 全部 |
| 一般 | 全部；沒有內容的「不做」「假設」可以省略 |

## 驗收條件怎麼寫

issue 的「建議的驗收條件」也照這裡寫。

- 每條寫出必須達成的結果：在什麼情況下、做了什麼、結果是什麼。
- 每條只講一件事。出現「而且」「以及」就考慮拆開。
- 每條標出對應的需求編號，依需求分組排列，才看得出每條需求有沒有被涵蓋。
- 依需求的性質選方法推導，不套固定清單：固定清單容易漏掉需求本身才有的情況（例如某個欄位的上限）。

  | 需求的性質 | 方法 | 要寫出的 AC |
  |---|---|---|
  | 輸入驗證、數值範圍 | 等價類、邊界值 | 每個欄位的合法最小值與最大值、剛好超出的值、型別錯誤 |
  | 多步驟流程、畫面狀態 | 狀態轉換 | 每個狀態下的每個操作會走到哪裡，包括返回、取消、失敗 |
  | 多個條件一起決定結果 | 決策表 | 每種條件組合的結果 |
  | 其他 | 正常與異常流程 | 成功時、失敗時的結果 |

- 涉及資料一致性、權限、同時操作、外部系統時，加上不變條件（例如資料庫和 Google Calendar 的事件一致、只動得到自己的資料）：只看畫面的 AC，錯的實作也能通過。
- 寫完再想一次：失敗、空資料、沒登入或沒權限、同時操作，以及和既有規則（例如排程規則、刪除行為）交會的地方有沒有漏。和這次需求無關的不寫。
- 每條都要能驗證：寫出對應的測試，或手動驗證的步驟與預期結果。
- 不寫和需求無關的技術細節，例如指定實作方式、沒有人會碰到的防禦情境。
- 清理、轉換這類結果，「測試對應」寫出完整的預期輸出，不只寫「不含某某」。

## 修 bug 時

照一般的格式，另外：

- **背景**：寫重現步驟、預期與實際的結果，以及根本原因（附 `檔案:行號`）。
- **AC1**：照重現步驟操作，錯誤不會出現。
- **其他 AC**：這次修正不能弄壞的既有行為（有的話）。
- **測試對應**：加一欄「改程式前是否失敗」。AC1 的測試改程式前必須失敗，才證明它重現了 bug。

## 快速路徑的短版規格

條件見 `/feature`「快速路徑」。放在 PR 描述，不存進這裡。

```markdown
# <功能名稱>

- 等級：一般（快速路徑：<符合條件的理由>）
- issue：#NN（由 `/issue` 開發時）

## 背景
現在的結果與預期的結果。修 bug 時另外寫重現步驟與原因（附 `檔案:行號`）。

## 驗收條件
| # | 條件 |
|---|---|

## 修法
一兩行。

## 測試對應
| AC | 測試或驗證步驟 | 預期結果 |
|---|---|---|
```

- 驗收條件照「驗收條件怎麼寫」，但沒有需求編號。
- 修 bug 時照「修 bug 時」的 AC1 與「改程式前是否失敗」欄。
- 短版規格核准後不修改：要改驗收條件時，改走完整流程（見 `/feature`「快速路徑」）。

## 核准後

驗收條件的任何新增、修改、刪除都記在「修改紀錄」，由開發者確認。「原因」寫一句決定的內容、寫在哪裡（AC 編號、ADR 或術語表），以及檢查過哪些，例如「開發者決定一般等級也要問答 → AC3；檢查過 AC1、AC4 不用改」。
