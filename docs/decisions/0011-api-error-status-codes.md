# 0011. API 錯誤回應：狀態碼表示類別，error_code 表示原因

- 狀態：已採用
- 日期：2026-11-10

## 背景

全站 API 的狀態碼是各功能各自決定的。同一個狀態碼代表不同的意思，前端又只看狀態碼判斷畫面，結果顯示錯的畫面：

- 400 同時代表「尚未連接帳號」和「外部服務回了 4xx」，前端把所有 400 都當成未連接（issue #59）。
- 401 在前端代表「第三方憑證失效，要重新連結」，所以本系統沒登入只能回 403，不能照 HTTP 語意回 401。
- 409 同時代表「已經綁定過」和「排程建議已過期」，前端靠畫面所在的位置猜是哪一種。
- 外部服務逾時、限流都歸成 502，部分外部服務的錯誤被歸成 400、401 或 500，監控分不出「該修程式」和「等對方恢復」。

只靠狀態碼，原因的種類比合適的狀態碼多，只能繼續靠慣例分配，沒辦法照語意設計。盤點與分階段的修改計畫見 [docs/specs/issue-62-status-codes.md](../specs/issue-62-status-codes.md)。

## 決定

### 回應格式

- 本後端產生的錯誤回應都是 `{"detail": <給人看的訊息>, "error_code": <原因>}`，包括 `AppError`、router 裡的 `HTTPException`、422、429、500、503，以及未知路由的 404 與不支援的方法 405。`error_code` 用大寫加底線（例如 `NOT_LINKED`）。
- 狀態碼表示錯誤的**類別**（本 API 對呼叫者而言的錯誤性質），`error_code` 表示**具體原因**。前端依 `error_code` 決定畫面；`detail` 只用來顯示，不用來判斷，文字要和 `error_code` 的原因一致。
- 422 的 `detail` 是驗證錯誤的清單，但不帶 `input`，也不帶可能含輸入值的 `ctx`：缺欄位時 `input` 是整個 request body，會把憑證原樣帶回。
- 不經過本後端的回應（Cloud Run 自己回的 429、5xx、504，以及網路錯誤）沒有 `error_code`。前端遇到沒有 `error_code` 的回應時退回依狀態碼處理：429 當成限流，其他顯示通用錯誤。
- 新增錯誤原因時，同時更新下面的對照表。

### 分類原則

- 使用者或呼叫者自己能處理的歸 4xx，外部服務暫時有問題的歸 502、503、504，我方的錯誤（程式、設定）歸 500。
- 401 只用在本系統的登入（Clerk JWT）失敗：token 缺少、格式錯誤、簽章或期限驗證失敗。抓 Clerk 公鑰（JWKS）失敗是外部服務的問題，歸 502 或 504。
- 第三方帳號的狀態（未連結、已存的憑證失效）不是呼叫者對本 API 的身分驗證失敗，歸 409：請求和資源目前的狀態衝突。
- 422 是 request 不符合 schema（FastAPI 的預設）；格式正確但違反業務規則是 400。
- **憑證被拒**：
  - 連結或更新帳號時，外部平台拒絕這次驗證用的憑證，一律 400 `INVALID_CREDENTIALS`，包括只改 Jira 網域或 Moodle 帳號、用已存的憑證驗證的情況：使用者正在編輯表單，可以直接修正。
  - `REAUTH_REQUIRED` 只用在拿已存的憑證抓資料時被拒、權限不足，或已存的憑證無法解密。
- **憑證無法解密**：記 warning，不刪已存的憑證：正式與開發環境共用資料庫，可能是另一個環境用自己的金鑰加密的。帳號列表遇到無法解密的帳號時照常回 200，那個帳號不顯示憑證並標示要重新連結，不讓整個清單失敗。
- 外部服務回的狀態碼不照抄，依它對本 API 呼叫者的意義轉換：例如 Google 用 403 加 reason、GitHub 用 403 回報的限流算限流；只有明確的帳密或 token 錯誤才算憑證被拒，其他無法判斷的回應算 `UPSTREAM_ERROR`。
- **安全**：
  - 查別人的資料和查不存在的資料，回一樣的 404 與一樣的訊息。
  - 錯誤回應不帶憑證、token，也不帶第三方回應的原文；原文只記在 log。

### 對照表

| 狀態碼 | error_code | 什麼時候 |
|---|---|---|
| 400 | `INVALID_REQUEST` | 格式正確但違反業務規則（例如階段之間的優先序、時區不合法、沒有可更新的欄位、組合 id 格式錯誤、webhook 的 payload 不是 JSON 或缺欄位）；需要讓前端分辨的規則另外給專屬的 error_code |
| 400 | `INVALID_CREDENTIALS` | 連結或更新帳號時，外部平台拒絕驗證用的憑證 |
| 400 | `INVALID_PLATFORM_DOMAIN` | 連結或更新 Jira 時，網域不存在或回 404 |
| 400 | `INVALID_AUTHORIZATION_CODE` | Google OAuth 授權碼無效或已過期（`invalid_grant`） |
| 401 | `UNAUTHENTICATED` | Clerk JWT 缺少、格式錯誤、簽章或期限驗證失敗 |
| 401 | `INVALID_WEBHOOK_SIGNATURE` | webhook 簽章錯誤，或伺服器沒設定簽章密鑰（見下面「例外」） |
| 401 | `INVALID_SCHEDULER_TOKEN` | 定時同步（`POST /internal/scheduled-sync`）的密鑰錯誤、格式不對，或伺服器沒設定密鑰（見下面「例外」） |
| 404 | `NOT_FOUND` | 本系統的資料不存在或不屬於目前的使用者；未知路由。外部平台回的 404 不用這個 code |
| 405 | `METHOD_NOT_ALLOWED` | 路由存在但不支援這個方法 |
| 409 | `NOT_LINKED` | 需要的第三方帳號還沒連結 |
| 409 | `REAUTH_REQUIRED` | 拿已存的第三方憑證抓資料時被拒、權限不足、已存的 Jira 網域回 404，或已存的憑證無法解密，要重新連結（或到設定確認） |
| 409 | `ALREADY_EXISTS` | 重複建立（使用者已註冊、平台已綁定） |
| 409 | `SUGGESTION_EXPIRED` | 排程建議的快照已過期 |
| 409 | `IDEMPOTENCY_KEY_REUSED` | 同一個 Idempotency-Key 用在不同的請求；重試也不會成功 |
| 409 | `REQUEST_IN_PROGRESS` | 同一個請求還在處理中；稍後重試會成功 |
| 409 | `NO_PRIMARY_CALENDAR` | Google 帳號沒有 primary calendar |
| 422 | `VALIDATION_ERROR` | request 不符合 schema；不回傳輸入值 |
| 429 | `RATE_LIMITED` | 本系統的限流 |
| 500 | `INTERNAL_ERROR` | 未預期的例外、伺服器設定錯誤（例如 Google `invalid_client`），或我方送錯請求導致外部服務回 4xx |
| 502 | `UPSTREAM_ERROR` | 外部服務回 5xx、回應無法解析或缺少必要內容（例如換 token 後沒有 access token）、無法判斷原因的 4xx，或連不上 |
| 503 | `UPSTREAM_RATE_LIMITED` | 外部服務限流；對方有給 `Retry-After` 時一併帶上 |
| 503 | `SERVICE_UNAVAILABLE` | 本系統的依賴（資料庫、Redis）暫時不能用 |
| 504 | `UPSTREAM_TIMEOUT` | 外部服務逾時（包括抓 Clerk JWKS） |

### 例外

- **webhook 沒設定簽章密鑰時回 401**：依分類原則這是我方的設定錯誤（500），但 webhook 的呼叫者是外部服務，回 500 會讓外部知道伺服器漏了設定。維持 401，另外記 error log，由監控發現。
- **定時同步沒設定密鑰時回 401**：理由和 webhook 相同，呼叫者是 GitHub Actions（[ADR 0013](0013-scheduled-sync-trigger.md)），回 500 會讓外部知道伺服器漏了設定。維持 401 `INVALID_SCHEDULER_TOKEN`，啟動時記 error log。

### 過渡期間

依規格分三個階段修改。第一階段先讓每個錯誤回應依**實際原因**帶上 `error_code`，狀態碼維持原本的值，所以這段期間同一個 `error_code` 可能搭配和對照表不同的狀態碼；第二階段才把狀態碼改成對照表的值。前端在第一階段就改成依 `error_code` 判斷，第二階段改狀態碼時不受影響。

例外：

- 帳號列表遇到無法解密的帳號，第一階段就從 500 改成 200：整個清單打不開是使用者會遇到的問題，從錯誤改成成功也不影響前端的相容性。
- 改掉驗證 library 之前，分不出抓 Clerk JWKS 失敗和 token 無效，兩者都帶 `UNAUTHENTICATED`。
- 成功回應帶不了 `error_code`：目前靜默回 200 的情況（例如排程的外部 id 不存在），要等第二階段改成錯誤回應時才有 `error_code`。

## 放棄的做法

- **只靠狀態碼，每種原因分配不同的狀態碼**：原因的種類比合適的狀態碼多，例如「尚未連結」只能挑一個沒用過的碼，不符合 HTTP 語意，等於繼續靠慣例。
- **第三方帳號狀態沿用 400、401**：401 會同時代表本系統沒登入和第三方要重新連結，監控與前端都要再靠 `error_code` 區分，本系統的沒登入也不能回 401。
- **第一階段只有 Bug 類依原因給 `error_code`**：其他照目前的狀態碼給，第二階段改狀態碼時前端要再改一次。
- **更新帳號時用已存的憑證驗證被拒，回 `REAUTH_REQUIRED`**：設定頁要處理兩種被拒，而使用者正在編輯表單，直接修正比重新連結合理。
- **維持現狀，只修 #59 這類明顯的錯誤**：沒有依據可循，新功能會繼續產生不一致。

## 影響

- 決定採用時，程式還沒照這份 ADR 改。改完之前，[docs/api.md](../api.md) 記錄的是目前的行為。
- 前端的錯誤判斷要從狀態碼改成 `error_code`，並為沒有 `error_code` 的回應保留依狀態碼的退回處理。
- 帳號列表的回應（`LinkedAccountOut`）要加一個欄位標示無法解密、要重新連結的帳號，前端型別同步更新。
- 新增 endpoint 或錯誤原因時，照這份 ADR 選狀態碼與 `error_code`，並更新對照表。
