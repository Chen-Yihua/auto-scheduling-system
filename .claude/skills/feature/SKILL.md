# 功能開發流程

需求：$ARGUMENTS

你是提需求、負責驗收的一方，不自己寫程式（文字修正除外）。實作交給 `feature-implementer`，審查交給 `specification-reviewer`（規格）與 `acceptance-reviewer`（實作）。這些 agent 看不到這段對話，所以規格要寫到不看對話也能照著做。

## 流程

| 步驟 | 做什麼 | 先載入 |
|---|---|---|
| 1. 判斷等級 | 讀程式碼，照「判斷等級」 | — |
| 2. 需求確認 | 簡述需求理解、需求問答、工程方案探索 | `clarify-requirements` |
| 3. 規格 | 寫規格草稿、需要時做規格審查、請開發者核准 | `write-spec` |
| 4. 實作與審查 | 交給 agent 實作、審查、處理發現 | `implement-and-review` |
| 5. 回報 | 照「回報」 | — |

開始前，先看草稿資料夾（`.drafts/`）有沒有這次的暫存檔（檔名見 `references/resume.md`「暫存檔表」）。有的話，問開發者要接續還是刪掉重來。這些檔案可能是上次中斷或漏刪留下的，所以開發者回答前，不把內容當成已確認的決定。暫停、接續、暫存檔遺失時讀 `references/resume.md`。

## 硬規則

1. **不用 plan mode**：plan mode 中不能寫檔。開發者在 plan mode 叫出這個流程時，先請開發者退出。
2. **核准前只寫草稿資料夾**：不改 repo 的其他檔案、不開分支。工作目錄是開發者與其他 session 共用的，寫在別處可能被別的 commit 帶走。暫存檔都以 `<功能>-` 開頭，只建立 `references/resume.md` 暫存檔表上的檔案。
3. **核准**：開發者明確說「核准」才算；提出修改、回答問題、沒有回應都不算。
4. **提問**：一律用 `clarify-requirements`「需求問答」的 ❓／➡️ 文字格式，不用 AskUserQuestion。
5. **漏洞**：照 CLAUDE.md「漏洞」。
6. **不合併 PR**：合併由開發者決定。

## 判斷等級

依變更**碰到什麼**判斷，不看改動大小。照順序判斷，符合就停：

1. **高風險**：改變下面任何一項的行為或保證，或屬於「重大架構決策」：
   - 資料一致性：同時操作、中途失敗後的資料狀態、既有資料讀不讀得出來或要不要轉換。
   - 認證與授權：誰動得到哪些資料。
   - 個資、憑證、token 的保護：不出現在 log、回應、公開的地方。
   - 和外部系統同步的一致性與可靠性。
   - 其他安全性，例如輸入驗證、注入。
2. **文字修正**：不改任何程式行為，也不改任何規則。例如 Markdown、註解、錯字，以及不會被執行、也不會被測試讀到的文字。skill、agent、CLAUDE.md 與 `docs/` 的流程說明，只改措辭、規則不變的才算。
3. **一般**：其他。例如 bug、新功能、新增 endpoint、改 request／response 格式、只補測試、改流程規則。

| 等級 | 規格 | 規格審查 | 實作審查 |
|---|---|---|---|
| 高風險 | 完整格式，實作計畫寫放棄的做法 | 一定做 | 直到沒有阻擋；每輪看整個功能 |
| 一般 | 完整格式，沒內容的節可省略；或快速路徑 | 需要時才做（`write-spec`） | 直到沒有阻擋；第 2 輪起只看修正與它的連帶影響 |
| 文字修正 | 不寫，照「文字修正的流程」 | 不做 | 不做 |

- 不確定時取較高的等級。等級和理由寫在規格開頭，和規格一起核准。
- 高風險看的是行為或保證有沒有改變，不是碰到哪個欄位。例如新增選填欄位、舊資料照常讀得出來，不算高風險；改既有欄位的型別或意義、要轉換既有資料，算高風險。
- 重構、套件升級可能改變行為，所以不是文字修正，依實際影響判斷。
- 任何階段發現碰到更高等級的範圍，就升級並告訴開發者，補做該等級的步驟（`clarify-requirements`「升級等級」）。降級要開發者同意。
- 等級只影響規格與審查的深度；CLAUDE.md「完成的定義」、測試要求、開發者核准，每個等級都一樣。

## 快速路徑

需求已經寫清楚時，完整規格和規格審查多出的只是等待，所以一般等級同時符合下面 3 條時，規格階段可以簡化：

1. 需求（issue 或 `/feature` 的參數）已寫清楚現在的結果與預期的結果。
2. 沒有要開發者決定的事（業務規則）。技術判斷由你決定，寫進短版規格的「修法」。
3. 不碰高風險範圍。

做法：

- 把需求理解的簡述和短版規格（`docs/specs/README.md`「快速路徑的短版規格」）放在同一則訊息，請開發者核准一次。規格開頭寫「一般（快速路徑：<理由>）」。
- 不建立 `<功能>-grill.md`，不做規格審查。代價是規格本身的問題要到實作審查才會被發現。
- 短版規格放在 PR 描述，不存進 `docs/specs/`。更新 PR 描述時保留短版規格那一段。
- 核准前發現不符合 3 條的任一條：告訴開發者，改走完整流程。
- 核准後要改短版規格的驗收條件或修法時，照 `implement-and-review`「規格問題的處理」問開發者：
  - 開發者決定在這個 PR 補：改走完整流程（見下方）。
  - 開發者決定另開 issue：留在快速路徑，短版規格不動。

核准後改走完整流程時，照順序做：

1. 以短版規格為基礎寫完整規格，不同的驗收條件記在「修改紀錄」。
2. 照 `write-spec`「什麼時候做規格審查」判斷要不要審查。
3. 請開發者核准。
4. 照 `implement-and-review`「交付清單」交給 `feature-implementer`。
5. 把 PR 描述裡的短版規格換成規格檔的連結。

## 重大架構決策

新增服務或外部依賴、改變模組分層、改資料庫結構（新增 collection 或索引、改既有欄位的型別或意義、轉換既有資料；新增選填欄位不算）、改部署方式。

- 屬於高風險。
- 核准前寫 ADR 草稿 `<功能>-adr-<名稱>.md`（格式見 `docs/decisions/README.md`），和規格一起核准。

## 文字修正的流程

1. 在 `<功能>-spec.md` 寫改動清單：要改的檔案、改前與改後的文字、為什麼屬於文字修正。
2. 請開發者核准。
3. 從 `main` 開分支，自己修改。
4. 跑改到範圍的檢查（只改 `.md` 時不用），開 PR、等 CI。
5. 回報 PR 連結、CI 結果，並照「清理暫存」處理。

- 修改中發現會改變程式行為（包括測試斷言會看到的文字）：停下來告訴開發者，照新的等級補做問答與規格。已改的內容保留，併進新規格的實作計畫。
- 發現和這次無關的問題：照 `implement-and-review`「開 issue 追蹤」判斷要不要開 issue；不開的在回報寫原因。

## 回報

給開發者的回報包括：

- PR 連結、等級。
- 驗收條件 → 測試 → 結果的對照表（文字修正沒有），測試附 `檔案:行號` 連結。PR 描述放同一張表。
- 假設清單、規格的修改紀錄。
- 審查留言的連結，以及阻擋項目的處理結果。
- 這次開了或留言的 issue、建立或沿用的 advisory（只寫編號）。
- 待辦：還沒做完的後續動作，例如合併後要在 issue 留言。

## 清理暫存

回報前，確認草稿資料夾裡已確認的內容（決定、術語、審查結果）都已經寫進規格、PR 描述、審查留言、ADR 或 `docs/glossary.md`。確認完，刪掉這次的暫存檔：只刪暫存檔表列出的確切檔名，不用「`<功能>-` 開頭」比對，免得刪到名稱開頭相同的其他功能。

## 取消

核准前開發者說不做時：

1. 有 `<功能>-glossary.md` 時，列出裡面的術語，問開發者要不要保留。要保留的，照「文字修正的流程」另開 PR 只改 `docs/glossary.md`；開 PR 前先對照 `origin/main` 的 `docs/glossary.md`，有相同或相近的術語就問開發者。
2. 照「清理暫存」刪掉暫存檔。

核准後 PR 被關閉時不用另外處理：改動只在分支上。
