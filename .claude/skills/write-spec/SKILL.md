# 寫規格

> 什麼時候讀：需求確認完成後，到開發者核准規格之前。文字修正不寫規格，見 `feature`「文字修正的流程」。

規格草稿照 `docs/specs/README.md` 的格式寫，放在 scratchpad 的 `<功能>-spec.md`。修 bug 的規格照同一份文件的「修 bug 時」寫。ADR 草稿和規格一起核准，核准後照 `implement-and-review`「交付清單」交給 `feature-implementer` 存進 `docs/decisions/`。

## 規格內容

- **需求／不做**：要做什麼、明確排除什麼。
- **假設**：程式碼看不出來、由你判斷的事，以及開發者明確交給你決定的事，逐條列出；開發者決定的事寫進需求、不做或驗收條件，不寫成假設。無法合理假設、而且會影響整體方向的問題才先問；寫規格時碰到需要開發者決定的業務規則，照 clarify-requirements「新的決定一律回到決策樹」，不寫成假設。
- **驗收條件**：編號 AC1、AC2…，「在 X 情況下，系統要 Y」，每條都要能驗證。逐一想過失敗、空資料、載入中、未登入／無權限、資料處理、安全性；不適用的寫進「不適用的情境」並說明原因。
- **計畫與測試對應**：要改的檔案、步驟、每條驗收條件對應的測試。

## 已確認的決定寫進規格

`<功能>-grill.md` 不 commit，所以交給開發者核准前，逐項對照「已確認」的每一項：都在規格、ADR 草稿或 `<功能>-glossary.md` 裡找得到，驗收條件和它不矛盾；開發者決定、會影響實作的項目寫在需求、不做或 AC，不寫成「假設」。要寫在術語表的項目，在 `<功能>-glossary.md` 找得到就算。屬於重大架構決策（定義見 `feature`「重大架構決策」）的，寫成 ADR 草稿 `<功能>-adr-<名稱>.md`，和規格一起核准。

## 規格審查

文字修正以外的等級，草稿寫好、交給開發者核准前，把草稿 `<功能>-spec.md` 的路徑、等級、`<功能>-grill.md` 的路徑，以及 ADR 草稿、`<功能>-glossary.md` 的路徑（有的話）交給 `specification-reviewer`。

### 處理發現

核准前，規格草稿由主 session 修改：

- 不改變行為的「規格對現有系統的描述和程式不符」：依依據直接改草稿。
- 涉及產品行為、權限、安全性、資料處理或架構的發現（含會改變行為的「規格對現有系統的描述和程式不符」、「規格內容互相矛盾或沒有依據」、「規格沒寫某個情境該怎麼做」）：照 `implement-and-review`「規格問題的處理」第 2 步問開發者。
- 只換說法、意思不變的寫法問題：不阻擋，由寫草稿的主 session 直接改草稿，不開 issue；交給開發者時列出改了哪些。
- 其他的發現：改草稿，在交給開發者時列出。
- 「沒有錯，但可以更好」（上面的寫法問題除外）：列在交給開發者的訊息裡，由開發者決定要不要採用；規格還沒核准，不開 issue。

處理發現時開發者做的新決定，照 `clarify-requirements`「新的決定一律回到決策樹」。

### 審查次數與審查後的修改

- **最多 2 次**：第 1 次完整審查；為了處理發現而新增或改寫驗收條件、假設或設計時，第 2 次只審改過的部分與連帶影響，不重審整份規格。送審時附上：修改內容與原因、受影響的 AC、假設、實作計畫與相關決策，以及第 1 次報告在 scratchpad 的路徑。第 2 次還有阻擋的項目，就整理好問開發者，不繼續自動審查。
- **只改措辭、意思不變**：不需要重新審查；改完確認沒有改變原本的規格意思。
- **開發者要求修改**：改了驗收條件、假設或設計，就再做一次只審改過的部分的審查（不計入上面的 2 次）；修改已影響整體設計方向、原本的審查基準失效時，評估是否需要完整審查。
- 任何修改都先確認影響範圍：不能只看修改的文字或單一 AC，要一併看受影響的其他 AC、假設、實作計畫與測試對應。

### 審查紀錄

每一輪的報告原文存在 scratchpad。照 `docs/reviews/README.md`「紀錄檔格式」把各輪的結果整理在 scratchpad 的 `<功能>-spec-review.md`，寫上每一項的處理方式與決定者；`feature-implementer` 回報 PR 已建立後，照 `implement-and-review`「審查紀錄的 commit」存成 `docs/reviews/specification/<功能>.md` 並 commit。

### 交給開發者核准

訊息附上草稿路徑與審查摘要：改了什麼、還需要開發者決定什麼、有哪些不採用的建議；以及 已確認決定的對照結果（每一項寫在規格、ADR 草稿或術語表的哪裡）。核准的定義見 `feature`「硬規則」。
