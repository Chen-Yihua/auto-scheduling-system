# 暫停、接續與暫存檔遺失

> 什麼時候讀：暫停或接續一次開發、草稿資料夾（`.drafts/`）裡這次的暫存檔遺失時。

## 暫停與接續

暫停與接續時，直接用草稿資料夾裡這次的暫存檔（下面暫存檔表列出的檔名），不用複製。

## 暫存檔遺失時

以遺失了哪個暫存檔為單位處理，不依遺失的時間點：每個暫存檔都由固定的步驟產生，遺失的時間點則列舉不完（`docs/decisions/0010-scratchpad-loss-recovery.md`）。做錯時，已核准的內容可能被推翻或憑記憶重寫，所以照順序做：

1. 先 `git fetch`，到暫存檔表寫的位置找正式版本（repo、本機分支、`origin` 上這次的分支、工作目錄或 GitHub）。找到就以正式版本為準，不憑記憶重新產生；之後要修改時才複製回草稿資料夾。
2. 有部分成果時（例如分支上已改了一部分），逐項標出已完成、未完成、部分完成、待確認；無法確認的標「待確認」，不推定已完成。
3. 告訴開發者依據的來源（分支、commit、有沒有未 commit 的改動），請開發者確認有沒有已確認、但還沒交付或寫進紀錄的項目；沒有依據的項目重新核准後才執行。
4. 找不到正式版本時，用 `clarify-requirements`「需求問答」的格式請開發者選擇重做或不補。已核准的內容重做後要重新核准。不補時，在 PR 描述記錄遺失的項目、影響與不補的決定；規格審查的留言不補時，照 `implement-and-review`「交給 acceptance-reviewer 審查」處理。

重跑審查的發現照 `implement-and-review`「發現處理」；重跑同一次不另計次數。

## 暫存檔表

這張表是暫存檔唯一的清單：只建立表上的暫存檔，開始前的檢查、清理、取消都用這些確切的檔名比對。新增暫存檔時，在表上寫出檔名與正式版本的位置。

| 暫存檔 | 檔名 | 正式版本（找不到時） |
|---|---|---|
| 已確認的決定與待問 | `<功能>-grill.md` | 核准後以規格為準，不重建（核准前：從需求問答重做） |
| 術語 | `<功能>-glossary.md` | PR 分支或 `origin/main` 的 `docs/glossary.md`；要修改時只把要改的條目複製到 `<功能>-glossary.md`，不含檔頭（核准前：重新確認） |
| 規格草稿（文字修正是改動清單） | `<功能>-spec.md` | PR 分支的 `docs/specs/<功能>.md`；快速路徑是 GitHub 上的 PR 描述（`gh api repos/{owner}/{repo}/pulls/<PR> --jq .body`）。都找不到時，已核准的規格請開發者選擇重寫再核准或取消（文字修正的改動清單：請開發者補上項目） |
| ADR 草稿 | `<功能>-adr-<名稱>.md` | PR 分支的 `docs/decisions/`（沒有時重寫，和規格一起重新核准） |
| 審查報告原文 | `<功能>-spec-review-r<N>.md`、`<功能>-impl-review-r<N>.md`（N 是第幾輪） | 已貼出的看 PR 留言（`gh pr view <PR> --json comments`）；還沒貼出的請開發者選擇重跑或不補 |
| 改寫漏洞細節的留言（只在有漏洞時） | `<功能>-spec-review-r<N>-comment.md`、`<功能>-impl-review-r<N>-comment.md` | PR 留言，不重建 |
| 上一版規格 | `<功能>-spec-v<N>.md` | 只給第 2 次規格審查比對用，不恢復；遺失時只附修改內容與原因 |
| advisory 的內容 | `<功能>-advisory.json` | GitHub 上的 advisory（用 GHSA 編號讀回），不重建 |
| PR 描述 | `<功能>-pr-body.md` | GitHub 上的 PR 描述，不重建 |
