# 審查紀錄

兩種審查共用這份文件的分類、報告格式與紀錄格式。`<功能>` 和 `docs/specs/` 裡的規格檔同名：

| 審查 | agent | 時機 | 紀錄檔 |
|---|---|---|---|
| 規格審查 | `specification-reviewer` | 規格核准前 | `specification/<功能>.md` |
| 實作審查 | `acceptance-reviewer` | 實作完成後 | `implementation/<功能>.md` |

- 一個功能的一種審查只有一份紀錄檔，保存每一輪的重要發現與這一輪帶來的改變，以及最終結果：發現的問題、分類與嚴重程度、是否阻擋、開發者決策與理由、處理方式、最終修正結果、尚未處理的項目。每一輪的完整報告只存在主 session 的 scratchpad，不 commit。
- 每一輪審查完就更新紀錄檔：加上新的發現與這一輪的摘要，更新處理結果與輪數，由主 session commit 並 push 到同一個 PR 分支（時機與範圍見 `/feature` 第 2 節「審查紀錄的 commit」），中途中斷也不會遺失已做的決定。前幾輪的內容不覆蓋，處理方式在之後的輪改變時，接著寫（例如「第 1 輪：改 AC3；第 2 輪：改做法後不適用」）。
- 等級是「文字修正」的變更不審查，沒有紀錄檔；輕量的規格審查只有 1 輪，之後新增或改寫的驗收條件在紀錄檔標成「未經審查」（規則見 `/feature` 第 1 節「判斷等級」與「規格審查」）。
- 紀錄檔永久保存，生命週期見 [docs/README.md](../README.md)「生命週期」。
- 審查 agent 只能讀、不能寫檔，所以由主 session 整理報告寫進紀錄檔。標成「漏洞」的內容是例外：repo 是公開的，寫進紀錄檔前照 `/feature` 的「漏洞的處理」改寫成一般性的描述（或開發者確認建立後的 advisory 編號）。
- `docs/reviews/` 底下的 `*-round<N>.md` 是改成這個格式前的逐輪紀錄。GitHub issue 與實驗紀錄引用了這些路徑，所以保留原樣，不搬移也不改寫。

## 分類

每項發現分開判斷下面五件事，不互相推導：類型看根本原因，嚴重程度看影響，阻擋看類型的規則。例如 Factual Error 即使是 Minor 也阻擋；和這次功能無關、main 上原本就有的資料遺失問題是 Critical，但屬於 Improvement Suggestion，不阻擋。

### 問題類型

依**根本原因**分類，不看問題表面的描述：先問「照規格正確實作，問題還在嗎？」，還在就是規格的問題（前三類），不在就是實作或測試的問題。

| 類型 | 定義 | 阻擋合併 |
|---|---|---|
| Factual Error | 規格對**現有**系統的描述和程式碼、文件不符，例如既有 API 的狀態碼、既有的排程規則 | 是（核准後的修正仍要開發者確認） |
| Specification Defect | 規格內部有問題：AC 之間、AC 與假設之間互相矛盾；假設沒有依據；照規格做，會讓另一條 AC 在某些條件下不成立；或等級判斷偏低（例如標成輕量，卻改變了既有資料的讀取或權限） | 是 |
| Missing Acceptance Criteria（Missing AC） | 需求範圍內的某個情境，規格沒有定義行為 | 是（開發者決定另開 issue 才解除） |
| Implementation Defect | 規格正確，程式和規格不符 | 是 |
| Test Gap | 測試不足 | 測的是某條驗收條件，而且錯的實作也會通過 → 是；其他 → 否 |
| Improvement Suggestion | 所有驗收條件都成立，只是可以更好；包括和這次功能無關、原本就有的問題 | 否 |

- 只要會讓某條驗收條件在某個條件下不成立（例如同時操作、中途失敗），就不是 Improvement Suggestion，要依根本原因歸到 Specification Defect、Missing AC 或 Implementation Defect。
- 修正 Factual Error 會改變行為（不只是改文字）時，改列 Specification Defect，由開發者決定。
- 規格審查不審實作，所以不會出現 Implementation Defect 和 Test Gap。

### 嚴重程度

| 嚴重程度 | 定義 |
|---|---|
| Critical | 會造成資料錯誤或遺失、權限或安全問題，或主要流程無法使用 |
| Major | 使用者在一般操作下會遇到的錯誤或缺漏，但有替代做法；或某條驗收條件在特定條件下不成立 |
| Minor | 少見的邊緣情境、訊息文字、操作細節；不影響行為、但違反規格或專案規則的改動 |
| Info | 不影響任何行為與驗收條件：可讀性、文件補充、供參考的觀察 |

Critical／Major／Minor 和 `docs/experiments/feature-grill/README.md` 計算 Missing AC 時用的定義相同。

### 涉及安全／架構

不論類型，另外標一欄：

- 「漏洞」：實際可被利用的程式漏洞。「阻擋合併」一律是「是」。
- 「安全」：安全相關的改善建議，或規格、流程、文件的安全缺漏；不是可被利用的漏洞。
- 「架構」：重大架構影響（新增服務或外部依賴、改變模組分層、改資料庫結構或部署方式）。「改資料庫結構」的範圍見 `/feature` 第 3 節。
- 「否」。

### 開發者決策

reviewer 依發現的內容提出判斷，主 session 照 `/feature` 的處理表執行：

| 值 | 什麼時候 |
|---|---|
| 需要選擇 | 涉及未定義的產品行為、權限、安全性、資料處理或架構。列出選項與各自的影響，附上建議；開發者要選定一個選項，只回「是」不算 |
| 需要確認 | 要改規格（核准後的規格修改都要開發者確認），或要開發者決定在這個 PR 處理還是另開 issue，但不涉及上一列的五項 |
| 否 | 依規則處理：交回實作修正、依查證依據修正、不阻擋的發現開 issue |

### 確定程度

| 值 | 什麼時候 |
|---|---|
| 已驗證 | 跑過測試或指令看到結果，或讀到直接決定這個行為的程式碼 |
| 推論 | 依程式碼推斷，沒有實際重現；寫出推斷的步驟，以及為什麼沒有實際驗證 |
| 待確認 | 找不到依據，需要開發者或其他資訊確認 |

不要把推論或待確認的內容寫成確定的事實。

## 報告格式

兩種 reviewer 的報告都用這個結構。讀者是之後沒看過這次對話、也不熟悉這段程式碼的人：先用使用者的操作與結果說明問題，技術細節放在後面。依據一律寫 `檔案:行號`，引用規格時寫 AC 或假設的編號，不要寫「上面提到的」「這次對話裡」這類只有當下看得懂的說法。

````markdown
## Summary（摘要）

- 發現：N 項（Critical N／Major N／Minor N／Info N）
- 阻擋合併：N 項（#1、#3）
- 需要開發者決策：N 項（#3：需要選擇）
- 主要風險：一到三句，用使用者的操作與結果描述，不用函式名稱
- 建議優先處理：#1 → #3 → …，各附一句理由

| # | 標題 | 類型 | 嚴重程度 | 阻擋合併 | 開發者決策 | 涉及安全／架構 | 確定程度 |
|---|---|---|---|---|---|---|---|

沒有發現時寫「沒有發現」，只留這一節和 Technical Evidence。

## Problem Details（問題說明）

每項發現都要寫，順序和 Summary 的表相同；Info 的項目也一樣，只是可以每點寫得比較短。

### #1 <一句話標題>

1. **問題**：發生了什麼，用一兩句話說明。
2. **情境**：在什麼操作或條件下會發生（例如同時操作、中途失敗、資料為空）。
3. **影響**：使用者或資料會怎樣；影響哪些驗收條件、假設或功能。
4. **技術原因**：為什麼會這樣，程式或規格的哪個部分造成。
5. **建議**：建議怎麼處理與理由。規格的問題寫出建議的驗收條件。只是建議，不要寫成已確認的需求。
6. **開發者決策**：否／需要確認／需要選擇。需要選擇時列出選項與各自的影響，最後寫建議與理由。

第 2 輪以後，和前幾輪某一項出自同一個根本原因時，在「技術原因」寫明「與紀錄檔 #M 同一根本原因」（規格審查核准前還沒有紀錄檔，寫「與第 N 輪 #M」）。

## Technical Evidence（技術證據）

### 執行過的檢查

跑過的指令與結果（例如 `pytest` 632 passed）。

### <reviewer 各自的檢查表>

### 各項發現的證據

#### #1

- 依據：`檔案:行號`
- 程式碼或資料流程：
- 測試結果：
- 已驗證：
- 待確認：
````

reviewer 各自的檢查表：

- `specification-reviewer`：「查證紀錄」表與「已接受的風險」。
- `acceptance-reviewer`：「驗收條件」表。
- 高風險等級，兩種 reviewer 另外填「安全與一致性檢查」表。規格審查看驗收條件與實作計畫有沒有定義，實作審查看程式與測試有沒有做到：

| 項目 | 結果（有涵蓋／沒有涵蓋／不適用） | 依據（AC 編號或檔案:行號） |
|---|---|---|
| 登入與權限：只動得到自己的資料，沒登入或沒權限時的回應 | | |
| 輸入驗證與注入 | | |
| 憑證、token、個資不出現在 log、回應、錯誤訊息與公開的地方 | | |
| 同時操作 | | |
| 中途失敗後的資料狀態 | | |
| 和外部系統（Google Calendar、外部平台）的一致性 | | |
| 既有資料：結構改變時舊資料讀不讀得出來、要不要轉換 | | |

「沒有涵蓋」的項目依根本原因列成發現；「不適用」寫出原因。

## 紀錄檔格式

主 session 從各輪的報告整理，不貼報告原文。不寫指向 Context／Frontier 項的 C、Q 編號，換成決定的內容與落點（規則見 `/feature` 第 1 節「Context 與 Frontier」）。

```markdown
# <功能名稱>：規格審查紀錄 | 實作審查紀錄

- 規格：[docs/specs/<功能>.md](../../specs/<功能>.md)
- PR：#NN
- 等級：輕量 | 標準 | 高風險
- 輪數：N（第 1 輪 YYYY-MM-DD `<commit>`；第 2 輪 …）
- 最終結果：沒有阻擋項目 | 仍有阻擋（#N，原因）

## 摘要

- 發現：N 項（類型與嚴重程度各幾項）
- 開發者決策：N 項
- 尚未處理：N 項

## 各輪摘要

| 輪 | 日期／commit | 新發現（阻擋） | 這一輪之後改了什麼 |
|---|---|---|---|
| 1 | YYYY-MM-DD `<commit>` | #1–#5（#1、#3） | AC3 改寫、新增 AC7；#2 開 issue |

## 發現與處理

| # | 輪 | 標題 | 類型 | 嚴重程度 | 阻擋合併 | 涉及安全／架構 | 根本原因 | 處理 | 決定者 | 結果 |
|---|---|---|---|---|---|---|---|---|---|---|

## 問題說明

### #1 <標題>

問題、情境、影響、技術原因各一兩句；依據 `檔案:行號`。

## 開發者決策

| # | 問題 | 選項 | 開發者的決定 | 理由 |
|---|---|---|---|---|

## 尚未處理

| # | 原因 | 後續（issue 編號或「無」） |
|---|---|---|
```

- 「#」沿用第 1 輪報告的編號，之後各輪的新發現接著編號，跨輪不重編；「輪」寫第幾輪發現的。
- 「根本原因」是阻擋項目的簡短名稱，同一個根本原因在之後各輪沿用同一個名稱，用來累計輪數（見 `/feature` 第 3 節）；不阻擋的寫「—」。
- 「決定者」寫開發者、規則（例如阻擋的 Implementation Defect / Test Gap 直接交回實作），或主 session（只限文件同步、修正違反既有規則的地方，以及規格審查時依查證依據修正、不改變行為的 Factual Error；規格核准後的修改一律由開發者確認）。
- 「結果」寫 commit、issue 或 advisory 編號。規格審查在核准前，寫「規格已修改」或「開發者決定不採用」即可。
- 「問題說明」只寫阻擋合併、需要開發者決策，或尚未處理的項目；其他項目看「發現與處理」表就夠。
- 「開發者決策」只記審查與核准後產生的決定；問答與寫規格階段的決定只留在規格（內容與落點），不記進這張表（見 `/feature` 第 1 節「Context 與 Frontier」）。
- 沒有開發者決策、沒有尚未處理的項目時，那一節寫「無」。
- 規格審查的紀錄另外保留最後一輪的「查證紀錄」與「已接受的風險」兩節：實作後的 `acceptance-reviewer` 以它們為準。
- 高風險等級另外保留最後一輪的「安全與一致性檢查」表。
- 輕量的規格審查紀錄另外加「## 未經審查的驗收條件」一節：第 1 輪後新增或改寫的 AC 編號與改了什麼；沒有的寫「無」。實作後的 `acceptance-reviewer` 對這些 AC 補做事實查證、一致性與情境檢查，結果寫在實作審查紀錄。
- 「各輪摘要」每輪一列，寫這一輪的新發現與它造成的改變（規格、做法、程式），讓讀者看得出每輪的差異，不只最後的結果。
- ADR 0007 以前的紀錄檔沒有「等級」與「各輪摘要」，保留原樣。
- 規格審查在核准前沒有 PR，「PR」寫「（核准前）」，PR 開好後再補上。
