# 功能規格

每個用 `/feature` 開發的功能一份，檔名 `<功能>.md`，和實作放在同一個 PR。為什麼放在這裡見 [ADR 0002](../decisions/0002-specs-in-repo.md)。

規格是實作 agent 唯一的需求來源，要寫到不看討論過程也能照著做。

## 格式

```markdown
# <功能名稱>

- 狀態：草稿 | 已核准 | 已完成
- PR：#NN

## 背景
為什麼要做。

## 需求
要做什麼。

## 不做
明確排除的範圍。

## 假設
程式碼看不出來、經開發者核准的業務規則，逐條編號。

## 驗收條件
| # | 條件 |
|---|---|
| AC1 | 在 X 情況下，系統要 Y |

每條都要能驗證。逐一想過失敗、空資料、載入中、未登入／無權限、資料處理、安全性；不適用的寫在下面並說明原因。

## 不適用的情境
| 情境 | 原因 |
|---|---|

## 實作計畫
要改的檔案、步驟。

## 測試對應
| AC | 測試 |
|---|---|

## 修改紀錄
| 日期 | 修改 | 原因 | 確認者 |
|---|---|---|---|
```

規格核准後，驗收條件的任何新增、修改、刪除都要記在「修改紀錄」，並註明開發者確認過。
