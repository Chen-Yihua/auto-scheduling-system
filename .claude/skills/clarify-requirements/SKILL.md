# 需求確認

> 什麼時候讀：`/feature` 判斷完等級之後。所有等級都做；深度依「需求問答」的提問原則（小改動自然只有一兩題）。之後任何階段出現新的決定、或要升級等級時，回來讀「新的決定一律回到決策樹」與「做到一半改成較高的等級」。

## 需求理解

由 /issue 進來時，需求來自 issue。

開始需求探索前，先用自己的話簡述對需求的理解：

- 開發者想解決什麼問題、誰會使用、預期達成什麼目的。
- 現有系統如何運作，以及這次需求可能影響的功能、資料或流程。
- 發現需求與現有系統或既有規則衝突時，直接指出。

讓開發者有機會修正理解上的錯誤，再進入後續流程。需求已清楚時，不為了形式額外提問。

文字修正只需確認修改目標與範圍，不需要完整的需求理解流程。

## 記錄決定

對話可能被摘要，審查用的 agent 也看不到對話，所以開發者確認的決定要馬上寫到會留下來的地方，不要攢到最後：

- 業務規則、範圍、行為 → 規格草稿 `<功能>-spec.md` 的需求、不做或驗收條件。開發者決定的不寫成「假設」；只有開發者明確說「你決定」的才寫成假設。
- 術語 → `<功能>-glossary.md`（見下面「術語」）。
- 重大架構決策 → ADR 草稿 `<功能>-adr-<名稱>.md`。

scratchpad 另外只留一份 `<功能>-grill.md`，兩節：

- **已確認**：一行一項，寫決定的內容與寫在哪裡（規格的哪一節或哪條 AC、ADR，或「術語表」），開發者交給你決定的標註「（你決定）」。
- **待問**：現在就能問、前提都已確認的問題，加上還沒問到的分支。開發者回答後移到「已確認」；回答帶出的新問題加進「待問」。

所有等級都用這份檔案：問開發者的題目與回答都要記進去。從程式碼、文件、git 紀錄查到的事實不放進來，寫進規格的「背景」。

這份檔案不 commit，也不是正式紀錄：已確認的內容都已經在規格、ADR 或術語表裡，之後的讀者看那些檔案。寫進規格、審查紀錄、ADR、PR 描述、issue、commit 訊息時，不引用這份檔案，直接寫決定的內容與寫在哪裡。問答與寫規格階段的決定只留在規格，當時的選項不保留；審查與核准後產生的決定，照 `docs/reviews/README.md`「紀錄檔格式」記在審查紀錄的「開發者決策」表。

### 術語

開發者回答了一個術語的名稱與定義（包括接受建議答案），這個術語就算確定。術語表的位置、收錄範圍與格式見 `docs/README.md`「術語表」。

- 核准前任何階段（問答、寫規格、規格審查）確定的術語：馬上照格式寫進 scratchpad 的 `<功能>-glossary.md`（只寫這次確定的術語，不含檔頭），在 `<功能>-grill.md` 的「已確認」記一筆，寫在哪裡填「術語表」。核准前仍然只寫 scratchpad，不改 repo。
- 核准後（實作回報、實作審查）才確定或修改的術語：照 `implement-and-review`「規格問題的處理」寫進規格的修改紀錄（寫在哪裡：「術語表」），更新 `<功能>-glossary.md`，照 `implement-and-review`「交付清單」交給 `feature-implementer`。
- 核准後，`<功能>-glossary.md` 的術語合併進 `docs/glossary.md`（第一個術語合併時由 `feature-implementer` 建立檔案，不預先填寫）。
- 文字修正不寫術語表。

## 需求問答

問答規則改寫自 [mattpocock/skills](https://github.com/mattpocock/skills) 的 `grilling`（commit `4ae2317`，MIT 授權）。

本節的目的是確認足以決定本次需求與系統行為的重要事項，不是找出所有可能的例外情境。

第一輪開頭寫出暫定的等級與理由；等級仍和規格一起核准。問答的題目與回答照上面「記錄決定」記進 `<功能>-grill.md`。

**提問原則：**

- 只有答案可能改變需求、系統行為、重要設計取捨或本次範圍時，才向開發者提問。
- 程式碼、文件、git 紀錄可以查證的事實，由你自行查證。
- 一般實作細節由 Agent 依照現有架構、專案慣例與工程原則決定，不把技術實作選擇全部交給開發者。
- 低風險且不影響整體方向的不確定性，可以提出合理假設，記錄依據與可能影響。
- 超出本次需求範圍的改善，列為後續 Issue。
- 不為了涵蓋所有可能的例外情境而持續增加問題。

**需求探索停止條件：**

以下條件都滿足時，結束需求問答：

1. 影響需求、系統行為、重要設計或範圍的決定都已確認。
2. 可以透過程式碼、文件或其他資料查證的事實，已完成必要查證。
3. 剩餘不確定性已有合理假設或明確排除方式。
4. 沒有尚未處理的重大風險或會影響規格方向的問題。

開發者要求收尾時，整理仍未決定的事項，逐項標明可能影響，請開發者決定列為假設或排除在本次範圍外；重大風險不得直接當作低風險假設。

把需求畫成**決策樹**：每個決定底下掛著因它而來的決定。每一**輪**問「待問」裡現在就能問的所有問題，一次問完，等開發者回答完再算下一輪。同一輪裡，答案取決於另一題的問題，放到下一輪。

每一輪的格式：

```
❓ **Q1** - **<標題>**：<內容，可以有多段、多個選項>

➡️ <建議答案>

---

❓ **Q2** - …
```

- 題目的問法要讓「是」等於接受建議答案；下一點的「需要你選擇」題目除外。
- 涉及未定義的產品行為、權限、安全性、資料處理或架構的題目，先列出選項與各自的影響，`➡️` 那一行寫建議與理由，並標明「需要你選擇」：開發者要選定一個選項（或另外說明），只回「是」不算（和 `implement-and-review`「規格問題的處理」同一個標準）。
- **事實自己查，不問開發者**：程式碼、文件、git 紀錄查得到的就自己讀；範圍很大時才派 `Explore` agent。查詢還沒結束時，只有依賴查詢結果的題目要等，其他照問。
- **決定交給開發者**：業務規則、範圍、取捨都要問，不可自己回答自己的問題。開發者明確說「你決定」的才由你決定，並記下來。
- 只靠討論決定不了的問題（畫面怎麼排、操作感受），不要一直換句話問：說明這題需要看到畫面才能決定，請開發者選擇先用假設、或排除在這次範圍外。
- **用詞和術語表不一致時馬上問**：開發者或 issue 用的詞和 `docs/glossary.md`、`<功能>-glossary.md` 的定義不一致時，馬上指出並問清楚。
- **用詞模糊時提出明確的說法**：用詞模糊，或同一個詞可能指不同概念時，提出明確的說法請開發者選。

（以上兩條用詞規則改寫自 mattpocock/skills 的 `domain-modeling`，commit `4ae2317`，MIT 授權。）

「待問」空了之後，先讀規格會碰到、但還沒讀過的程式碼（實作計畫會改的檔案、新功能和既有規則交會的地方，例如既有的排程規則、刪除行為、登入驗證），因為寫規格時才讀到的程式碼，常會冒出問答沒問到的決定。查證後只有發現會影響需求、重要設計或本次範圍的新決定，才重新加入「待問」，再問一輪。

接著把「已確認」列給開發者，請開發者確認雙方理解一致；開發者確認前，不寫規格草稿。

## 工程方案探索

需求確認後、撰寫規格前，先從工程角度分析合理的實作方式，而不是直接將使用者提出的做法轉換成程式碼。依開發等級調整分析深度：高風險完整分析；一般依範圍簡要到完整；文字修正跳過。不為了形式而提出不必要的方案。

**1. 分析現有系統**

- 閱讀相關程式碼、文件與既有設計，理解目前的運作方式、資料流及模組責任。
- 確認是否已有可重用的機制，以及本次需求可能影響的上下游功能。

**2. 評估工程設計**

- 是否能利用現有機制，以更簡單、一致的方式解決問題？
- 是否存在重複邏輯、責任不清或不合理的模組邊界？
- 是否有更根本的解法，而不是只增加判斷或補丁？
- 修正既有問題時，先確認根本原因。

**3. 提出實作方案**

- 比較有實際意義的替代方案，說明差異、成本及推薦理由。
- 一般技術實作方式由 Agent 決定；涉及產品行為、業務規則或重大設計取捨時，回到決策樹請開發者確認。
- 將選定方案與必要的設計理由寫入規格的「實作計畫」。

## 新的決定一律回到決策樹

已確認之後，任何階段（寫規格、規格審查、實作回報、實作審查）出現需要開發者決定的事，都照這裡處理，不要在決策樹之外決定：

1. 加進「待問」，用「需求問答」的格式問開發者；開發者回答後移到「已確認」，並寫進規格（或 ADR、術語表）。
2. 檢查有沒有改變已確認的項目：判斷方式是「同一個欄位、同一支 API、同一條排程或刪除規則」。每一項寫有沒有改變、原因。例如「子任務可以插入任意位置」要檢查 AI 推斷優先序的調整（現在要同時看前後兩個階段）、刪除後遞補（插入、刪除的一致性），以及優先序與截止日的限制。
3. 有已確認的項目被改變時，把它重新打開問開發者，影響檢查附在題目前面。
4. 開發者確認新增和改變的項目後，才能進下一階段；只要確認這些項目，不用整份重看。

## 做到一半改成較高的等級

只升不降；降級要開發者同意。依升級的時間點處理：

- 核准前（寫規格、規格審查）：補做新等級該有的問答，再改寫草稿。一般升級成高風險不重做問答，新的決定照「新的決定一律回到決策樹」。
- 文字修正修改中發現會改變程式行為：補做問答，再照新等級寫規格；已改的內容保留、不還原，問答與寫規格期間不再繼續修改，併進新規格的實作計畫。
- 規格核准後（實作回報、實作審查）：不補做問答，之後的新決定照「新的決定一律回到決策樹」。
