# 0017. 審查發現改用 Conventional Comments 標籤

- 狀態：已採用
- 日期：2026-11-20

## 背景

[0005](0005-specification-review.md) 把審查發現依根本原因分成 6 種類型，之後又加上 4 種嚴重程度、涉及安全／架構、開發者決策、確定程度；[0003](0003-issue-workflow.md) 規定審查輪數依根本原因計算、不阻擋的發現一律開 issue。每項發現要分開判斷 6 個欄位，阻擋依類型決定，處理表依類型分成 5 種去處。開發者讀報告要對照很多定義，規則越細，審查越容易找到「規則沒寫到」的地方（issue #155，來自 #152 第二部分第 2 點）。

一般做法：

- [Conventional Comments](https://conventionalcomments.org/)：每則留言標一個標籤；blocking 是解決前不應該接受，non-blocking 是不應該因此不接受。
- Google〈[The Standard of Code Review](https://google.github.io/eng-practices/review/reviewer/standard.html)〉：改動確定讓整體程式碼健康度變好時就應該核准，即使不完美；個人偏好與純風格不是要求修改的理由。
- [GitLab Code Review Guidelines](https://docs.gitlab.com/development/code_review/)：非必要的建議標 non-blocking；只剩 non-blocking 的建議時就往下一步。

## 決定

1. 每項發現標一個標籤（`issue`、`suggestion`、`nitpick`、`question`），只描述發現的性質；定義只寫在 `docs/reviews/README.md`「分類」。
2. 阻擋另外判斷：問題的實際影響嚴重到這次 PR 不應該被接受時才阻擋。評估時考量正確性、安全性、可靠性、需求與驗收條件的符合度、程式碼健康度；安全、架構、影響大小是考量，不是分類。不訂固定的阻擋清單。`nitpick` 一律不阻擋，其他標籤不由標籤決定阻擋。
3. 漏洞的標題開頭寫「漏洞：」，阻擋照第 2 點判斷；「漏洞的處理」會暫停流程、不公開細節、不推送修正，開發者決定前 PR 不能結束，這些不看阻擋欄位。
4. 主 session 依標籤、阻擋與「要不要改規格」決定去處：要改規格、會改變規格寫到的行為或新增規格沒寫的行為，或涉及沒有核准過的重大架構決策（不分阻擋與否）時問開發者；阻擋、不用改規格的交回實作；`question` 先查程式碼與文件，要開發者決定的才問；不阻擋的由主 session 決定改不改，和這次 PR 無關的（包括審查以外發現的），判斷之後還需要有人處理才開 issue，不開的寫原因。
5. 修正只要對應某條驗收條件，或是屬於這次 PR、不改變也不新增行為的品質修正，`feature-implementer` 就可以做；會改變或新增行為的，問開發者。
6. 實作審查連續 3 輪都還有阻擋，第 3 輪留言貼出後就停下來問開發者，不看是不是同一個原因。
7. 拿掉類型、嚴重程度、涉及安全／架構、開發者決策、確定程度、「寫法問題」與「輪數依根本原因計算」。

## 放棄的做法

- **保留類型，只拿掉嚴重程度**：類型的主要用途是決定阻擋與去處，保留類型仍要對照 6 個定義。
- **用固定清單判斷阻擋（例如「驗收條件不成立、規格有錯、測試讓錯的實作也通過、違反 CLAUDE.md」）**：清單寫不到的情況會被判成不阻擋，補上去又變成新的細則；Google、GitLab 都是依實際影響判斷。
- **用裝飾詞標出要改規格（例如 `issue (blocking, spec)`）**：等於又加一個欄位；Conventional Comments 也是把怎麼修寫在留言內文。
- **不阻擋的發現一律開 issue**：屬於這次 PR 的小問題（註解寫錯、少測試）延後到另一個 issue，等於合併一個已知可以順手修好的改動；不值得追蹤的也開，issue 會越積越多。
- **輪數照舊依根本原因計算**：要替每項阻擋取名稱、跨輪比對，本身就是一組要審查的規則；連續 3 輪都還有阻擋已經足以讓開發者介入。

## 影響

- 推翻 [0003](0003-issue-workflow.md) 的「不阻擋的審查發現自動開 issue」「審查輪數依根本原因計算」「實際漏洞一律阻擋」「安全改善建議分開分類」，以及「暫停的條件」裡「實際漏洞（一律阻擋）」與標成「安全」的那兩項；[0005](0005-specification-review.md) 的「審查分類依根本原因」與「不阻擋的發現在同一則訊息裡一起問，回答後才開 issue」；[0010](0010-scratchpad-loss-recovery.md)「審查豁免」的「並阻擋」與「三種實際風險仍然阻擋」（改成列為發現，阻擋照第 2 點）；[0012](0012-simplify-process-levels.md) 決定 3 的「去處只有四種」與規格草稿什麼時候問開發者。四份只改狀態行。
- 0003 當初不在當前 PR 修不阻擋的發現，理由是「這些修改沒有經過規格核准」。新規則仍保留開發者的決定權：會改變或新增行為的修正、要改規格的修正、沒有核准過的重大架構決策都要問開發者；不需要問的只限不改變行為的品質修正，而且每項決定都寫在審查留言，開發者看得到。
- 0003 也提到由開發者逐項決定要不要開 issue 容易遺漏；新規則由主 session 判斷，不開的原因寫在審查留言的「處理」，沒有審查留言時寫在給開發者的回報，所以每一項都有紀錄。
- 0005 的規格審查、開發者要選定選項的規則照舊。
- 舊的審查紀錄、規格與實驗紀錄仍用舊名稱，讀時用 `docs/README.md` 的舊名稱對照表。
- 同一個原因反覆出現但中間有一輪沒有阻擋時，不會累計到 3 輪；開發者從審查留言看得到。
- 阻擋改成依實際影響判斷後，兩個 reviewer 對同一種問題可能判得不一樣；判斷理由寫在每項發現的「影響」裡，主 session 與開發者可以從留言看出來。
