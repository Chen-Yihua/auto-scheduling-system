# 寫規格

> 文字修正不寫規格（`feature`「文字修正的流程」）；快速路徑寫短版規格、不做規格審查（`feature`「快速路徑」）。

## 寫草稿

規格照 `docs/specs/README.md` 的格式，寫在草稿資料夾的 `<功能>-spec.md`；修 bug 另外照同一份的「修 bug 時」。重大架構決策另外寫 ADR 草稿 `<功能>-adr-<名稱>.md`，和規格一起核准。

**假設**：先看這件事由誰決定，因為假設是開發者核准時才第一次看到的內容，把開發者決定過的事寫成假設，讀者會以為還沒定。

- 開發者決定過的：寫進需求、不做或驗收條件。
- 還要開發者決定的（例如業務規則）：照 `clarify-requirements`「新的決定」問，確認後寫進需求、不做或驗收條件。
- 由你判斷、或開發者交給你決定的：寫成假設。

**對照已確認的決定**：`<功能>-grill.md` 不 commit，所以請開發者核准前，逐項確認「已確認」的每一項都在規格、ADR 草稿或 `<功能>-glossary.md` 裡找得到，而且和驗收條件不矛盾。

## 什麼時候做規格審查

規格審查找的是寫程式前就看得出來的問題，例如對現有系統的描述錯了、需求有兩種讀法。需求清楚時審查多出的只是等待，實作審查也會檢查規格，所以照順序判斷，符合就停：

1. 高風險：做。
2. 一般，符合下面任一種：做。
   - 有影響實作的重要歧義：照字面可以寫出兩種行為不同的程式。
   - 還有要開發者決定的事（「請你決定」不是「無」）。
   - 開發者的決定改變了既有的規則或行為（例如既有的排程規則、刪除行為）。
3. 其他：不做。規格開頭寫「規格審查：沒有（<理由>）」，由 `acceptance-reviewer` 在實作審查時補做規格的檢查。

問答裡已經決定、只影響這次新增行為的事，或只是確認細節，不算第 2 條：這類規格出錯的代價小，實作審查也會補查。

要審查時，把下面的路徑交給 `specification-reviewer`：`<功能>-spec.md`、等級、`<功能>-grill.md`，以及 ADR 草稿、`<功能>-glossary.md`（有的話）。

## 處理發現與審查次數

發現照 `implement-and-review`「發現處理」的「核准前」那一欄處理。每次審查都要重讀規格與程式碼，所以只在可能找到新問題時才審：

1. 第 1 次：完整審查。
2. 處理發現時改了驗收條件、假設或設計：第 2 次只審改過的部分與受影響的內容。附上修改內容與原因、受影響的 AC，以及第 1 次報告和上一版規格（`<功能>-spec-v<N>.md`）的路徑。只改措辭不審。
3. 之後的修改由你自己檢查：受影響的 AC、假設、實作計畫與測試對應都一起改或確認不用改。
4. 修改帶出新的重大歧義、架構或安全問題時，可以再審一次，只審那個問題，並告訴開發者理由。

報告原文存成 `<功能>-spec-review-r<N>.md`。規格審查在 PR 開之前做，所以留言等 PR 開好後才貼（`implement-and-review`「審查留言」）。

## 請開發者核准

訊息附上草稿路徑，以及：

- 規格審查的摘要：改了什麼、哪些建議不採用；沒做審查時寫理由。
- 還要開發者決定什麼。
- 已確認決定的對照結果：每一項寫在規格、ADR 草稿或術語表的哪裡。開發者核准規格時一起確認這份對照。

核准的定義見 `feature`「硬規則」。
