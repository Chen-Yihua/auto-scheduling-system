# 功能開發流程（grilling 實驗版）

需求：$ARGUMENTS

這是實驗用的入口，正式流程仍是 `/feature`。和 `/feature` 唯一的差別是寫規格前多了第 0 節的需求問答；實驗目的與紀錄方式見 `docs/experiments/feature-grill/README.md`。

開始時執行 `git rev-parse HEAD` 和 `date -Iseconds`，記下起始 commit 與時間；之後每個階段結束時也記下時間，第 4 節填實驗紀錄時用。

## 0. 釐清需求（不開 plan mode）

問答規則改寫自 [mattpocock/skills](https://github.com/mattpocock/skills) 的 `grilling`（commit `4ae2317`，MIT 授權）。不開 plan mode：plan mode 會讓你急著產出計畫，這一節要的是問到沒有問題為止。

把需求畫成**決策樹**：每個決定底下掛著因它而來的決定。每一**輪**問「前沿」：前提都已經決定好、現在就能問的所有問題，一次問完，等開發者回答完再算下一輪。同一輪裡，答案取決於另一題的問題，放到下一輪。

每一輪的格式：

```
❓ **Q1** - **<標題>**：<內容，可以有多段、多個選項>

➡️ <建議答案>

---

❓ **Q2** - …
```

- 題目的問法要讓「是」等於接受建議答案；下一點的「需要你選擇」題目除外。
- 涉及未定義的產品行為、權限、安全性、資料處理或架構的題目，先列出選項與各自的影響，`➡️` 那一行寫建議與理由，並標明「需要你選擇」：開發者要選定一個選項（或另外說明），只回「是」不算（和 `/feature` 第 3 節「規格問題的處理」同一個標準）。
- **事實自己查，不問開發者**：程式碼、文件、git 紀錄查得到的就自己讀；範圍很大時才派 `Explore` agent。查詢還沒結束時，只有依賴查詢結果的題目要等，其他照問。
- **決定交給開發者**：業務規則、範圍、取捨都要問，不可自己回答自己的問題。開發者明確說「你決定」的才由你決定，並記下來。
- 只靠討論決定不了的問題（畫面怎麼排、操作感受），不要一直換句話問：說明這題需要看到畫面才能決定，請開發者選擇先用假設、或排除在這次範圍外。
- 不設題數上限。開發者要求收尾時，把還沒問到的分支列為「未決定」，請開發者決定各自寫成假設或不做。

前沿空了之後，先讀規格會碰到、但還沒讀過的程式碼（實作計畫會改的檔案、新功能和既有規則交會的地方，例如既有的排程規則、刪除行為、登入驗證），因為寫規格時才讀到的程式碼，常會冒出第 0 節沒問到的決定。有新的決定就再問一輪。

接著整理「已決定的事項」，編號 D1、D2…，寫進 scratchpad 的 `<功能>-decisions.md`：規格審查 agent 要讀它，對話很長時也不會因為被摘要而遺失。每項寫內容、來源（開發者決定／開發者交給你決定）、前提（依賴哪些 D 項）。請開發者確認雙方理解一致；開發者確認前，不進第 1 節。

### 新的決定一律回到決策樹

D 項確認之後，任何階段（寫規格、規格審查、實作回報、實作後審查）出現需要開發者決定的事，都照這裡處理，不要在決策樹之外決定：

1. 編成新的 D 項（接著編號），寫進 `<功能>-decisions.md`，標上是在哪個階段產生的。
2. 做影響檢查：列出可能受影響的既有 D 項。判斷方式是「同一個欄位、同一支 API、同一條排程或刪除規則」，或「前提」裡有關聯。每一項寫有沒有改變、原因。例如「子任務可以插入任意位置」要檢查 AI 推斷優先序的調整（現在要同時看前後兩個階段）、刪除後遞補（插入、刪除的一致性），以及優先序與截止日的限制。
3. 有既有 D 項被改變時，把它重新打開，用第 0 節的格式問開發者，影響表附在題目前面。
4. 開發者確認新增和改變的 D 項後，才能進下一階段；只要確認這些項目，不用整份重看。

## 1–4. 照 `/feature` 執行

讀 `.claude/skills/feature/SKILL.md`，照第 1–4 節執行，差異只有：

| 項目 | `/feature-grill` 的做法 |
|---|---|
| 第 1 節的提問 | 寫規格時發現第 0 節漏掉的決定，照「新的決定一律回到決策樹」處理，算進問答輪數。plan mode 裡只能用 AskUserQuestion 提問，所以題目的描述要寫出可能影響哪些 D 項；回答後，把影響表寫在 plan 檔開頭的「新增的決定」一節；有既有 D 項被改變時，ExitPlanMode 前先用 AskUserQuestion 請開發者確認。存成規格檔時拿掉這一節 |
| 規格審查 | 已決定事項傳 `<功能>-decisions.md` 的路徑。需要開發者決定的發現，照「新的決定一律回到決策樹」處理 |
| 核准後的規格問題 | 照 `/feature` 第 3 節「規格問題的處理」，開發者的決定也照「新的決定一律回到決策樹」編成 D 項；規格「修改紀錄」的「原因」寫上 D 編號 |
| 規格內容 | 開發者決定的 D 項寫進「需求」「不做」「驗收條件」；只有開發者交給你決定的 D 項，以及你為了寫規格另外做的判斷，才寫進「假設」。「背景」最後加一行：`需求釐清：/feature-grill（實驗），問答 N 輪` |
| 第 4 節的回報 | 另外照下面「實驗紀錄」填一份紀錄，在回報裡附上檔案路徑 |

## 實驗紀錄

複製 `docs/experiments/feature-grill/TEMPLATE.md` 到 `docs/experiments/feature-grill/records/<功能>-feature-grill.md`，照模板裡每個欄位的說明填寫。

- 數字從規格的「修改紀錄」、`docs/reviews/specification/<功能>.md`、`docs/reviews/implementation/<功能>.md`、`<功能>-decisions.md`、這次對話的問答輪數計算，不要估算；拿不到的數字寫「無資料」與原因。
- Missing AC 的嚴重程度由你依模板的定義提出，開發者確認後才算數。
- Token 與時間從這個 session 的 transcript 計算，不用請開發者執行 `/cost`：`~/.claude/projects/<專案目錄>/` 底下包含這次 `/feature-grill` 指令的 `.jsonl`，每筆 assistant 訊息有 `message.usage` 與 `timestamp`。從 `/feature-grill` 開始的那筆算起，同一個 `message.id` 只算一次，`isSidechain` 為 true 的不算；subagent 的用量取 Agent 工具回報的數字。
- 紀錄檔不要放進這個功能的 PR：實驗紀錄最後一起用另一個 PR 提交。
