# 實作與審查

> 發現可被利用的漏洞時（任何階段），直接讀「漏洞的處理」。

核准後照下面的步驟往下做，不用每一步都等開發者確認；只有下面寫明要問開發者的情況才停下來問。

## 步驟

照順序做，每一步的細節見括號裡的節：

1. 整理交付清單，交給 `feature-implementer` 實作、開 PR（「交付清單」「交辦實作與處理回報」）。
2. PR 建立後，貼規格審查每一輪的留言（「審查留言」）。
3. 交給 `acceptance-reviewer` 審查（「交給 acceptance-reviewer 審查」）。
4. 依每項發現處理（「發現處理表」）。
5. 處理完這一輪的發現後，貼這一輪的留言（「審查留言」）。
6. 還有阻擋的項目就回到第 3 步（「重新審查與連續 3 輪都還有阻擋」）。
7. 沒有阻擋後，照 `feature`「回報」回報。

## Commit 責任

依文件種類分清楚由誰 commit。

| 種類 | 檔案 | 誰寫內容 | 誰 commit、push |
|---|---|---|---|
| 產品文件 | 規格（`docs/specs/`）、ADR（`docs/decisions/`）、術語表（`docs/glossary.md`） | 主 session（核准前在草稿資料夾（`.drafts/`）） | `feature-implementer`，照交付清單 |
| 程式碼與測試 | 其他 | `feature-implementer` | `feature-implementer` |

文字修正沒有 `feature-implementer`，照 `feature`「文字修正的流程」自己 commit。

## 交付清單

交給 `feature-implementer` 產品文件時附上，列出每個檔案的 repo 路徑與草稿資料夾來源。術語表另外列出術語，分成「新增」、「修改既有定義（開發者已確認）」與「更新本 PR 的術語」：修改要寫術語名稱、原定義與新定義；這個 PR 先前交付、`origin/main` 還沒有的術語要改定義時，標成「更新本 PR 的術語」，寫術語名稱、這個 PR 上一版的定義與新定義。

```
交付清單：
- `docs/specs/<功能>.md` ← <草稿資料夾>/<功能>-spec.md（快速路徑改寫成「PR 描述 ← <草稿資料夾>/<功能>-spec.md（快速路徑）」）
- `docs/decisions/NNNN-<名稱>.md` ← <草稿資料夾>/<功能>-adr-<名稱>.md（沒有寫「無」）
- `docs/glossary.md` ← <草稿資料夾>/<功能>-glossary.md（沒有寫「無」）
  - 新增：<名稱>、<名稱>（沒有寫「無」）
  - 修改既有定義（開發者已確認）：<名稱>；原定義：<origin/main 上的定義>；新定義：<新定義>（沒有寫「無」）
  - 更新本 PR 的術語：<名稱>；上一版定義：<PR 分支上的定義>；新定義：<新定義>（沒有寫「無」）
```

術語和 `origin/main` 的比對由 `feature-implementer` 做，比對規則寫在它自己的定義裡；有相同或相近、定義不一致時它會停下來回報，處理方式見下面「交辦實作與處理回報」。

用在兩個時間點：

- 核准後第一次交辦：交付前在草稿資料夾把規格狀態改成「已核准」，再把交付清單和分支名稱交給 `feature-implementer`。主 session 不自己把規格、ADR、術語表寫進工作目錄。
- 核准後修改規格、ADR、術語表（見下面「規格問題的處理」「核准後修改規格」、核准後的重大架構決策、核准後才確定或修改的術語）：先改草稿資料夾的來源檔，同樣整理交付清單交辦，列出這次改了哪些檔案、哪些術語。

## 交辦實作與處理回報

- 交給 `feature-implementer`，附上交付清單和分支名稱。
- 它建立 PR 後會把規格開頭的「PR」補上編號、commit、push，並回報 PR 編號。收到後，以 PR 分支上已 commit 的規格為準，同步更新草稿資料夾的 `<功能>-spec.md`，之後的交付清單才不會把 PR 編號蓋回去。
- 它回報規格有問題時：判斷要不要改規格；要改就照下面「規格問題的處理」，不用改就直接回覆它怎麼做。
- 它因為「術語重複或衝突」或「工作目錄有歸屬不明的改動」停下來回報時，照順序做：
  1. 用 `clarify-requirements`「需求問答」的格式問開發者；術語的決定照 `clarify-requirements`「新的決定一律回到決策樹」。
  2. 開發者決定修改 `origin/main` 上既有的定義時，交付清單把該術語標成「修改既有定義（開發者已確認）」，寫上原定義與新定義，再做第 4 步。
  3. 要改的是這個 PR 先前交付、`origin/main` 還沒有的術語時，標成「更新本 PR 的術語」，寫上上一版定義與新定義，再做第 4 步。
  4. 再交辦。
- 它回報的「發現但沒處理的問題」：是「漏洞」的照「漏洞的處理」；其他的照下面「發現處理表」第 8 步判斷要不要開 issue，要開的才照「開 issue 追蹤」開。不開的原因，有審查留言的那一輪寫在「處理」，沒有的寫在給開發者的回報（`feature`「回報」的「這次開了或留言了哪些 issue」旁邊）。

## 審查留言

規格審查與實作審查的每一輪，各貼一則公開的 PR 留言。照順序做：

1. 報告原文存成草稿資料夾的 `<功能>-spec-review-r<N>.md`（規格審查）或 `<功能>-impl-review-r<N>.md`（實作審查）。
2. 處理完這一輪的每項發現：決定處理方式，開好要開的 issue（「開 issue 追蹤」）。
3. 把報告原文複製成留言檔 `<功能>-spec-review-r<N>-comment.md` 或 `<功能>-impl-review-r<N>-comment.md`，只改留言檔，報告原文不動：
   1. 第一行寫 `## <功能>：規格審查第 N 輪` 或 `## <功能>：實作審查第 N 輪（commit <sha>）`（`<sha>` 是這一輪審查的 commit）。
   2. 「技術證據」一節包在收合區塊（點了才展開的區塊）裡：前面加 `<details><summary>技術證據</summary>`，後面加 `</details>`。
   3. 標題開頭是「漏洞：」的內容照「審查紀錄與重新審查」改寫。
   4. 最後加一節「處理」，每項發現照 `docs/reviews/README.md`「處理」寫。
4. 用 `gh pr comment <PR> --body-file <留言檔>` 貼出。它成功時印出的網址就是留言連結，回報時附上（`feature`「回報」）。
5. 留言貼出後不修改。交回實作的修正 commit，寫在下一輪留言的「處理」（寫法見第 3 步第 4 點）。
6. 最後一輪之後還有修正或開發者決定時（例如 `nitpick` 的修正、開發者要求在這個 PR 處理的不阻擋發現），另外貼一則補充留言：第一行寫 `## <功能>：實作審查補充`，寫這些 commit 與決定。

時機：規格審查的留言在 `feature-implementer` 回報 PR 已建立之後、交給 `acceptance-reviewer` 之前，依輪次貼出；實作審查的留言在處理完那一輪的發現後貼出，再請 `feature-implementer` 修正。

## 交給 acceptance-reviewer 審查

交給 `acceptance-reviewer` 前先 `git fetch origin main`，確認規格審查的留言已照上面「審查留言」貼出，附上規格檔路徑、等級、分支名稱、PR 編號、規格審查每一輪留言的連結與 PR 描述全文（`gh api repos/{owner}/{repo}/pulls/<PR> --jq .body`）；第 2 輪以後再附上前幾輪實作審查留言的連結。

快速路徑：不附規格檔路徑，等級寫「一般（快速路徑）」，改附「快速路徑，沒有規格審查」，跳過確認規格審查的留言已貼出。

規格審查的留言檔遺失、還沒貼出，開發者決定不補時（見 `feature/references/resume.md`），改附上「沒有規格審查留言」與原因，跳過確認規格審查的留言已貼出；`acceptance-reviewer` 照它的定義補做「完整格式的規格卻沒有規格審查留言」的情境檢查。

## 發現處理表

分類的定義見 `docs/reviews/README.md`「分類」。每項發現照下面順序判斷，符合一條就停。reviewer 在「建議」沒寫要不要改規格、屬於這次 PR 或無關那一句，或寫了也分不出來時，主 session 查證後自己判斷，在「處理」的「決定者」寫主 session。

1. 標題開頭是「漏洞：」：照「漏洞的處理」暫停並回報開發者，不交給實作、不開 issue。
2. `question`：主 session 先查程式碼、文件能不能回答；是要開發者決定的事，用 `clarify-requirements`「需求問答」的格式問開發者。阻擋的 `question` 回答前不往下做；回答後要改規格的，照第 4 步。
3. 涉及重大架構決策（定義見 `feature`「重大架構決策」），而且沒有已核准的決定可以依循（不分阻擋與否）：照「規格問題的處理」問開發者；需要時，決定後寫成草稿資料夾的 ADR 草稿，照「交付清單」交給 `feature-implementer` 存進 `docs/decisions/`。
4. 阻擋的發現，修正要改規格：照「規格問題的處理」問開發者。
5. 阻擋的發現，不用改規格：請 `feature-implementer` 修正或補測試。
6. `nitpick`：主 session 決定改不改，不開 issue。`feature-implementer` 寫的檔案請它改，主 session 寫的檔案自己改；已核准的規格、ADR、術語表照「核准後修改規格」。
7. 不阻擋，屬於這次 PR：主 session 決定改不改。要改的請 `feature-implementer` 修正；修正會改變規格寫到的行為，或新增規格沒寫的行為時，改照第 4 步。不改的在「處理」寫原因。
8. 不阻擋，和這次 PR 無關：主 session 判斷之後還需要有人處理的，照「開 issue 追蹤」開 issue；不需要的，在「處理」寫原因。開發者明確要求在這個 PR 處理時，照第 4 步寫成驗收條件再交給 `feature-implementer`。

第 6、7 步的修正，同一輪沒有阻擋的項目時，不另加一輪審查：主 session 看過修正的 diff，把修正的 commit 寫進「實作審查補充」留言。同一輪還有阻擋的項目時，修正併進下一輪審查。

## 規格問題的處理

1. 整理每一項：問題的情境、影響範圍（哪些檔案、哪些既有驗收條件）、建議的驗收條件與理由。
2. 用 `clarify-requirements`「需求問答」的格式問開發者，並請開發者決定要在這個 PR 補上，還是另開 issue。規格已經核准，每一項修改都要開發者確認。照順序判斷，符合一條就停：
   1. 涉及產品行為、權限、安全性、資料處理或架構：照 `clarify-requirements`「需求問答」的規則標明「需要你選擇」，列出選項與各自的影響，附上建議與理由。
   2. 其他（包括依查證依據修正、不改變行為的規格與現有系統不符）：可以附上建議的驗收條件，讓開發者一次確認。

   開發者的決定照 `clarify-requirements`「新的決定一律回到決策樹」處理。
3. 這個 PR 補：先做下面「核准後修改規格」的影響檢查，把確認後的驗收條件寫進草稿資料夾的規格，照「交付清單」交給 `feature-implementer` 更新規格、實作並補測試。
4. 另開 issue：用 `gh issue create` 記下缺漏與建議的驗收條件，在規格的「修改紀錄」（照「交付清單」交給 `feature-implementer`）與 PR 描述附上連結，這項就解除阻擋。快速路徑沒有「修改紀錄」，連結附在 PR 描述與那一輪審查留言的「處理」。

**停下來問開發者時，一起整理不阻擋的發現**：這一輪因為「發現處理表」第 1～4 步暫停（第 2 步只算阻擋的 `question`），或照「重新審查與連續 3 輪都還有阻擋」停下來時，同一則訊息分成「需要你決定」與「不阻擋的發現」兩區；後者寫主 session 對每一項的決定（改、不改、開 issue），開發者可以改。沒有暫停時，照「發現處理表」第 7、8 步。

### 核准後修改規格

寫進「修改紀錄」之前，先列出這次修改會影響到的其他驗收條件、假設、實作計畫與測試對應，一起更新或確認不用改。「修改紀錄」照 `docs/specs/README.md`「核准後」寫。

## 開 issue 追蹤

照「發現處理表」第 8 步判斷要開的，才照下面的步驟開：

1. 先查重複：`gh issue list --state all --search "<關鍵字>"`。已有相同問題時，在既有 issue 留言補充（`gh issue comment`），不另開。
2. 一項發現一個 issue；同一個檔案、同一個原因的多項發現合併成一個。
3. 內容照 `docs/issues.md`：先寫受影響的人遇到的情境，再寫技術背景、依據（`檔案:行號`）、審查的建議，最後附來源 PR 的連結，「來源」寫 `PR #NN 第 N 輪規格審查／實作審查 #M`（格式見 `docs/issues.md`）。
4. 標籤：程式行為不正確（包括原本就有的問題）用 `bug`，其餘（測試補強、可讀性、文件）用 `enhancement`。不加優先度，交給 `/issue-triage`。
5. 在這一輪留言檔「處理」的「結果」寫上 issue 連結。

## 漏洞的處理

漏洞的定義見 `docs/reviews/README.md`「漏洞」；細節不能出現的地方見 CLAUDE.md「漏洞」。這裡只寫主 session 怎麼處理，不定義漏洞的修復與發布流程。

1. 暫停目前的開發流程，不再交給 `feature-implementer` 任何修正。
2. 可以提出建立 private security advisory 的方案（附上要填的內容），開發者確認後才建立：
   1. 先查重複：`gh api --paginate repos/{owner}/{repo}/security-advisories --jq '.[] | {ghsa_id, summary, state}'`。已有相同問題時沿用它的 GHSA 編號，需要補充時先把要更新的內容寫進草稿資料夾的 `<功能>-advisory.json`，再 `gh api -X PATCH repos/{owner}/{repo}/security-advisories/<GHSA> --input .drafts/<功能>-advisory.json` 更新 description，不另建。
   2. 建立草稿 advisory（只有 repo 管理者看得到）：把下面的 JSON 寫進草稿資料夾的 `<功能>-advisory.json`，再 `gh api -X POST repos/{owner}/{repo}/security-advisories --input .drafts/<功能>-advisory.json`。
      ```json
      {
        "summary": "<一句話>",
        "description": "現象、影響範圍、依據（檔案:行號）、建議的修法、來源 PR",
        "severity": "low | medium | high | critical",
        "vulnerabilities": [{"package": {"ecosystem": "other", "name": "auto-scheduling-system"}}]
      }
      ```
   3. 建立失敗時，不要改開公開 issue，停下來問開發者。
3. 之後照開發者決定的方式處理；開發者決定前，PR 不能結束，不看 reviewer 標的阻擋。

## 審查紀錄與重新審查

- 貼留言前，在留言檔檢查**整份報告**（「摘要」「問題說明」「技術證據」的每一張表），所有提到「漏洞」位置或利用方式的地方，都改寫成一般性的描述（或開發者確認建立後的 advisory 編號）。報告原文不動，也不 commit。
- 重新審查時，reviewer 只看得到改寫過的留言：主 session 把原始內容直接寫進給 reviewer 的指示，不存檔。

### 重新審查與連續 3 輪都還有阻擋

修正後重新審查，直到沒有阻擋的項目為止：

1. 實作審查連續 3 輪都還有阻擋的項目時，第 3 輪的審查留言貼出後，不再交給 `feature-implementer` 任何修正（包括「發現處理表」第 5、7 步），「處理」的「結果」寫「等開發者決定」；主 session 照上面「停下來問開發者時，一起整理不阻擋的發現」整理後問開發者。不看是不是同一個原因。
2. 開發者決定繼續後，從下一輪重新算。
3. 第 2 輪以後的審查範圍照 `feature`「判斷等級」表的「實作審查」欄，寫進給 `acceptance-reviewer` 的指示。

規格審查最多 2 次（見 `write-spec`「審查次數與審查後的修改」），不適用這一節的 3 輪規則。

## 限制

- 不可把 agent 推測的行為當成已確認的需求；開發者確認前，不寫進規格的驗收條件。
- 不可因為發現缺漏就擴大範圍：只做開發者確認過要在這個 PR 補上的部分。
- 修正符合下面任一項才做：對應規格的某條驗收條件；或屬於這次 PR 的品質修正（例如修註解、補測試、改寫法），不改變規格寫到的行為，也不新增規格沒寫的行為。
