# 審查紀錄

兩種審查各自存檔，`<功能>` 和 `docs/specs/` 裡的規格檔同名，和實作放在同一個 PR：

| 審查 | agent | 時機 | 檔名 |
|---|---|---|---|
| 規格審查 | `specification-reviewer` | 規格核准前 | `<功能>-spec-round<N>.md` |
| 實作審查 | `acceptance-reviewer` | 實作完成後 | `<功能>-round<N>.md` |

審查 agent 只能讀、不能寫檔，所以由主 session 存檔：報告原文照貼，處理完後在最後補上「處理結果」。唯一的例外是標成「漏洞」的內容：repo 是公開的，存檔前照 `/feature` 的「漏洞的處理」改寫成一般性的描述（或開發者確認建立後的 advisory 編號）。

## 分類

兩種審查共用這份定義。依**根本原因**分類，不看問題表面的描述：先問「照規格正確實作，問題還在嗎？」，還在就是規格的問題（前三類），不在就是實作或測試的問題。

| 分類 | 定義 | 阻擋 |
|---|---|---|
| Factual Error | 規格對**現有**系統的描述和程式碼、文件不符，例如既有 API 的狀態碼、既有的排程規則 | 是（核准後的修正仍要開發者確認） |
| Specification Defect | 規格內部有問題：AC 之間、AC 與假設之間互相矛盾；假設沒有依據；或照規格做，會讓另一條 AC 在某些條件下不成立 | 是 |
| Missing Acceptance Criteria | 需求範圍內的某個情境，規格沒有定義行為 | 是（開發者決定另開 issue 才解除） |
| Implementation Defect | 規格正確，程式和規格不符 | 是 |
| Test Gap | 測試不足 | 測的是某條驗收條件，而且錯的實作也會通過 → 是；其他 → 否 |
| Improvement Suggestion | 所有驗收條件都成立，只是可以更好；包括和這次功能無關、原本就有的問題 | 否 |

- 只要會讓某條驗收條件在某個條件下不成立（例如同時操作、中途失敗），就不是 Improvement Suggestion，要依根本原因歸到 Specification Defect、Missing Acceptance Criteria 或 Implementation Defect。
- 修正 Factual Error 會改變行為（不只是改文字）時，改列 Specification Defect，由開發者決定。
- 規格審查不審實作，所以不會出現 Implementation Defect 和 Test Gap。

「涉及安全／架構」另外標一欄，不論分類：

- 「漏洞」：實際可被利用的程式漏洞。「阻擋」一律是「是」。
- 「安全」：安全相關的改善建議，或規格、流程、文件的安全缺漏；不是可被利用的漏洞。
- 「架構」：重大架構影響（新增服務或外部依賴、改變模組分層、改資料庫結構或部署方式）。
- 「否」。

## 格式

```markdown
# <功能名稱>：審查第 N 輪

- 規格：[docs/specs/<功能>.md](../specs/<功能>.md)
- PR：#NN
- 日期：YYYY-MM-DD
- 審查的版本：`<commit>`（審查範圍）
- 結果：有阻擋（各分類的數量）| 沒有阻擋項目

## 審查報告

（審查 agent 的報告原文；「漏洞」的內容已改寫）

## 處理結果

| # | 處理 | 決定者 | 根本原因 | commit / issue / advisory 編號 |
|---|---|---|---|---|
```

規格審查的紀錄用同一個格式，差別是標題寫「規格審查第 N 輪」，「審查的版本」寫規格草稿的日期，沒有 PR 時「PR」寫「（核准前）」，PR 開好後再補上。規格審查在核准前，「處理結果」不需要 commit 編號，寫「規格已修改」或「開發者決定不採用」即可。

「根本原因」是阻擋項目的簡短名稱，同一個根本原因在之後各輪沿用同一個名稱，用來累計輪數（見 `/feature` 第 3 節）。「決定者」寫開發者、規則（例如阻擋的 Implementation Defect / Test Gap 直接交回實作），或主 session（只限文件同步、修正違反既有規則的地方，以及規格審查時依查證依據修正、不改變行為的 Factual Error；規格核准後的修改一律由開發者確認）。沒處理的項目也要列出，寫「未處理」與原因。
