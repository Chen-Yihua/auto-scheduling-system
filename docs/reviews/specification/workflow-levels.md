## 問題說明

### #1、#13 標準和文字修正的界線

等級依序比對時，同一個修改可能同時符合文字修正和標準。第 1 輪只把 skill、agent 的規則修改排除在文字修正外，CLAUDE.md 與 `docs/` 裡定義流程的 Markdown 改規則時，照字面仍是文字修正、完全不審查。依據：`.claude/skills/feature/SKILL.md` 第 1 節「判斷等級」。

### #2 輕量的範圍

照架構分層（routers／crud／services／core）解讀「模組」，單一 API 的 bug 通常跨兩層，輕量幾乎用不到。改用功能範圍定義。

### #3、#15、#16 輕量單輪審查後的缺口

輕量只審 1 輪，第 1 輪後新增或改寫的 AC 不會再被規格審查，而實作審查原本把規格審查的查證紀錄當作已確認的事實，這些 AC 在任何階段都沒被查證。第 2 輪發現開發者要求的修改與既有的「改 AC 要重審」規則衝突，以及補查少了一致性檢查。

### #4 文字修正的漏洞處理

文字修正流程寫成第 3 節不適用，也就排除了公開 repo 的漏洞保密規則。

### #14 一句話排除

「失敗」被 AC 涵蓋時，照字面也算「不能用一句話排除」，會讓修失敗回應的 bug 升級成標準。

## 已接受的風險

- 文字修正只靠開發者核准，沒有 agent 審查；公開資訊的邊界也只靠核准。
- 輕量第 1 輪後改寫的 AC 要到實作審查才被檢查，修正的成本比較高（ADR 0007「影響」）。
- 輕量的實作重新審查不重審整個功能，其餘部分由 CI 測試擋住。
- 新增索引或 collection 屬於重大架構決策，因此是高風險。
- ADR 0007 以前的規格與審查紀錄不補等級與各輪摘要。
- 不同等級的實驗紀錄不能直接比較，用 TEMPLATE 的「等級」與「流程版本」區分。
- 標準在 2 輪之後，開發者修改 AC 時要不要跑第 3 輪沒有定義；這是改動前就有的問題，不在這次的範圍內。
- 第 2 輪之後依建議修改的 AC1、AC3、AC9、AC11 沒有再經過審查（標準最多 2 輪）。
