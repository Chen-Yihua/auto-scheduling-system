# 功能規格

用 `/feature` 開發的每個變更一份，檔名 `<功能>.md`；用 `/issue` 開發的檔名 `issue-<N>-<簡短名稱>.md`。等級是「文字修正」的不寫規格（見 `/feature`「判斷等級」）；一般等級的快速路徑也不寫規格檔，短版規格放在 PR 描述（見「快速路徑的短版規格」）。核准後才存進這裡，和實作放在同一個 PR。為什麼放在這裡見 [ADR 0002](../decisions/0002-specs-in-repo.md)。

規格是實作 agent 唯一的需求來源，要寫到不看討論過程也能照著做。

照 `CLAUDE.md`「寫作規則」；流程用語的意思見 `docs/README.md`「術語表」。

## 規格和目前系統的關係

規格記錄的是**核准當時**的需求、設計與驗收條件，PR 合併後不再隨程式更新。之後的變更改了它定義的行為，寫在新的規格裡，不回頭改舊規格的內容。目前系統的行為以程式碼、[api.md](../api.md)、[architecture.md](../architecture.md) 為準。

- 新規格取代了舊規格定義的行為時，在新規格的 PR 裡把舊規格的「狀態」改成「已被 [<新規格>](<檔名>.md) 取代」；只取代一部分時寫「部分被 [<新規格>](<檔名>.md) 取代（AC3、AC5）」。只改狀態這一行，其他內容保留原樣。
- 規格不因為過時而改寫或刪除；沒有持續參考價值時才刪除，條件見 [docs/README.md](../README.md)「生命週期」。
- ADR 0007 以前的規格有的寫「已完成」，意思是 PR 已合併，等同「已核准」；之後不再使用這個狀態，因為合併由開發者決定，沒有人負責回頭更新。

## 驗收條件怎麼寫

各等級都適用，issue 裡「建議的驗收條件」也照這裡寫（見 [docs/issues.md](../issues.md)）。

- 每條驗收條件寫出必須達成的結果：在什麼情況下、做了什麼、結果是什麼。
- 每條標出對應的需求編號，依需求分組排列；新增的 AC 放進它所屬的那一組。審查與核准後的修改才看得出每條需求有沒有被涵蓋。
- 依需求的性質選推導方法，只用適用的。逐項套固定清單容易漏掉需求本身才有的情況（例如某個欄位的上限），所以從需求推：

  | 需求的性質 | 方法 | 要寫出的 AC |
  |---|---|---|
  | 輸入驗證、數值範圍 | 等價類、邊界值 | 每個欄位：合法的最小值與最大值、剛好超出的值、型別錯誤 |
  | 多步驟流程、畫面狀態 | 狀態轉換 | 每個狀態下的每個操作會走到哪裡，包括返回、取消、失敗 |
  | 多個條件一起決定結果 | 決策表 | 每種條件組合的結果 |
  | 其他行為 | 正常與異常流程 | 成功時、失敗時的結果 |

- 需求涉及資料一致性、權限、同時操作、外部系統時，寫**不變條件**（只看畫面驗不出來、但一定要守住的系統狀態），例如資料庫和 Google Calendar 的事件一致、只動得到自己的資料：只看畫面的 AC 讓錯的實作也能通過。
- 寫完後，想一下失敗、空資料、沒登入或沒權限、同時操作、和既有規則（例如既有的排程規則、刪除行為）交會的地方有沒有漏；和這次需求無關的不用寫。
- 每條只講一件事：出現「而且」「以及」就考慮拆開。
- 每條都要能驗證：寫出對應的測試，或手動驗證的步驟（讀哪個檔案的哪一節、輸入什麼、跑什麼指令、查看哪個 CI run 或部署紀錄）與預期結果。
- 和需求無關的技術細節不寫進 AC，例如指定實作方式、沒有人會碰到的防禦情境。
- 清理、轉換這類結果，「測試對應」寫出完整的預期輸出，不只寫「不含某某」。

## 格式

```markdown
# <功能名稱>

- 狀態：草稿 | 已核准 | 已被 [<規格>](<檔名>.md) 取代 | 部分被 [<規格>](<檔名>.md) 取代（AC…）
- 等級：一般 | 高風險（理由）
- 規格審查：有 | 沒有（理由）（見 `write-spec`「什麼時候做規格審查」）
- issue：#NN（由 `/issue` 開發時）
- PR：#NN

## 簡短說明
這份規格要解決什麼，用一兩句話。寫不清楚、範圍可能太大時，在「請你決定」提出要不要拆成多份規格的建議，由開發者決定。

## 背景
先用一兩句寫出問題本身，再用實際案例說明。由 issue 來的規格，來源連結寫在問題前面。

## 需求
要做什麼，逐條編號。每條需求只講一件事：出現「而且」「以及」就考慮拆開。

## 不做
明確排除的範圍，以及刻意不處理的情況與原因。

## 假設
程式碼看不出來、經開發者核准的業務規則，逐條編號。

## 驗收條件
| # | 需求 | 條件 |
|---|---|---|
| AC1 | 1 | <必須達成的結果> |
| AC2 | 1 | 在 X 情況下，做 Y，結果是 Z |

照 `docs/specs/README.md`「驗收條件怎麼寫」。

## 實作計畫
要改的檔案、步驟，以及為什麼這樣做（解決做法）。高風險另外寫考慮過、沒選的做法與理由；屬於重大架構決策的連結 ADR。

## 測試對應
| AC | 測試或驗證步驟 | 預期結果 |
|---|---|---|

修 bug 時加一欄「改程式前是否失敗」（見下面「修 bug 時」）。

## 修改紀錄
| 日期 | 修改 | 原因 | 確認者 |
|---|---|---|---|

## 請你決定
要開發者決定的事，一項一條。核准前全部回答完，答案寫進需求、不做或驗收條件，這一節改寫「無」。
```

## 修 bug 時

修 bug 的規格照一般的格式寫，另外：

- **背景**：先用一兩句寫出問題本身，再寫重現步驟、預期與實際的結果，以及原因，原因要附程式碼依據（`檔案:行號`）。重現步驟與原因是對現有系統的描述，規格審查會去查證。修正前先確認根本原因。
- **AC1**：對應重現步驟：照重現步驟操作，不再出現這個錯誤。
- **其他 AC**：這次修正不能弄壞的既有行為（有的話）。
- **測試對應**：每條 AC 都有測試，並填「改程式前是否失敗」。AC1 對應的測試，改程式前必須失敗，才證明它真的重現了這個 bug。

## 各等級的規格

等級的判斷與各等級的審查見 `/feature`「判斷等級」（[ADR 0007](../decisions/0007-process-depth-by-risk.md)）。草稿寫在草稿資料夾（`.drafts/`）的 `<功能>-spec.md`，核准前不存進這裡，所以狀態「草稿」只會出現在草稿資料夾的草稿。

| 等級 | 必要的節 | 可以省略 |
|---|---|---|
| 一般（快速路徑見「快速路徑的短版規格」） | 簡短說明、背景、需求、驗收條件、實作計畫、測試對應、修改紀錄、請你決定 | 沒有內容的「不做」「假設」 |
| 高風險 | 全部；「實作計畫」寫放棄的做法 | 無 |

## 快速路徑的短版規格

一般等級走快速路徑時（條件見 `/feature`「快速路徑」），規格寫成下面的短版，放在 PR 描述，不存進 `docs/specs/`。

```markdown
# <功能名稱>

- 等級：一般（快速路徑：<符合 3 個條件的理由>）
- issue：#NN（由 `/issue` 開發時）

## 背景
現在的結果與預期的結果。修 bug 時另外寫重現步驟與原因（附 `檔案:行號`）。

## 驗收條件
| # | 條件 |
|---|---|

## 修法
一兩行。

## 測試對應
| AC | 測試或驗證步驟 | 預期結果 |
|---|---|---|
```

修 bug 時，另外照「修 bug 時」的 AC1 與測試對應（加一欄「改程式前是否失敗」）。

- 沒有「狀態」「規格審查」「PR」「需求」「不做」「假設」「實作計畫」「修改紀錄」「請你決定」。
- 驗收條件照「驗收條件怎麼寫」；沒有「需求」，所以不標需求編號。
- 不放「修改紀錄」：要在這個 PR 改驗收條件就改走完整流程，短版規格核准後不會修改。

## 核准後

規格核准後，驗收條件的任何新增、修改、刪除都要記在「修改紀錄」，並註明開發者確認過。「原因」寫決定的內容（一句話）＋寫在哪裡（規格的節或 AC 編號、ADR 編號，或「術語表」）＋檢查過哪些，例如「開發者決定一般等級也要問答 → AC3；檢查過 AC1、AC4 不用改」；有規格的等級（一般、高風險）都這樣寫。PR 合併後的變更照上面「規格和目前系統的關係」寫新規格。
