# 0010. scratchpad 遺失時以暫存產物為單位恢復，審查不逐一要求特定案例

- 狀態：已採用（暫存產物表的位置已移到 feature/references/resume.md，見 [0012](0012-simplify-process-levels.md)）
- 日期：2026-11-09

## 背景

`/feature` 核准前只寫 scratchpad；scratchpad 是 session 專用的暫存資料夾，session 中斷後可能被清掉。[0009](0009-docs-delivery-and-glossary.md) 只寫了舊路徑存在時的接續：把 `<功能>-` 開頭的暫存檔複製到新的 scratchpad，C、Q 編號接續；沒有寫舊路徑不存在時怎麼處理。

`/feature` 第 4 節「暫停與接續」後來依時間點列了舊路徑不存在時的四種情況：核准前、核准後、核准後但 PR 還沒建立、文字修正。PR #71 的實作審查中，同一個根本原因「舊 scratchpad 不存在時的接續」連續 3 輪阻擋：每補一個時間點，就找到下一個（規格審查紀錄草稿 commit 前、審查報告原文整理前、文字修正核准後但還沒套用完）。時間點可以一直切下去，列舉永遠不完整。依 [0003](0003-issue-workflow.md) 的先例（每補一層規則就出現新的邊界情況時，另開 issue 一次設計），這些情況移到 issue #73。issue #72 是同一段規則的另一個缺口：核准後接續時，從 PR 分支複製的術語表、ADR、審查紀錄要存成什麼檔名、放什麼內容沒有寫。同一套規則還在 `docs/README.md` 抄了一份，暫存檔的清單也在三個地方各列一次。

本 ADR 補充 0009，不取代它。

## 決定

- **以暫存產物為單位恢復**：scratchpad 裡的每一種暫存產物都由某個步驟產生。舊 scratchpad 不存在或缺檔時，依「遺失了哪個產物」決定恢復方式，不依遺失的時間點。通用步驟：找出遺失的產物；先 `git fetch`，有正式版本（repo、本機分支、`origin` 上這次的分支或工作目錄）就以它為準，不憑記憶重新產生；有部分成果時逐項標出已完成、未完成、部分完成、待確認，無法確認的不推定已完成；告訴開發者依據的分支、commit 與未 commit 的改動，請開發者補上還沒交付的項目，沒有依據的項目重新核准才執行；都沒有時請開發者選擇重做或不補，已核准的內容重做後要重新核准；不補時記在 PR 描述與實作審查紀錄的「已接受的風險」。
- **暫存產物表**：每一種暫存產物的檔名、產生它的步驟與恢復方式，只在 `/feature` 第 4 節「暫停與接續」定義一次；`/feature` 第 1 節與 `docs/README.md` 只指向它。新增暫存產物時在表上補這三項，就能套用通用步驟。術語表、ADR、審查紀錄有正式版本時不複製到 scratchpad，術語表與 ADR 之後要修改才複製再改；規格複製成 `<功能>-spec.md`，之後的交付清單要用。
- **審查豁免（只限 scratchpad 遺失）**：通用步驟已能合理處理的情況，審查不得要求逐一增加特定案例，也不因此阻擋合併，reviewer 寫在報告的「已接受的風險」。只有通用步驟處理不了，而且會造成已核准的決定被推翻、正式文件被憑記憶重寫、開發者沒被告知決定或成果遺失時，才列為發現並阻擋。豁免不擴大到其他流程。

## 放棄的做法

- **繼續逐一補時間點**：PR #71 已經證明補不完：每補一個時間點，審查就找到下一個，同一個根本原因連續阻擋。
- **保留常見的時間點情況，再加通用規則**：同一件事有兩套規則，兩者可能不一致；列出的情況也會讓審查繼續要求補上沒列到的時間點。
- **把 scratchpad 改到 repo 內的資料夾**：核准前不改 repo、不開分支是既有的規則（[0009](0009-docs-delivery-and-glossary.md) 放棄「術語核准前直接寫進工作目錄」的理由相同）：工作目錄是開發者與其他 session 共用的，未核准的內容可能被別的 commit 帶走，取消時也要還原。

## 影響

- 遺失後能恢復到哪裡，取決於產品文件與審查紀錄有沒有及時 commit、push；沒有正式版本的部分只能重做或由開發者決定不補。
- 被豁免的情況不再當成發現，審查可能漏掉通用步驟其實處理不好的情況；為此保留三種實際風險仍然阻擋。
- 新增暫存產物時，要同時更新 `/feature` 第 4 節的暫存產物表。
- 0009 的內文與狀態不變；既有規格與審查紀錄裡依時間點寫的規則是當時的紀錄，不回改。
