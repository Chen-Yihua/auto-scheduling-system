# 需求清楚的改動走快速路徑

- 狀態：已核准（2026-11-20）
- 等級：一般（改流程文件裡的規則：`feature`「判斷等級」新增快速路徑，連帶改規格格式、交付與審查的規則。不改程式碼，不涉及資料一致性、認證授權、憑證保護；新增服務、改資料庫或部署才算重大架構決策，這次不是）
- issue：#157
- PR：#167

## 簡短說明

在「一般」等級裡加一條快速路徑：需求已經寫清楚、沒有要開發者決定的事、不碰高風險範圍的改動，規格寫短版，放在 PR 描述，不做規格審查。快速路徑只簡化規格階段：實作、實作審查、核准後改規格的處理都沿用一般流程。另寫 ADR 0018 說明部分推翻 ADR 0002、0006、0007、0012 的理由。

## 背景

來源 issue：https://github.com/Chen-Yihua/auto-scheduling-system/issues/157

**問題**：開發者用 `/issue` 修一個現象和預期都寫清楚的小 bug，也要寫完整規格、做最多 2 次規格審查、實作審查做到沒有阻擋，小改動也要多輪 commit、CI 與決定。

**現況**：

- `.claude/skills/feature/SKILL.md:41-55`「判斷等級」只有高風險、一般、文字修正三級，判斷順序是先看高風險、再看文字修正、都不符合是一般（`:43`）。bug 與小的行為修改都是一般（`:48`）：完整格式的規格、規格審查最多 2 次、實作審查直到沒有阻擋。文字修正只限不改任何規則（`:49`）。
- ADR 0006 決定 bug 也用完整規格並做規格審查，依據是 #28、#46：兩個一開始看起來都是小修正，問題出在驗收條件的矛盾與缺漏。ADR 0007「放棄的做法」不採用「輕量不做規格審查」，理由相同。ADR 0012 決定 2 把原本的輕量併進一般。
- ADR 0002「放棄的做法」不採用「只寫在 PR 描述」，理由是 PR 描述沒有版本紀錄。GitHub 會保留 PR 描述的編輯歷史（描述旁的「edited」）。
- 規格檔放在 `docs/specs/`、一般一定做規格審查，是下面這些地方的前提：
  - `.claude/skills/feature/SKILL.md:11`（規格核准前交給 `specification-reviewer`）、`:23`（流程表第 3 步）。
  - `.claude/agents/feature-implementer.md:9`（交付清單的規格路徑）、`:28-29`（開 PR、把規格開頭的「PR」補上編號）。
  - `.claude/agents/acceptance-reviewer.md:9`（收到的規格檔）、`:15`（規格審查的查證紀錄當作已確認的事實）、`:21`（情境涵蓋與事實查證在規格審查時已經做過；完整格式卻沒有規格審查留言時補查情境；修 bug 時檢查 AC1 與「改程式前是否失敗」）。
  - `.claude/skills/implement-and-review/SKILL.md:41`（交付清單的規格那一行）、`:87-89`（交給 `acceptance-reviewer` 前確認規格審查留言已貼出）、`:115`（「規格問題的處理」第 4 步把 issue 連結寫進規格的「修改紀錄」）。
  - `.claude/skills/write-spec/SKILL.md:10`（規格照 `docs/specs/README.md` 的格式）、`:28`（文字修正以外的等級都做規格審查）。
  - `.claude/skills/issue/SKILL.md:34-36`（規格檔、等級與規格格式、需求問答把「建議的驗收條件」當題目問）。
  - `.claude/skills/feature/references/resume.md:26`（規格草稿的正式版本是 `docs/specs/<功能>.md`）。
  - `.claude/skills/clarify-requirements/SKILL.md:47`（所有等級都用 `<功能>-grill.md`）。
  - `docs/specs/README.md:3`（每個變更一份，文字修正除外）、`:97-99`「各等級的規格」。
  - `docs/reviews/README.md:3`（`<功能>` 和 `docs/specs/` 的規格檔同名）、`:10`（文字修正不審查）。
  - `docs/README.md:9`（`specs/` 是每個變更一份，文字修正除外）。
- 一般做法：`obra/superpowers` 的 [`brainstorming`](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)：需求都在請求裡的清楚小事直接做、做完說明；小改動用一兩行的短設計，核准後才動手。

## 需求

### 快速路徑的條件

1. `.claude/skills/feature/SKILL.md` 新增一節「快速路徑」，放在「判斷等級」之後。開頭寫明：快速路徑只簡化規格階段，實作、實作審查、核准後改規格的處理都沿用一般流程。
2. 先照「判斷等級」決定等級；是一般，才看下面 3 個條件。3 個條件都符合才走快速路徑：
   1. 需求（issue 內容或 `/feature` 的參數）已寫清楚現在的結果與預期的結果。
   2. 沒有要開發者決定的事。
   3. 不碰高風險範圍（「判斷等級」表的高風險一列）。
3. 同一節寫明改動大小不是條件。
4. 主 session 判斷符合時，在規格的等級寫「一般（快速路徑：<符合 3 個條件的理由>）」，和規格一起由開發者核准。
5. 寫短版規格時遇到程式碼看不出來的事：
   - 是業務規則（要開發者決定的事）：算不符合條件 2。
   - 是技術判斷：照 `clarify-requirements`「工程方案探索」依範圍做，結果寫進短版規格的「修法」。

### 規格階段

6. 快速路徑照 `clarify-requirements`「需求理解」簡述需求，不建立 `<功能>-grill.md`，不另外請開發者確認「已確認」清單。
7. 快速路徑把需求理解的簡述與短版規格放在同一則訊息，請開發者核准一次。核准的定義照「硬規則」第 3 條。
8. 快速路徑不做規格審查。
9. 快速路徑的短版規格放在 PR 描述，不存進 `docs/specs/`。
10. 留在快速路徑期間，每次更新 PR 描述都以目前的描述為基礎，短版規格那一段不動。
11. 核准前發現 3 個條件有任何一個不符合時，主 session 告訴開發者，改走一般的完整流程：照 `clarify-requirements`「需求問答」問答、寫完整格式的規格、做規格審查。

### 實作與核准後

12. 快速路徑的實作與實作審查和一般相同，差別只有交付與審查的輸入（見 `implement-and-review`「交付清單」「交給 acceptance-reviewer 審查」）。
13. 核准後任何階段（實作回報、實作審查），修正要改短版規格的驗收條件、背景或修法時，照 `implement-and-review`「規格問題的處理」問開發者：
    1. 開發者決定在這個 PR 補上：改走一般的完整流程（需求 14）。
    2. 開發者決定另開 issue：留在快速路徑，短版規格不動。
14. 核准後改走一般的完整流程：主 session 以短版規格為基礎寫完整格式的規格，和短版規格不同的驗收條件照「核准後修改規格」寫進修改紀錄；照一般流程做規格審查、交給開發者核准、照「交付清單」交給 `feature-implementer`；主 session 照 CLAUDE.md「開發流程」第 3 點，把 PR 描述裡的短版規格換成規格檔的連結。
15. 只改措辭、不改意思的 `nitpick` 不改短版規格。
16. 改走一般的完整流程後，要退回快速路徑需要開發者同意。
17. `implement-and-review`「規格問題的處理」第 4 步（另開 issue）寫明：快速路徑沒有「修改紀錄」，issue 連結附在 PR 描述與那一輪審查留言的「處理」。
18. 「判斷等級」表一般那一列的「規格」「規格審查」兩欄，各加一句「快速路徑見「快速路徑」」；「實作審查」欄與其他列不改。

### 短版規格

## 不做

- 不新增第四個等級：快速路徑是一般等級裡的一條路徑，「只升不降」與「不確定取較高」照舊適用（改走完整流程等同升級）。
- 不把文字修正併進快速路徑，文字修正的流程不改：文字修正不改行為，不需要 `feature-implementer` 與實作審查（ADR 0007）。文字修正改到一半發現會改變程式行為時，照現行規則重新判斷等級；判斷成一般時，一律走一般的完整流程，不走快速路徑：現行規則要求補做問答、把已改的內容併進「實作計畫」，短版規格沒有這兩樣，這種情況也很少走到。
- 「文字修正」的範圍不變：改定義流程或規則的文件裡的規則，仍然是一般或高風險（ADR 0007）。
- 不為快速路徑另外寫實作審查的輪數、改走完整流程後的 PR 編號、`feature`「回報」沒有內容的欄位：一般流程的規則已經涵蓋（「連續 3 輪都還有阻擋」在開發者決定後重新算；主 session 寫完整規格時照格式填 PR）。`feature`「回報」沒有內容的欄位，也不另外寫規則。
- 不改 `specification-reviewer`：快速路徑不會交給它；改走完整流程後收到的是完整規格。
- 不改高風險與文字修正的規則。
- 不回頭改寫既有規格與審查紀錄（`docs/README.md`「生命週期」）。
- 這次沒碰到的舊段落不照寫作規則第 6 條改寫，留給 #165。
- 這次的 PR 本身不走快速路徑：有要開發者決定的事。
