# 審查結果

兩種審查共用這份文件的分類、報告格式與「處理」的寫法。每一輪審查的結果貼成一則公開的 PR 留言，貼法見 `implement-and-review`「審查留言」。`<功能>` 和 `docs/specs/` 裡的規格檔同名；快速路徑沒有規格檔，`<功能>` 和分支名稱相同（`/issue` 是 `issue-<N>-<簡短名稱>`）：

| 審查 | agent | 時機 |
|---|---|---|
| 規格審查 | `specification-reviewer` | 規格核准前；留言在 PR 開好後貼出 |
| 實作審查 | `acceptance-reviewer` | 實作完成後 |

- 等級是「文字修正」的變更不審查，沒有審查留言。什麼時候做規格審查、做幾次，見 `write-spec`「什麼時候做規格審查」「審查次數」；沒做的沒有規格審查留言。
- 審查 agent 只能讀、不能寫檔，所以由主 session 把報告貼成留言。標題開頭是「漏洞：」的內容是例外：repo 是公開的，貼出前照 `implement-and-review`「漏洞的處理」改寫成一般性的描述（或開發者確認建立後的 advisory 編號）。
- `specification/`、`implementation/` 與 `*-round<N>.md` 是改用 PR 留言前的紀錄檔，不再新增。不改寫；沒有持續參考價值時才刪除，條件見 [docs/README.md](../README.md)「生命週期」。

## 分類

每項發現標一個標籤，另外標阻擋或不阻擋，兩件事分開判斷：標籤只描述發現的性質，阻擋看實際影響。

### 標籤

標籤用英文原名：

| 標籤 | 定義 |
|---|---|
| `issue` | 要修的問題，包括會影響需求或驗收條件正確性的寫法 |
| `suggestion` | 可以更好的改法，包括安全改善、讓文字更清楚的改寫 |
| `nitpick` | 只換說法、意思不變的小地方 |
| `question` | 要開發者決定或回答的事，例如未定義的產品行為、權限、資料處理 |

### 阻擋

阻擋（定義見 [docs/README.md](../README.md)「術語表」）依實際影響判斷，和標籤分開：

- 問題的實際影響嚴重到照現在的規格或程式，這次 PR 不應該被接受（規格審查時是規格不應該被核准），標阻擋；否則標不阻擋。
- 評估實際影響時，考量正確性、安全性、可靠性、是否符合需求與驗收條件，以及程式碼健康度（之後讀、改這份程式或文件的難易）。安全、架構、影響大小是評估時的考量，不是另外的分類。
- 不要求完美才能合併：個人偏好、純風格差異、非必要的改善不阻擋。
- `nitpick` 一律不阻擋；`issue`、`suggestion`、`question` 不由標籤決定阻擋，各自依實際影響判斷。

實作審查的 `issue`、`suggestion`，reviewer 在「建議」另外寫：

- 修正要不要改規格；涉及重大架構決策（定義見 `feature`「重大架構決策」）時也寫明。
- 不阻擋的，屬於下面哪一種：
  - 屬於這次 PR：問題出在 `git diff origin/main...HEAD` 改到的程式、測試或文件，或和某條驗收條件有關。
  - 和這次 PR 無關：其他。

reviewer 沒有實際驗證的推論，在「依據」寫明是推論與推斷的步驟。不要把推論寫成確定的事實。

### 漏洞

漏洞是實際可被利用的程式漏洞；安全改善建議不是漏洞，標 `suggestion`。

- 漏洞的標題（摘要表的「標題」欄，也就是問題說明裡冒號後面的那段）開頭寫「漏洞：」，例如 `### #1 \`issue\`（阻擋）：漏洞：…`。阻擋照上面「阻擋」判斷。之後所有「標題開頭是『漏洞：』」都是指這一段。
- 處理照 `implement-and-review`「漏洞的處理」。
- 漏洞不論「特殊情況的判斷」怎麼寫，都照這一節處理。

### 特殊情況的判斷

- **暫存檔遺失時**：`.claude/skills/feature/references/resume.md` 的恢復步驟處理不了，而且會讓已核准的決定被推翻、正式文件被憑記憶重寫，或開發者沒被告知決定或成果遺失時，列成發現。其他遺失的情況寫在報告的「已接受的風險」，不要求替每種情況加規則，因為遺失的時間點列舉不完，每補一個情況，審查就會找到下一個。
- **規格「不做」**：「不做」是開發者依當時已知的事實做的決定，所以只有三種情況列成發現：實作做了「不做」排除的改動、查到「不做」依據的事實不成立（包括實際後果和「不做」寫的不同，或和規格審查的查證紀錄不同，例如實作新增了會產生這個情況的依賴），或規格審查時認為某個情況不該列在「不做」。第一種是實作沒照決定做，第二種是決定的前提變了，第三種是規格還沒核准、決定還能改。其他「不做」寫明不處理的情況，寫在報告的「已接受的風險」。

## 報告格式

兩種 reviewer 的報告都用這個結構。讀者是之後沒看過這次對話、也不熟悉這段程式碼的人：先用使用者的操作與結果說明問題，技術細節放在後面。依據一律寫 `檔案:行號`，引用規格時寫 AC 或假設的編號，不要寫「上面提到的」「這次對話裡」這類只有當下看得懂的說法。

````markdown
## 摘要

- 主要風險：一到三句，用使用者的操作與結果描述，不用函式名稱
- 建議優先處理：#1 → #3 → …，各附一句理由

| # | 標題 | 標籤 | 阻擋 |
|---|---|---|---|

沒有發現時寫「沒有發現」，只留這一節和「技術證據」。

## 問題說明

每項發現都要寫，順序和「摘要」的表相同；`nitpick` 可以只寫「問題」與「建議」。

### #1 `<標籤>`（阻擋／不阻擋）：<一句話標題>

1. **問題**：在什麼操作或條件下（例如同時操作、中途失敗、資料為空），發生了什麼。
2. **影響**：使用者或資料會怎樣；影響哪些驗收條件、假設、檔案或功能。
3. **依據**：程式或規格的哪個部分造成（`檔案:行號`）；互相矛盾的寫出是哪幾條；推論要寫明是推論。
4. **建議**：建議怎麼處理與理由。規格的問題寫出建議的驗收條件。`question` 列出選項、各自的影響，最後寫建議與理由。只是建議，不要寫成已確認的需求。

### 執行過的檢查

跑過的指令與結果（例如 `pytest` 632 passed）。

### <reviewer 各自的檢查表>
````

reviewer 各自的檢查表：

- `specification-reviewer`：「查證紀錄」表與「已接受的風險」。
- `acceptance-reviewer`：「驗收條件」表與「已接受的風險」（列「特殊情況的判斷」的「暫存檔遺失時」判定不算問題的情況，以及規格「不做」裡寫明不處理的情況，另見「特殊情況的判斷」；沒有寫「無」）；沒有規格審查時，另附 `specification-reviewer` 的「查證紀錄」表。

| 同時操作 | | |
| 中途失敗後的資料狀態 | | |
| 和外部系統（Google Calendar、外部平台）的一致性 | | |

「沒有涵蓋」的項目列成 `issue`，阻擋照「阻擋」判斷；「不適用」寫出原因。

## 處理

主 session 在審查檔案最後加的一節，寫這一輪每項發現怎麼處理。決定怎麼記照 `.claude/skills/clarify-requirements/SKILL.md`「記錄決定」。

```markdown
## 處理

| # | 處理方式 | 決定者 | 結果 |
|---|---|---|---|

### 開發者決定

| # | 選項 | 開發者的決定 | 理由 |
|---|---|---|---|
```

- 「#」沿用這一輪報告的編號。
- 「處理方式」：照 `implement-and-review`「發現處理」。
- 「決定者」寫開發者、規則（例如阻擋的發現，不用改規格，直接請 `feature-implementer` 修正），或主 session（照 `implement-and-review`「發現處理」由主 session 決定的項目；規格核准後的修改一律由開發者確認）。
- 「結果」寫下面其中一種：修正的 commit、issue 或 advisory 編號；「不改：<原因>」；「不開 issue：<原因>」；「等開發者決定」；規格審查在核准前，寫「規格已修改」或「開發者決定不採用」。實作審查的留言在這一輪的修正都 commit 後才貼，所以要修的項目直接寫 commit。
- 「開發者決定」表只列開發者決定的項目，寫選項與理由；沒有時寫「無」。
